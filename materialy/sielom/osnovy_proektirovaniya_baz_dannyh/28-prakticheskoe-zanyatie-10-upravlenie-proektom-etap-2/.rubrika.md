## 2. Критериальная шкала оценивания (0–4 балла)

| Балл | Критерий | Дескрипторы требований к решению |
| :---: | :--- | :--- |
| **2** | **Написание скрипта миграции (отлично)** | Безупречный синтаксис DDL-команд прямой миграции `V{N}`. Корректные типы данных, наложение ограничений (`UNIQUE`, `FOREIGN KEY`). Полное соблюдение принципа обратной совместимости (Zero-Downtime): новые колонки либо объявлены как `NULLable`, либо имеют валидное значение `DEFAULT`, гарантирующее сохранение работоспособности старых INSERT-запросов на существующих строках таблицы. |
| **1** | **Написание скрипта миграции (хорошо / частично)** | В целом логика DDL верна, однако допущены несущественные недочеты (например, не задано имя констрейта, либо отсутствует модификатор `IF NOT EXISTS`), при этом структура таблицы создается и данные не разрушаются. |
| **0** | **Написание скрипта миграции (неудовлетворительно)** | Грубая ошибка DDL: колонка объявлена `NOT NULL UNIQUE` без `DEFAULT` на эксплуатируемой таблице (фатальный сбой мигратора); синтаксические ошибки SQL; разрушение первичных ключей или связей. |
| **1** | **Протокол отката и регрессионного теста (зачтено)** | Разработан зеркальный скрипт отката `U{N}` по правилу LIFO (удаление внешних ключей строго до удаления таблиц). Описан валидный регрессионный тест клиентского приложения: проверка работы старых SELECT/INSERT запросов и контроль времени отклика/индексации. |
| **0** | **Протокол отката и регрессионного теста (не зачтено)** | Скрипт отката нарушает ссылочную целостность (пытается удалить таблицу, на которую ссылается FK); оставляет мусорные объекты; регрессионный тест не описан или содержит бессмысленный набор символов. |
| **1** | **Выводы и самопроверка (зачтено)** | Корректно сформирована строка системного аудита `flyway_schema_history` (все обязательные поля заполнены). Даны развернутые, глубокие и технически грамотные ответы на оба вопроса самопроверки. |
| **0** | **Выводы и самопроверка (не зачтено)** | Запрос фиксации в системную таблицу версий пропущен; ответы на контрольные вопросы отсутствуют либо содержат грубейшие антипаттерны («миграции не нужны, проще руками поправить в pgAdmin»). |

## 3. Полные закрытые эталоны решений по 4 практическим сценариям

### Вариант 1. Складской комплекс

#### 1. DDL прямой миграции: `V2__add_barcode_ean13.sql`
```sql
-- Миграция V2: Добавление штрихкода EAN-13 в таблицу товаров
-- Требование Zero-Downtime: колонка создается NULLable, чтобы старые терминалы могли вставлять товары
ALTER TABLE products 
    ADD COLUMN IF NOT EXISTS barcode_ean13 VARCHAR(13) NULL;

-- Добавление уникального ограничения (NULL-значения не конфликтуют в стандарте SQL)
ALTER TABLE products 
    ADD CONSTRAINT uq_products_barcode UNIQUE (barcode_ean13);

-- Комментарий к метаданным
COMMENT ON COLUMN products.barcode_ean13 IS 'Уникальный международный штрихкод товара стандарта EAN-13';
```

#### 2. DDL скрипта отката: `U2__drop_barcode_ean13.sql`
```sql
-- Откат миграции V2: удаление ограничения и колонки
ALTER TABLE products 
    DROP CONSTRAINT IF EXISTS uq_products_barcode;

ALTER TABLE products 
    DROP COLUMN IF EXISTS barcode_ean13;
```

#### 4. Протокол регрессионного теста
```text
Сценарий 1: Старый запрос поиска товара терминалом сбора данных (TSD v1.0):
SELECT product_id, title, price_rub, stock_qty 
FROM products 
WHERE category = 'Электроника' AND stock_qty > 0;
Результат: Успешно возвращено 120 строк. Время выполнения: 12 мс.

Сценарий 2: Создание товара через старую экранную форму без поля barcode_ean13:
INSERT INTO products (title, category, price_rub, stock_qty) 
VALUES ('Тестовый кабель USB-C', 'Аксессуары', 450.00, 50);
Результат: Успешная вставка (ID=10001). Поле barcode_ean13 заполнено значением NULL.
Вывод: Обратная совместимость с клиентами v1.0 сохранена на 100%.
```

#### 5. Эталон ответов на самопроверку
1. В реляционном стандарте SQL значение `NULL` означает отсутствие данных («неизвестно»). Согласно правилам трехзначной логики (3VL), сравнение `NULL = NULL` дает `UNKNOWN`, а не `TRUE`. Поэтому уникальное ограничение (`UNIQUE`) разрешает неограниченное количество строк со значением `NULL`, контролируя уникальность строго среди непустых значений.
2. Если применить `ADD COLUMN NOT NULL UNIQUE` без `DEFAULT` на таблице с 10 000 записей, СУБД моментально аварийно прервет транзакцию. Причина: СУБД попытается заполнить существующие 10 000 строк значением `NULL`, что нарушит ограничение `NOT NULL`. Если же задать статический `DEFAULT '0000000000000'`, то миграция упадет на ограничении `UNIQUE`, так как 10 000 строк получат одинаковое дефолтное значение.

### Вариант 2. Гостиничный сервис

#### 1. DDL прямой миграции: `V3__add_booking_sources.sql`
```sql
-- 1. Создание справочника источников бронирования
CREATE TABLE IF NOT EXISTS booking_sources (
    source_id SERIAL PRIMARY KEY,
    source_name VARCHAR(50) NOT NULL UNIQUE,
    commission_pct NUMERIC(4, 2) NOT NULL DEFAULT 0.00,
    is_active BOOLEAN NOT NULL DEFAULT TRUE
);

-- 2. Наполнение справочника (ID=1 — дефолтный источник для офлайн-регистрации)
INSERT INTO booking_sources (source_id, source_name, commission_pct) VALUES
    (1, 'Стойка регистрации (Прямой визит)', 0.00),
    (2, 'Официальный сайт отеля', 0.00),
    (3, 'Сервис Островок!', 15.00),
    (4, 'Яндекс.Путешествия', 14.00)
ON CONFLICT (source_id) DO NOTHING;

-- Корректировка последовательности SERIAL
SELECT setval('booking_sources_source_id_seq', (SELECT MAX(source_id) FROM booking_sources));

-- 3. Добавление внешнего ключа в таблицу Бронирования с DEFAULT 1 (Zero-Downtime)
ALTER TABLE bookings 
    ADD COLUMN IF NOT EXISTS source_id INT NOT NULL DEFAULT 1;

ALTER TABLE bookings 
    ADD CONSTRAINT fk_bookings_source 
    FOREIGN KEY (source_id) REFERENCES booking_sources(source_id)
```

### Вариант 3. Банковский портал

#### 1. DDL прямой миграции (фаза Expand): `V4__extract_client_passports.sql`
```sql
-- 1. Создание защищенной таблицы паспортных данных
CREATE TABLE IF NOT EXISTS client_passports (
    passport_id SERIAL PRIMARY KEY,
    client_id INT NOT NULL UNIQUE,
    doc_series VARCHAR(10) NOT NULL,
    doc_number VARCHAR(15) NOT NULL,
    issue_date DATE NOT NULL DEFAULT CURRENT_DATE,
    issued_by VARCHAR(255) NOT NULL DEFAULT 'МВД РОССИИ',
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_passports_client FOREIGN KEY (client_id) 
        REFERENCES clients(client_id) ON DELETE CASCADE
);

-- 2. DML Перенос существующих данных (Backfill)
-- Извлекаем серию (первые 4 символа) и номер (оставшиеся) из сырой строки
INSERT INTO client_passports (client_id, doc_series, doc_number, issued_by)
SELECT 
    client_id,
    SUBSTRING(passport_raw FROM 1 FOR 4) AS doc_series,
    TRIM(SUBSTRING(passport_raw FROM 5)) AS doc_number,
    'Миграция v4: первичное заполнение' AS issued_by
FROM clients
WHERE passport_raw IS NOT NULL AND passport_raw <> ''
ON CONFLICT (client_id) DO NOTHING;

-- ВАЖНО: Колонка clients.passport_raw НЕ УДАЛЯЕТСЯ на этапе Expand!
```

#### 2. DDL скрипта отката: `U4__rollback_client_passports.sql`
```sql
-- Безопасный откат: синхронизация новых паспортов обратно в строку клиентов перед удалением
UPDATE clients c
SET passport_raw = cp.doc_series || ' ' || cp.doc_number
FROM client_passports cp
WHERE c.client_id = cp.client_id;

-- Удаление новой таблицы
DROP TABLE IF EXISTS client_passports;
```

```text
Сверка количества перенесенных записей:

    (SELECT COUNT(*) FROM clients WHERE passport_raw IS NOT NULL) AS old_cnt,

Результат: old_cnt = 42500, new_cnt = 42500. Контрольные суммы совпали.

Тест старой формы открытия счета операционистом:

```

#### 5. Эталон ответов на самопроверку
1. На этапе Expand удалять старую колонку категорически запрещено, так как в распределенной системе старые версии клиентских приложений (например, банкоматы, мобильные клиенты или внешние шлюзы) продолжают читать и писать поле `passport_raw`. Мгновенное удаление приведет к генерации ошибок 500.
2. Фазу Contract (удаление колонки `ALTER TABLE clients DROP COLUMN passport_raw;`) разрешается выполнять только после того, как: 1) 100% клиентских приложений обновлены до новой версии и переключены на чтение/запись в `client_passports`; 2) успешно отработал фоновый бэкфилл всех исторических записей; 3) завершен период опытно-промышленной эксплуатации (обычно от 2 до 4 недель) без инцидентов.

#### 4. Протокол регрессионного теста производительности
```text
Тестируемый запрос сводной ведомости:
EXPLAIN ANALYZE 
SELECT student_id, score, status 
FROM exam_results 
WHERE submission_date BETWEEN '2026-06-01' AND '2026-06-30' 
  AND student_id = 45892;

1. План выполнения ДО создания индекса (V4):
   Seq Scan on exam_results (cost=0.00..48520.00 rows=15 width=18) (actual time=1240.150..14210.820 rows=4 loops=1)
   Planning Time: 0.182 ms
   Execution Time: 14211.205 ms (14.2 сек — деградация производительности)

2. План выполнения ПОСЛЕ создания индекса (V5):
   Bitmap Index Scan on idx_exam_results_date_student (cost=4.20..15.30 rows=4 width=18) (actual time=0.045..0.048 rows=4 loops=1)
   Planning Time: 0.210 ms
   Execution Time: 0.082 ms

Вывод: Время выборки сократилось с 14 211 мс до 0.08 мс (ускорение более чем в 170 000 раз). Риск таймаута веб-портала ликвидирован.
```

#### 5. Эталон ответов на самопроверку
1. В составном индексе B-Tree данные физически упорядочиваются сначала по первой колонке (`submission_date`), а внутри одинаковых дат — по второй колонке (`student_id`). Если запрос фильтрует только по второй колонке (`WHERE student_id = 45`), СУБД не сможет выполнить эффективный точечный поиск и применит полное сканирование (Index Skip Scan либо Seq Scan). Ведущая колонка индекса должна соответствовать предикатам с наибольшей селективностью и наиболее частым фильтрам.
2. Создание обычного индекса (`CREATE INDEX`) захватывает блокировку `ShareLock` на таблицу `exam_results`. Эта блокировка разрешает чтение (SELECT), но полностью блокирует любые операции вставки, обновления и удаления (INSERT, UPDATE, DELETE). На таблице в 2 000 000 строк построение индекса может занять несколько минут, в течение которых все преподаватели и студенты получат отказ в сохранении оценок (Deadlocks / Connection pool exhaustion). Опция `CONCURRENTLY` строит индекс в фоновом режиме без блокировки пишущих транзакций.

## 4. Классификатор типовых студенческих ошибок и штрафные баллы

| Код ошибки | Описание ошибки и ее деструктивные последствия | Штраф |
| :---: | :--- | :---: |
| **ERR-01** | **Деструктивный NOT NULL:** Добавление обязательной колонки без `DEFAULT` на существующей таблице, ломающее обратную совместимость с клиентами v1.0. | **-1.0 балл** |
| **ERR-02** | **Асимметричный Rollback:** Скрипт отката удаляет таблицу до удаления внешнего ключа, вызывая ошибку целостности СУБД (`Foreign key violation`). | **-0.5 балла** |
| **ERR-03** | **Преждевременный Contract:** Удаление старой колонки на шаге Expand в сценарии с разделением таблиц, приводящее к падению старых клиентов. | **-1.0 балл** |
| **ERR-04** | **Синтаксические ошибки DDL:** Несогласованные типы данных, пропущенные запятые, незакрытые скобки в SQL-скриптах. | **-0.5 балла** |
| **ERR-05** | **Отсутствие регрессионного теста:** Студент сдал только скрипты создания, но не описал и не проверил работу старых запросов. | **-0.5 балла** |
| **ERR-06** | **Пропуск вопросов самопроверки:** Не заполнены аналитические выводы или даны односложные отписки без технической аргументации. | **-0.5 балла** |
