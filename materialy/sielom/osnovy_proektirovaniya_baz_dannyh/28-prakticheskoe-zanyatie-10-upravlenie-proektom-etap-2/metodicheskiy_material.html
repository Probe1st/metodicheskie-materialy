1. Педагогическая концепция и целеполагание

Настоящее занятие завершает проектировочно-эксплуатационный цикл учебного курса ОП.08. Если на предыдущих занятиях обучающиеся осваивали нормализацию, создание реляционных объектов, триггеры, индексы и создание клиентских форм с безопасной аутентификацией, то занятие №28 погружает будущих техников-программистов в реальную промышленную практику эволюции структур баз данных (Database Schema Evolution & Versioning).

Ключевая дидактическая цель: Сформировать устойчивые практические навыки управления жизненным циклом и эволюцией схемы БД с использованием профессиональных инструментов миграций (Flyway, Liquibase), версионирования DDL-скриптов, накатов (migrate), безопасных откатов (rollback), применения архитектурного паттерна расширения-сжатия (Expand/Contract) при непрерывном развертывании (Zero-Downtime Deployment) и проведения комплексного регрессионного тестирования клиентских приложений.

Комплекс образовательных задач:

  • Образовательные (обучающие):
    • Освоить принципы декларативного и императивного версионирования схемы БД;
    • Изучить структуру, назначение и алгоритм валидации служебной мета-таблицы flyway_schema_history (контрольные суммы CRC32/SHA-256, статусы исполнения, временные метки);
    • Освоить синтаксис и правила наименования файлов версионированных миграций (V{Version}__{Description}.sql), скриптов отката (U{Version}__{Description}.sql) и повторяемых миграций (R__{Description}.sql);
    • Отработать шаблон непрерывного развертывания без остановки сервиса (Zero-Downtime Deployment: фаза Expand, фаза переходного дублирования, фаза Contract);
    • Сформировать методологию регрессионного тестирования прикладного ПО после DDL-изменений.
  • Развивающие:
    • Развивать системное инженерное мышление, способность прогнозировать риски блокировки таблиц (Table Locks) и деградации производительности в высоконагруженных промышленных базах данных;
    • Сформировать критическое отношение к «ручным правкам» схемы на продуктивных серверах (ClickOps/Ad-hoc DDL) и привить культуру Database as Code (DbaC).
  • Воспитательные:
    • Воспитывать профессиональную дисциплину релиз-инженера, ответственность за целостность данных пользователей и непрерывность бизнес-процессов организации.

3. Фундаментальный технологический стек: Эволюция схемы БД

3.1. Системы миграций: Flyway vs Liquibase

Эволюция схемы БД в современных продуктовых командах подчиняется принципам CI/CD. Прямой доступ разработчиков к боевым серверам блокируется; все изменения DDL оформляются в виде версионированных скриптов, хранящихся в Git.

  • Flyway: легковесный SQL-first инструмент. Каждое изменение оформляется как чистый SQL-файл строгого формата наименования. Минимальный порог входа, абсолютный контроль над нативными возможностями конкретной СУБД (PostgreSQL, MySQL, Oracle, MS SQL).
  • Liquibase: СУБД-агностичный инструмент. Поддерживает форматы XML, YAML, JSON и SQL (Changesets). Автоматически преобразует абстрактные типы и операции в DDL целевой СУБД, однако имеет более сложный синтаксис.

3.2. Соглашение об именовании миграций Flyway

V1__init_schema.sql       -- Версионированная миграция (Versioned): выполняется строго один раз
V2__add_barcode_col.sql   -- Следующая версия схемы (накат)
U2__add_barcode_col.sql   -- Undo-миграция (обратный откат для версии 2)
R__recreate_views.sql     -- Повторяемая миграция (Repeatable): выполняется при каждом изменении хэша файла
B3__cleanup_old_data.sql  -- Baseline-миграция (базовая точка отсчета)

3.3. Служебная таблица версий: flyway_schema_history

При первом запуске мигратора в базе данных создается техническая таблица, отслеживающая состояние каждого скрипта:

CREATE TABLE flyway_schema_history (
    installed_rank INT NOT NULL PRIMARY KEY,   -- Порядковый номер выполнения миграции
    version VARCHAR(50) NULL,                  -- Номер версии (NULL для Repeatable миграций)
    description VARCHAR(200) NOT NULL,         -- Описание из названия файла (замена _ на пробелы)
    type VARCHAR(20) NOT NULL,                 -- Тип: SQL, UNDO, BASELINE
    script VARCHAR(1000) NOT NULL,             -- Имя файла миграции (например, V2__add_barcode.sql)
    checksum INT NULL,                         -- CRC32 или SHA-256 контрольная сумма файла
    installed_by VARCHAR(100) NOT NULL,        -- Пользователь БД, выполнивший накат
    installed_on TIMESTAMP DEFAULT CURRENT_TIMESTAMP, -- Дата и время наката
    execution_time INT NOT NULL,               -- Длительность исполнения в миллисекундах
    success BOOLEAN NOT NULL                   -- Флаг успешности (TRUE/FALSE)
);
Правило иммутабельности: Как только миграция применилась на production, файл V{N}__*.sql замораживается. Любое ручное исправление текста примененного файла изменит контрольную сумму (checksum), что приведет к аварийной остановке сборки с ошибкой ValidateFailedException: Migration checksum mismatch for migration version X.

3.4. Обеспечение Zero-Downtime Deployment: Паттерн Expand/Contract

При непрерывном развертывании (Blue-Green или Rolling Deployments) в течение определенного времени новая и старая версии клиентского приложения обращаются к одной и той же схеме БД одновременно. Если разработчик выполнит деструктивный DDL (удаление колонки, переименование, добавление NOT NULL без дефолта), старая версия упадет с ошибкой 500.

Для предотвращения простоев применяется паттерн расширения-сжатия (Expand / Contract):

  1. Фаза 1: Расширение (Expand): В базу добавляется новая колонка или таблица со смягченными ограничениями (NULLable, дефолтные значения). Старые колонки остаются нетронутыми.
  2. Фаза 2: Параллельная запись и бэкфилл (Write Both / Transition): Приложение версии N+1 начинает писать данные одновременно в старую и новую структуры. Фоновым скриптом (backfill) обновляются исторические данные.
  3. Фаза 3: Переключение чтения (Read New): Новая версия приложения переключает все SELECT-запросы на новую структуру. Старая колонка больше не читается.
  4. Фаза 4: Сжатие (Contract): После полного вывода из эксплуатации старой версии приложения накатывается миграция очистки (DROP COLUMN / DROP TABLE), удаляющая устаревшие артефакты.

4. Методология регрессионного тестирования после DDL-изменений

После проведения миграций разработчик обязан провести регрессионное тестирование, подтверждающее, что модификация схемы не нарушила работу существующих компонентов.

Вектор проверки Потенциальный риск дефекта Регрессионный тестовый сценарий
Обратная совместимость INSERT Новая колонка объявлена как NOT NULL без DEFAULT, из-за чего старый код вставки падает с ошибкой СУБД. Выполнение типового SQL-запроса INSERT из старой версии клиента (без упоминания новой колонки). Запись должна успешно создаваться.
Стабильность представлений и процедур Переименование или перенос полей ломает скомпилированные представления (VIEW), функции и триггеры. Вызов представлений и сохраненных процедур. Проверка состояния системного каталога на отсутствие инвалидированных объектов.
Производительность (Query Performance) Отсутствие или повреждение индексов после реструктуризации приводит к переходу СУБД в режим полного сканирования (Seq Scan / Table Scan). Анализ плана выполнения тяжелых запросов через EXPLAIN ANALYZE до и после миграции. Контроль времени отклика сводных отчетов.
Идемпотентность и обратимость Скрипт миграции падает при повторном запуске, либо откат оставляет в базе "фантомные" объекты. Тестовый накат: Migrate → Rollback → Migrate. Схема базы до и после цикла должна быть побайтово идентична.

5. Классификатор типовых студенческих ошибок и педагогические приемы

Ошибка №1: Добавление колонки NOT NULL без значения по умолчанию
Студенческий код: ALTER TABLE goods ADD COLUMN barcode VARCHAR(13) NOT NULL;
Последствия: Если таблица содержит хотя бы одну строку, СУБД отвергнет выполнение запроса (ошибка нарушения NOT NULL). Если таблица пуста, миграция пройдет, но любое старое приложение при вставке рухнет.
Педагогический прием: Попросить студента предварительно наполнить таблицу 10 тестовыми строками и попробовать запустить свой скрипт. Продемонстрировать необходимость конструкции DEFAULT 'DEFAULT_VALUE' либо добавления ограничения в два этапа.
Ошибка №2: Попытка ручного редактирования уже примененного файла миграции
Действие студента: Обнаружив опечатку в типе данных, студент исправляет файл V1__baseline.sql вместо создания миграции V2__fix_column.sql.
Последствия: Несоответствие хэша flyway_schema_history.checksum и падение сборки.
Педагогический прием: Показать студенту лог ошибки Flyway. Объяснить концепцию «журнала проводок»: в бухгалтерском учете ошибки не стирают ластиком, а проводят сторнирующую операцию.
Ошибка №3: Неполный Undo-скрипт отката (асимметричный rollback)
Студенческий код: В V3 создается таблица и внешний ключ, а в U3 удаляется только внешний ключ, таблица остается в схеме.
Последствия: База находится в «грязном» промежуточном состоянии, повторный накат невозможен (ошибка «Table already exists»).
Педагогический прием: Правило зеркала: каждое действие в прямом скрипте должно иметь строго обратную команду в обратном порядке (LIFO: Last In, First Out).

6. Критерии оценивания практической работы (4-балльная шкала)

  • 2 балла — Проектирование DDL-скрипта миграции: Безупречный синтаксис прямой миграции (V{N}), правильное наименование, обеспечение обратной совместимости (дефолтные значения для NOT NULL, сохранение старых связей), корректность типов данных и констрейнтов.
  • 1 балл — Протокол отката (Undo) и регрессионного теста: Зеркальный скрипт отката (U{N}), возвращающий схему в исходное состояние без потери связности; корректно оформленный протокол регрессионной проверки старых сценариев.
  • 1 балл — Заполнение системного журнала и выводы самопроверки: Точный расчет метаданных flyway_schema_history (версия, описание, тип, хэш, статус); исчерпывающие и аргументированные ответы на теоретические контрольные вопросы.

Штрафные вычеты: синтаксическая ошибка DDL — -0.5 б.; отсутствие зеркальности в Undo-скрипте — -0.5 б.; пропуск регрессионного теста — -0.5 б.; отсутствие ответов на вопросы самопроверки — -0.5 б.
