# Закрытая критериальная рубрика преподавателя: Значения и ограничения поля (CHECK, IN, RegEx)

Данный документ представляет собой закрытый методический инструмент преподавателя дисциплины «ОП.08 Основы проектирования баз данных» (СИЭУиП) для практического занятия №12 (Занятие №34) и содержит критериальную шкалу оценивания, полные эталонные решения для всех 4 практических вариантов интерактивного рабочего листа `zanyatie.html`, эталон резервного домашнего задания `domashnee_zadanie.html` и классификатор типовых студенческих ошибок со шкалой штрафных вычетов.

## 1. Паспорт оценивания занятия

- **Дисциплина:** ОП.08 Основы проектирования баз данных.
- **Тематический раздел:** Тема 5. Организация запросов SQL (§2.2 с.7–8 программы).
- **Тема занятия:** Практическое занятие №12: значения и ограничения поля (Занятие №34).
- **Вид занятия:** Практическое занятие (2 академических часа: 80 минут основной регламент / 60 минут сокращенный).
- **Форма контроля:** Проверка индивидуального аналитического, практического и тестового продукта в интерактивном рабочем листе `zanyatie.html` (4 дифференцированных варианта) либо в резервном дистанционном задании `domashnee_zadanie.html`.
- **Критериальная шкала:** 4-балльная шкала (проектирование ограничений CHECK — 2 б., протокол негативного тестирования — 1 б., выводы и самопроверка — 1 б.):
  * **Часть 1. Проектирование ограничений целостности CHECK (диапазоны, перечисления IN, регулярные выражения RegEx):** **2 балла** (1 балл при синтаксических неточностях, неполном охвате бизнес-правил или отсутствии именования `CONSTRAINT`; 0 баллов при неработоспособном DDL или отсутствии ограничений).
  * **Часть 2. Протокол негативного тестирования недопустимого ввода и перехват ошибок (`check_violation`, SQLSTATE 23514):** **1 балл** (0.5 балла при пропуске граничных тестов или неполном описании перехваченного исключения СУБД; 0 баллов при отсутствии негативных тестов).
  * **Часть 3. Инженерные выводы, сравнительный анализ клиентской/серверной валидации и самопроверка:** **1 балл** (0.5 балла при поверхностном описании без сопоставления уровней валидации и трёхзначной логики SQL NULL; 0 баллов при отсутствии выводов).
- **Итоговая оценка:**
  * **4 балла** — «Отлично» (DDL-код безупречен, ограничения именованы, тестовый протокол содержит точные граничные и запредельные значения с фиксацией кода ошибки 23514, выводы глубокие и технически аргументированные);
  * **3 балла** — «Хорошо» (ограничения корректны, протокол тестирования заполнен, допущены мелкие погрешности в регулярном выражении или формулировке выводов);
  * **2 балла** — «Удовлетворительно» (реализованы лишь простейшие диапазоны чисел, регулярные выражения или составные предикаты не освоены, протокол тестирования фрагментарен);
  * **0–1 балл** — «Не зачтено» (грубые ошибки в DDL, синтаксис CHECK не работает, протокол негативного тестирования отсутствует).

## 3. Эталоны решений рабочего листа `zanyatie.html`

### Вариант 1: Таблица «Сотрудники» (employees)
**Бизнес-правила:** Возраст от 18 до 70 лет (вычисляемый или по дате рождения / прямому полю возраста); оклад не менее МРОТ (19 242 руб.); валидация СНИЛС по регулярному выражению (формат `XXX-XXX-XXX YY` или `XXX-XXX-XXX-YY` / 11 цифр с разделителями: 3 цифры, дефис, 3 цифры, дефис, 3 цифры, пробел/дефис, 2 цифры).

#### Задание 1.1: Проектирование DDL-структуры таблицы с ограничениями CHECK
```sql
CREATE TABLE employees (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(150) NOT NULL,
    birth_date DATE NOT NULL,
    age INT NOT NULL,
    salary NUMERIC(12, 2) NOT NULL,
    snils VARCHAR(14) NOT NULL,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT chk_employees_age CHECK (age >= 18 AND age <= 70),
    CONSTRAINT chk_employees_salary CHECK (salary >= 19242.00),
    CONSTRAINT chk_employees_snils CHECK (snils ~ '^[0-9]{3}-[0-9]{3}-[0-9]{3} [0-9]{2}$')
);

-- Альтернативная проверка возраста через дату рождения:
-- CONSTRAINT chk_employees_birth_date CHECK (birth_date <= CURRENT_DATE - INTERVAL '18 years' AND birth_date >= CURRENT_DATE - INTERVAL '70 years')
```

#### Задание 1.2: Протокол негативного тестирования недопустимого ввода
1. **Тест 1 (Возраст < 18):**
   ```sql
   INSERT INTO employees (full_name, birth_date, age, salary, snils)
   VALUES ('Иванов Иван Иванович', '2010-05-15', 16, 25000.00, '123-456-789 01');
   ```
   *Результат СУБД:* `ERROR: new row for relation "employees" violates check constraint "chk_employees_age"`
   *SQLSTATE:* `23514` (`check_violation`). Строка отклонена, транзакция прервана.

2. **Тест 2 (Оклад ниже МРОТ):**
   ```sql
   INSERT INTO employees (full_name, birth_date, age, salary, snils)
   VALUES ('Петрова Анна Сергеевна', '1995-03-20', 31, 15000.00, '234-567-890 12');
   ```
   *Результат СУБД:* `ERROR: new row for relation "employees" violates check constraint "chk_employees_salary"`
   *SQLSTATE:* `23514` (`check_violation`).

3. **Тест 3 (Некорректный формат СНИЛС — буквы вместо цифр):**
   ```sql
   INSERT INTO employees (full_name, birth_date, age, salary, snils)
   VALUES ('Сидоров Петр Алексеевич', '1988-11-10', 38, 45000.00, '123-45A-789 01');
   ```
   *Результат СУБД:* `ERROR: new row for relation "employees" violates check constraint "chk_employees_snils"`
   *SQLSTATE:* `23514` (`check_violation`).

4. **Тест 4 (Позитивный тест — граничные корректные значения):**
   ```sql
   INSERT INTO employees (full_name, birth_date, age, salary, snils)
   VALUES ('Смирнов Алексей Викторович', '2008-01-01', 18, 19242.00, '111-222-333 44')
   RETURNING id, full_name, age, salary, snils;
   ```
   *Результат СУБД:* `INSERT 0 1`. Запись успешно сохранена.

### Вариант 2: Таблица «Аренда помещений» (lease_contracts)
**Бизнес-правила:** Площадь помещения > 0; арендная ставка > 0; дата окончания аренды строго позже даты начала; статус договора из перечисления `'DRAFT'`, `'ACTIVE'`, `'TERMINATED'`.

```sql
CREATE TABLE lease_contracts (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    contract_number VARCHAR(50) NOT NULL UNIQUE,
    premises_area NUMERIC(8, 2) NOT NULL,
    rental_rate NUMERIC(10, 2) NOT NULL,
```

### Вариант 4: Таблица «Студенческие работы» (student_submissions)
**Бизнес-правила:** Оценка по шкале от 2 до 5 (`grade BETWEEN 2 AND 5` или `NULL` до проверки); процент оригинальности/плагиата от 0.00 до 100.00% (`plagiarism_percent BETWEEN 0.00 AND 100.00`); ссылка на репозиторий проверяется регулярным выражением (`^https://(github|gitlab)\.com/[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+$`).

#### Задание 4.1: Проектирование DDL-структуры таблицы с ограничениями CHECK
```sql
CREATE TABLE student_submissions (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    student_id BIGINT NOT NULL,
    assignment_id BIGINT NOT NULL,
    submission_url VARCHAR(255) NOT NULL,
    plagiarism_percent NUMERIC(5, 2) NOT NULL,
    grade INT NULL,
    submitted_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT chk_submission_grade CHECK (grade IS NULL OR (grade >= 2 AND grade <= 5)),
    CONSTRAINT chk_submission_plagiarism CHECK (plagiarism_percent >= 0.00 AND plagiarism_percent <= 100.00),
    CONSTRAINT chk_submission_url CHECK (submission_url ~* '^https://(github|gitlab)\.com/[a-z0-9_.-]+/[a-z0-9_.-]+$')
);
```

## 4. Эталон резервного домашнего задания `domashnee_zadanie.html`

**Тема:** Проектирование комплексных ограничений CHECK для интернет-магазина (таблица `ecommerce_orders`).

### Эталонный DDL:
```sql
CREATE TABLE ecommerce_orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_code VARCHAR(30) NOT NULL UNIQUE,
    customer_email VARCHAR(100) NOT NULL,
    customer_phone VARCHAR(20) NOT NULL,
    total_amount NUMERIC(12, 2) NOT NULL,
    discount_amount NUMERIC(10, 2) NOT NULL DEFAULT 0.00,
    status VARCHAR(20) NOT NULL DEFAULT 'NEW',
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP NOT NULL,
    delivery_date DATE NULL,
    
    -- Ограничение формата кода заказа: ORD-YYYY-NNNNNN
    CONSTRAINT chk_orders_code CHECK (order_code ~ '^ORD-[0-9]{4}-[0-9]{6}$'),
    
    -- Валидация Email через RegEx:
    CONSTRAINT chk_orders_email CHECK (customer_email ~* '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$'),
    
    -- Валидация телефона (РФ: +7XXXXXXXXXX):
    CONSTRAINT chk_orders_phone CHECK (customer_phone ~ '^\+7[0-9]{10}$'),
    
    -- Сумма заказа и скидка:
    CONSTRAINT chk_orders_total CHECK (total_amount > 0),
    CONSTRAINT chk_orders_discount CHECK (discount_amount >= 0 AND discount_amount < total_amount),
    
    -- Статусная модель:
    CONSTRAINT chk_orders_status CHECK (status IN ('NEW', 'PAID', 'PROCESSING', 'SHIPPED', 'DELIVERED', 'CANCELLED')),
    
    -- Согласованность даты доставки:
    CONSTRAINT chk_orders_delivery CHECK (delivery_date IS NULL OR delivery_date >= created_at::DATE)
);
```

## 5. Классификатор типичных ошибок студентов и штрафные баллы

| Типовая ошибка студента | Характер проявления и методические последствия | Штраф |
| :--- | :--- | :--- |
| **Безымянные ограничения CHECK** | Использование синтаксиса `salary NUMERIC CHECK (salary >= 19242)`. СУБД присваивает автоматически сгенерированное имя (например, `employees_salary_check`), что делает диагностику и миграцию схемы трудночитаемой в production. | **-0.5 б.** |
| **Игнорирование NULL и трёхзначной логики SQL** | Студент не учитывает, что условие `CHECK (grade >= 2 AND grade <= 5)` вернет `UNKNOWN` при `grade IS NULL`. Так как ограничение CHECK срабатывает только при строгом `FALSE`, значение NULL успешно запишется, если колонка не объявлена `NOT NULL`. Если бизнес-логика запрещает NULL, студент обязан объявлять `NOT NULL`. | **-0.5 б.** |
| **Ошибки в регулярных выражениях** | Отсутствие привязок начала и конца строки `^` и `$`, из-за чего строка `'ABC 123-456-789 01 XYZ'` проходит валидацию СНИЛС. Использование регистрозависимого оператора `~` вместо `~*` при валидации email. | **-0.5 б.** |
| **Межколоночное ограничение на уровне столбца** | Попытка объявить ограничение, использующее два поля (например, `end_date DATE CHECK (end_date > start_date)`), в строке определения отдельного столбца. В SQL ограничение на уровне столбца может ссылаться только на сам этот столбец. Межколоночные ограничения объявляются строго на уровне таблицы (`CONSTRAINT chk_dates CHECK (end_date > start_date)`). | **-0.5 б.** |
| **Отсутствие граничных тестов в протоколе** | Тестируются только тривиальные значения (например, оклад 10 000 и 50 000), но не проверяется граничное значение 19 242 (МРОТ) и 19 241 (граница ошибки). | **-0.5 б.** |
| **Иллюзия достаточности фронтенд-валидации** | В аналитическом выводе студент заявляет, что валидации на HTML5-форме или в JavaScript достаточно, а ограничения в БД дублируют работу и замедляют систему. Ошибка свидетельствует о непонимании архитектуры безопасности (прямые API-запросы, консоль psql, обход интерфейса). | **-0.5 б.** |
