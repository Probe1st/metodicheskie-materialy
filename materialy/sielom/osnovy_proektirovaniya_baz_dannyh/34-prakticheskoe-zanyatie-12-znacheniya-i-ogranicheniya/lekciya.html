Значения и ограничения поля (CHECK, IN, RegEx)

Каталог синтаксических конструкций целостности данных, правила сопоставления с регулярными выражениями и обработка исключений ядра СУБД

1. Доменная целостность данных в реляционной модели

В реляционной теории Эдгара Кодда под доменом (Domain) понимается семантически осмысленное множество допустимых значений конкретного атрибута сущности. Базовых типов данных (таких как INTEGER, NUMERIC или VARCHAR) недостаточно для гарантии бизнес-корректности:

  • Числовой тип INT допускает отрицательные значения (-100 лет, -500 рублей оклада);
  • Строковый тип VARCHAR(100) позволяет записать любую бессмысленную строку вместо адреса электронной почты или ИНН;
  • Дата DATE позволяет указать дату закрытия договора раньше даты его открытия.

Для предотвращения сохранения некорректных данных стандарт ANSI SQL и СУБД PostgreSQL предоставляют механизм ограничений CHECK.

2. Каталог синтаксиса ограничений CHECK

2.1. Ограничение на уровне столбца (Column Constraint)

Объявляется непосредственно при описании поля таблицы. Может содержать ссылки только на значение этого конкретного столбца:

CREATE TABLE products (
 id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
 name VARCHAR(120) NOT NULL,
 price NUMERIC(10, 2) NOT NULL CHECK (price > 0),
 stock_qty INT NOT NULL CHECK (stock_qty >= 0));

2.2. Ограничение на уровне таблицы (Table Constraint)

Объявляется отдельной строкой таблицы через ключевые слова CONSTRAINT имя CHECK (условие). Преимущества явного табличного ограничения:

  1. Явное системное имя: в логах ошибок и диагностических сообщениях выводится читаемое имя (например, chk_products_price вместо системного products_price_check);
  2. Межколоночные проверки: возможность сопоставлять значения нескольких столбцов одной строки;
  3. Удобство миграции: легко удалять или отключать через ALTER TABLE tbl DROP CONSTRAINT chk_name;.
CREATE TABLE lease_contracts (
 id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
 contract_num VARCHAR(50) NOT NULL,
 start_date DATE NOT NULL,
 end_date DATE NOT NULL,
 deposit_amount NUMERIC(10, 2) NOT NULL,
 monthly_rate NUMERIC(10, 2) NOT NULL,
 CONSTRAINT chk_lease_dates CHECK (end_date > start_date),
 CONSTRAINT chk_lease_deposit CHECK (deposit_amount >= monthly_rate));

2.3. Добавление и валидация ограничений на существующей таблице

В высоконагруженных промышленных базах данных создание ограничения CHECK на миллионных таблицах блокирует запись. Для безопасного добавления применяется двухфазный подход:

-- Фаза 1: добавление ограничения без сканирования существующих данных (мгновенно):
ALTER TABLE lease_contracts
ADD CONSTRAINT chk_lease_rate CHECK (monthly_rate > 0) NOT VALID;

-- Фаза 2: валидация существующих строк без эксклюзивной блокировки записи:
ALTER TABLE lease_contracts VALIDATE CONSTRAINT chk_lease_rate;

3. Списки дискретных допустимых значений (Оператор IN)

Если бизнес-логика требует ограничения атрибута конечным набором состояний (статусная модель, категории, валюты), применяется оператор IN:

CREATE TABLE orders (
 id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
 customer_id BIGINT NOT NULL,
 order_status VARCHAR(20) NOT NULL,
 currency VARCHAR(3) NOT NULL,
 CONSTRAINT chk_order_status CHECK (order_status IN ('NEW', 'PAID', 'SHIPPED', 'CANCELLED')),
 CONSTRAINT chk_order_currency CHECK (currency IN ('RUB', 'USD', 'EUR', 'CNY')));
CHECK (status IN (...)) или CREATE TYPE... AS ENUM?
Перечисления ENUM создаются в системном каталоге базы данных. Добавление нового значения в ENUM в PostgreSQL возможно, но удаление или изменение порядка значений крайне затруднительно. Ограничение CHECK (status IN (...)) значительно гибче в сопровождении: его можно изменить простой командой ALTER TABLE.

4. Валидация строковых форматов с помощью регулярных выражений (POSIX RegEx)

PostgreSQL предоставляет мощный аппарат сопоставления строк с регулярными выражениями:

Оператор Назначение Пример использования
~ Соответствие шаблону (с учётом регистра) code ~ '^[A-Z]{3}-[0-9]{4}$'
~* Соответствие шаблону (без учёта регистра) email ~* '^[a-z0-9._]+@[a-z0-9.-]+\.[a-z]{2,}$'
!~ Не соответствует шаблону (с учётом регистра) login !~ '[^a-zA-Z0-9_]'
!~* Не соответствует шаблону (без учёта регистра) note !~* '(запрещено|ошибка)'

Правила составления шаблонов валидации:

  1. Якоря начала ^ и конца $: обязательны! Без них шаблон [0-9]{3} совпадет со строкой "АБВ123ГДЕ", так как ищет подстроку в любом месте.
  2. СНИЛС (11 цифр с разделителями): ^[0-9]{3}-[0-9]{3}-[0-9]{3} [0-9]{2}$
  3. Номер телефона РФ: ^\+7[0-9]{10}$
  4. Email: ^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$

5. Трёхзначная логика SQL и поведение NULL в ограничениях CHECK

Один из самых коварных нюансов SQL — трёхзначная логика истинности (Three-Valued Logic, 3VL): логическое выражение может принимать значения TRUE, FALSE или UNKNOWN.

Фундаментальное правило работы CHECK:
Ограничение CHECK отклоняет строку (генерирует ошибку) ТОЛЬКО ТОГДА, когда выражение вычисляется в строгое FALSE. Если выражение вернуло UNKNOWN (что происходит при сравнении с NULL), строка СЧИТАЕТСЯ КОРРЕКТНОЙ и успешно записывается в таблицу! 
-- Пример неожиданного поведения:
CREATE TABLE students (
 id BIGINT PRIMARY KEY,
 name VARCHAR(100) NOT NULL,
 age INT CHECK (age >= 18) -- Заметьте: нет NOT NULL!);

-- Этот запрос УСПЕШНО выполнится!
-- Потому что (NULL >= 18) -> UNKNOWN. А UNKNOWN не равно FALSE!
INSERT INTO students (id, name, age) VALUES (1, 'Иван', NULL);

Инженерное правило: если значение обязано существовать и удовлетворять диапазону, столбец обязан иметь директиву NOT NULL наряду с CHECK: age INT NOT NULL CHECK (age >= 18).

6. Обработка системных исключений целостности данных

При попытке вставки или обновления строки, нарушающей предикат CHECK, ядро СУБД возвращает ошибку:

  • Код исключения (SQLSTATE): 23514;
  • Имя класса ошибки: check_violation;
  • Сообщение: ERROR: new row for relation "..." violates check constraint "...".

Пример безопасного перехвата в процедурном коде (PL/pgSQL):

CREATE OR REPLACE FUNCTION register_employee(p_name TEXT, p_salary NUMERIC) 
RETURNS VOID AS $$
BEGIN
 INSERT INTO employees (full_name, salary) VALUES (p_name, p_salary);
EXCEPTION
 WHEN check_violation THEN
 RAISE EXCEPTION 'Бизнес-ошибка: размер оклада % руб. не удовлетворяет нормативам!', p_salary;
END;
$$ LANGUAGE plpgsql;

7. Вопросы и задания для самопроверки

1. В чем синтаксическое различие между ограничением CHECK на уровне столбца и на уровне таблицы?

Ответ: Ограничение на уровне столбца может проверять только значение самого этого столбца. Ограничение на уровне таблицы может связывать логическим условием несколько различных столбцов одной строки (например, end_date > start_date).

2. Почему предикат CHECK (discount < total) пропустит запись, если значение discount равно NULL?

Ответ: В стандарте SQL любая операция сравнения с NULL возвращает значение UNKNOWN. Ограничение CHECK генерирует ошибку только при строгом FALSE. Чтобы запретить такое поведение, для поля discount необходимо явно указать NOT NULL либо дополнить условие: CHECK (discount IS NOT NULL AND discount < total).

3. Какую роль выполняют метасимволы ^ и $ в регулярных выражениях валидации полей?

Ответ: Метасимвол ^ привязывает шаблон к началу строки, а $ — к ее концу. Без них регулярное выражение ищет подстроку в любом месте текста, что позволяет пользователю ввести мусорные символы до и после валидного фрагмента.

4. Какой стандартный пятисимвольный код ошибки SQLSTATE возвращает PostgreSQL при нарушении CHECK?

Ответ: Код ошибки 23514 (класс 23 — нарушение ограничений целостности, подкласс 514 — check_violation).
