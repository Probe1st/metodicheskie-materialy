1. Методическая концепция и целеполагание

Ограничения целостности на уровне значений полей (доменная целостность, Domain Integrity) являются фундаментальным защитным барьером реляционной базы данных. В производственных информационных системах бизнес-правила часто нарушаются из-за ошибок фронтенд-валидации, прямого доступа к API, пакетного импорта сторонних данных или несанкционированных скриптов обновления.

Педагогическая цель занятия: сформировать у будущих техников-программистов устойчивый навык строгого декларативного проектирования ограничений значений полей средствами языка SQL (предикаты CHECK, списки IN, регулярные выражения POSIX ~ и ~*), понимание трёхзначной логики SQL при валидации NULL, а также выработать методологию составления исчерпывающего протокола негативного тестирования недопустимого ввода с фиксацией системного исключения check_violation (код ошибки SQLSTATE 23514).

Ключевой профессиональный тезис: «База данных — последний и единственный неподкупный рубеж защиты целостности данных. Клиентскую валидацию можно обойти через Postman или отключение скриптов, но ограничение CHECK в СУБД делает сохранение мусорных данных физически невозможным».

3. Архитектурная реализация бизнес-ограничений в SQL

3.1. Доменные предикаты CHECK на уровне столбца и таблицы

Ограничение CHECK требует, чтобы предикат истинности возвращал TRUE или UNKNOWN (при наличии NULL) для каждой вставляемой или обновляемой строки. Если предикат вычисляется в FALSE, СУБД немедленно откатывает оператор и генерирует исключение.

Критическое правило синтаксиса:
  • Ограничение на уровне столбца (Column Constraint): может ссылаться только на текущий столбец (например, salary NUMERIC(10,2) CHECK (salary >= 19242)).
  • Ограничение на уровне таблицы (Table Constraint): обязательно при валидации взаимосвязи двух и более полей (например, CONSTRAINT chk_dates CHECK (end_date > start_date)).

3.2. Списки допустимых дискретных значений через оператор IN

Для статусов заказов, договоров, валют и категорий применяется оператор вхождения в кортеж литералов:

CONSTRAINT chk_order_status CHECK (status IN ('DRAFT', 'ACTIVE', 'PENDING', 'CLOSED', 'CANCELLED'))

Преподавателю следует подчеркнуть: использование CHECK (status IN (...)) является легковесной и переносимой альтернативой созданию пользовательского перечислимого типа CREATE TYPE ... AS ENUM, так как не требует сложных миграций при добавлении новых вариантов.

3.3. Валидация форматов строк через регулярные выражения POSIX

В современных реляционных СУБД (PostgreSQL, SQLite с расширениями) поддерживаются операторы сопоставления с регулярными выражениями:

  • ~ — регистрозависимое соответствие шаблону;
  • ~* — регистронезависимое соответствие шаблону;
  • !~ и !~* — отрицание соответствия.

Пример эталонной проверки email-адреса:

CONSTRAINT chk_user_email CHECK (
    email ~* '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$'
)

Пример проверки номера СНИЛС (формат: 3 цифры, дефис, 3 цифры, дефис, 3 цифры, пробел, 2 цифры):

CONSTRAINT chk_user_snils CHECK (
    snils ~ '^[0-9]{3}-[0-9]{3}-[0-9]{3} [0-9]{2}$'
)

4. Сопоставление клиентской валидации и СУБД-ограничений

Важнейший педагогический элемент занятия — преодолеть заблуждение студентов о том, что валидации на HTML5/JavaScript «достаточно» для надежной работы приложения.

Критерий сравнения Клиентская валидация (HTML5 / JS / React) СУБД-ограничения (CHECK / UNIQUE / FK)
Главная цель Мгновенная обратная связь пользователю (User Experience, UX), предотвращение лишнего сетевого трафика. Гарантированное обеспечение целостности и непротиворечивости реляционного хранилища.
Уязвимость к обходу Легко обходится: отключение JS, прямые запросы через cURL/Postman, мобильные клиенты других версий. Обойти невозможно: ни один запрос INSERT или UPDATE не пройдет мимо ядра СУБД.
Область действия Только конкретная экранная форма пользовательского интерфейса. Все источники данных: веб-приложения, фоновые очереди, консоль администратора, ETL-скрипты.
Вывод для инженера Необходима для удобства человека. Обязательна для выживания и финансово-юридической чистоты системы.

5. Перехват исключений check_violation (код 23514) и протокол тестирования

При нарушении условия CHECK ядро PostgreSQL прерывает выполнение запроса и генерирует стандартную ошибку:

ERROR: new row for relation "employees" violates check constraint "chk_employees_salary"
DETAIL: Failing row contains (10, Петров Иван, 1990-01-01, 35, 12000.00, 123-456-789 00).
SQLSTATE: 23514 (check_violation)

В прикладных серверных приложениях (Node.js/pg, Python/psycopg2, Java/JDBC, C#/Npgsql) разработчик перехватывает именно класс ошибки 23514 для формирования понятного бизнес-сообщения:

-- Демонстрация в блоке PL/pgSQL
DO $$
BEGIN
    INSERT INTO employees (full_name, age, salary, snils)
    VALUES ('Иванов', 15, 25000, '123-456-789 00');
EXCEPTION
    WHEN check_violation THEN
        RAISE NOTICE 'Перехвачена ошибка целостности! Код SQLSTATE: %', SQLSTATE;
END $$;

Методика составления протокола тестирования недопустимого ввода

Каждый студент в рамках своего варианта обязан составить тестовую матрицу, содержащую 4 категории проверок:

  1. Тест выхода за нижнюю границу: отрицательное число, возраст < 18, сумма 0 при строгом > 0.
  2. Тест выхода за верхнюю границу: процент > 100%, возраст > 70 лет, оценка > 5.
  3. Тест нарушения формата (RegEx / IN): некорректная структура СНИЛС, недопустимый статус.
  4. Граничный позитивный тест: точное попадание в минимально и максимально разрешенные значения (например, оклад ровно 19 242.00 руб., оценка ровно 2 или 5).

6. Типовые ошибки обучающихся и педагогические приемы

Типовая ошибка студента Причина и механизм проявления Педагогический прием устранения
Безымянные ограничения CHECK Студент пишет salary NUMERIC CHECK (salary >= 19242). СУБД дает имя employees_salary_check, что затрудняет отладку логов. Требовать строгое использование именованных ограничений: CONSTRAINT chk_имятаблицы_имяполя.
Ловушка трёхзначной логики (NULL) Студент ожидает, что CHECK (age >= 18) запретит значение NULL. В SQL условие NULL >= 18 возвращает UNKNOWN, а ограничение пропускает строку! Наглядно продемонстрировать вставку NULL в колонку без NOT NULL. Закрепить правило: «CHECK защищает от FALSE, а от NULL защищает NOT NULL».
Отсутствие символов якорей в RegEx Шаблон snils ~ '[0-9]{3}...' без ^ и $. В итоге строка с посторонними буквами в начале и конце успешно проходит валидацию. Показать на интерактивной доске разницу между поиском подстроки и строгой валидацией всей длины строки через символы ^ (начало) и $ (конец).
Межколоночное условие на уровне столбца Попытка написать end_date DATE CHECK (end_date > start_date) внутри объявления одного столбца приводит к синтаксической ошибке. Объяснить границу видимости: определение столбца «видит» только себя. Межколоночные связи пишутся только в конце таблицы через CONSTRAINT.

7. Организация оценивания по 4-балльной шкале

Оценивание результатов практического занятия производится строго на основании критериев закрытой рубрики (.rubrika.md):

  • 2 балла — Проектирование ограничений CHECK: DDL-код без ошибок, именование chk_*, верные предикаты, корректное использование IN и регулярных выражений;
  • 1 балл — Протокол негативного тестирования: оформление тестовых запросов INSERT/UPDATE с выходом за границы и искажением форматов, фиксация ошибки check_violation (23514);
  • 1 балл — Выводы и самопроверка: аргументированное объяснение взаимодействия клиентского интерфейса и базы данных, трёхзначной логики и роли ограничений целостности.

Итоговая оценка выставляется по сумме баллов: 4 б. — «Отлично», 3 б. — «Хорошо», 2 б. — «Удовлетворительно», 0–1 б. — «Не зачтено».
