| Критерий | 0 баллов | 1 балл | 2 балла |
| :--- | :--- | :--- | :--- |

#### Перевод баллов в академическую оценку:
- **4 балла:** Оценка «5» (отлично) — исчерпывающее понимание архитектуры ANSI/SPARC, безошибочный выбор защитных механизмов.
- **3 балла:** Оценка «4» (хорошо) — верное различение типов независимости, незначительные неточности в SQL-синтаксисе или деталях триггеров.
- **2 балла:** Оценка «3» (удовлетворительно) — базовое понимание концепции, но спутаны детали B-Tree/Hash или не раскрыт механизм VIEW.

### 3. Эталонные решения практических заданий (`zanyatie.html`)

#### Вариант 1: Декомпозиция таблицы Клиенты на ЮрЛица и ФизЛица
1. **Классификация (Критерий 1):**
   - Тип независимости: **Логическая независимость данных (Logical Data Independence)**.
   - Граница ANSI/SPARC: между **Внешним уровнем** (External Level — старая бухгалтерская программа) и **Концептуальным уровнем** (Conceptual Level — разделенные таблицы `Legal_Entities` и `Individuals`).
2. **Механизм реализации через VIEW (Критерий 2):**
   ```sql
   CREATE OR REPLACE VIEW Clients AS
   SELECT client_id, company_name AS name, inn, NULL AS passport, kpp
   FROM Legal_Entities
   UNION ALL
   SELECT client_id, full_name AS name, inn, passport_data AS passport, NULL AS kpp
   FROM Individuals;
   ```
3. **Обработка операций записи (INSTEAD OF):**
   - Прямой `INSERT INTO Clients` завершится ошибкой, так как сложные представления с `UNION ALL` необновляемы по умолчанию.
   - Требуется триггер `INSTEAD OF INSERT ON Clients`, который анализирует передаваемые поля (например, наличие КПП или типа лица) и маршрутизирует вставку: в `Legal_Entities`, если указан КПП/ОГРН, либо в `Individuals`, если указаны паспортные данные.
4. **Вывод и самопроверка (Критерий 3):**
   - Код старой программы сохраняет работоспособность, так как структура кортежей, возвращаемых представлением `Clients`, полностью соответствует исходной сигнатуре полей.
   - Граница применимости: независимость будет нарушена, если из обеих таблиц полностью удалят обязательный реквизит (например, `inn`), необходимый старой программе, без возможности его программного вычисления.

#### Вариант 2: Перенос архива заказов на медленный HDD-массив и секционирование
1. **Классификация (Критерий 1):**
   - Тип независимости: **Физическая независимость данных (Physical Data Independence)**.
   - Граница ANSI/SPARC: между **Концептуальным уровнем** (Conceptual Level — сущность `Orders`) и **Внутренним/Физическим уровнем** (Internal Level — файлы дисковых разделов, Tablespaces).
2. **Механизм секционирования (Partitioning):**
   - Механизм *Partition Pruning* (отсечение партиций): планировщик СУБД анализирует условие фильтрации `WHERE order_date = '2022-04-12'` и обращается только к соответствующему дисковому файлу секции `orders_2022`, не сканируя терабайты остальных лет.
   - Прикладной программист **не должен** менять имя таблицы: в SQL-запросе пишется родительская мастер-таблица `Orders`, а диспетчеризацию выполняет ядро СУБД.
3. **Роль Tablespaces:**
   - Табличные пространства (Tablespaces) позволяют сопоставить логические объекты СУБД с конкретными физическими путями в файловой системе ОС. Это обеспечивает многоуровневое хранение (Tiered Storage): горячие оперативные данные — на быстрых NVMe SSD, холодный архив — на недорогих HDD массивах (RAID-6).
4. **Вывод и самопроверка (Критерий 3):**
   - Запрос `SELECT * FROM Orders WHERE order_date = ...` выполняется идентично, так как логическая схема таблицы, имена колонок и типы данных не изменились. Физическое перемещение байтов прозрачно изолировано ядром СУБД.

#### Вариант 3: Оптимизация поиска по миллиону записей (B-Tree vs Hash, EXPLAIN)
1. **Классификация (Критерий 1):**
   - Тип независимости: **Физическая независимость данных (Physical Data Independence)**.
   - Создание индекса не изменяет концептуальную схему: набор колонок, типы данных, ограничения целостности и логические кортежи таблицы `Products` остаются абсолютно прежними.
2. **Выбор типа индекса: B-Tree vs Hash:**
   - Для запроса с фильтром `category_id = 42 AND price BETWEEN 1000 AND 5000` оптимален **составной B-Tree индекс**: `CREATE INDEX idx_products_cat_price ON Products USING btree(category_id, price);`.
   - **Hash-индекс категорически не подходит**, так как хэш-таблица предназначена исключительно для точечных проверок на точное равенство (`=`). Хэш-функция разрушает упорядоченность значений, поэтому операторы сравнения (`<`, `>`, `<=`, `>=`, `BETWEEN`) не могут использовать хэш-индекс.
3. **Анализ плана EXPLAIN:**
   - До создания индекса: `Seq Scan on products (cost=0.00..38491.00 rows=150 width=84)` — последовательное считывание всех страниц таблицы с диска (высокая стоимость ввода-вывода).
   - После создания индекса: `Bitmap Index Scan on idx_products_cat_price` / `Index Scan` — прямое позиционирование по B-дереву и чтение только релевантных страниц. Время падает с 2500 мс до 1–2 мс.
4. **Вывод и самопроверка (Критерий 3):**
   - Разработчику микросервиса каталога не требуется модифицировать SQL-запрос, так как оптимизатор СУБД (Cost-Based Optimizer) автоматически выбирает наиболее эффективный план доступа на основе актуальной статистики распределения данных.

#### Вариант 4: Добавление поля «Статус_лояльности» и экранирование касс
1. **Классификация (Критерий 1):**
   - Добавление атрибута в таблицу — это изменение **Концептуального уровня** (Conceptual Level).
   - Произошло нарушение **Логической независимости данных** для кассовых терминалов, ориентированных на фиксированный кортеж колонок.
2. **Экранирование через VIEW:**
   ```sql
   CREATE OR REPLACE VIEW v_pos_customers AS
   SELECT customer_id, card_code, full_name, discount_percent, phone
   FROM Customers;
   ```
   В представлении `v_pos_customers` явно перечисляются только те столбцы, которые поддерживаются протоколом кассовых аппаратов, исключая новое поле `loyalty_tier`.
3. **Разграничение прав доступа (GRANT/REVOKE):**
   ```sql
   -- Запрещаем кассовым аппаратам прямой доступ к базовой таблице:
   REVOKE ALL ON TABLE Customers FROM role_cashier;
   
   -- Разрешаем чтение только экранирующего представления:
   GRANT SELECT ON v_pos_customers TO role_cashier;
   ```
4. **Вывод и самопроверка (Критерий 3):**
   - Прямой доступ к таблицам со стороны десятков внешних систем создает жесткую связность (tight coupling). Использование слоя представлений (VIEW) создает интерфейсный изолирующий слой (API базы данных), позволяющий развивать структуру хранилища без риска остановки торговых операций.

### 4. Типичные ошибки обучающихся и методы их устранения

1. **Ошибочное отнесение индексов к логической схеме:**
   - *Проявление:* Студент утверждает, что раз команда `CREATE INDEX` пишется в SQL-консоли, это «логическое изменение базы».
   - *Методический прием:* Задать вопрос: «Вернет ли запрос `SELECT * FROM Products` новую колонку после создания индекса? Изменится ли бизнес-смысл сущности "Товар"? Нет. Следовательно, это оптимизация физического доступа, то есть физический уровень».
2. **Игнорирование триггеров INSTEAD OF при обновлении VIEW:**
   - *Проявление:* Студент считает, что создания `CREATE VIEW ... UNION ALL` достаточно для полноценной замены таблицы, забывая про операции `INSERT/UPDATE/DELETE`.
   - *Методический прием:* Напомнить студентам правила реляционной теории: СУБД не может однозначно определить, в какую именно из двух таблиц объединения поместить новую запись, если не задан явный алгоритмический триггер `INSTEAD OF`.
3. **Представление о физическом дублировании строк во VIEW:**
   - *Проявление:* Опасения, что создание представлений удвоит объем занятой дисковой памяти.
   - *Методический прием:* Подчеркнуть, что стандартное VIEW не содержит данных — это «трафарет» (сохраненный SQL-запрос), который компилируется в единое дерево запроса вместе с клиентским кодом в момент вызова.
