1. Дидактическая концепция и целеполагание

Занятие №24 посвящено важнейшему аспекту архитектуры современных корпоративных информационных систем: проектированию надежных интерфейсов взаимодействия с пользователем и эшелонированной системы контроля входных данных. В классических реляционных архитектурах интерфейс пользователя (Frontend) и ядро хранения данных (Backend / СУБД) образуют единый контур защиты, в котором ни один уровень не имеет права слепо доверять другому.

Ключевая дидактическая цель: сформировать у обучающихся устойчивое инженерное понимание концепции «эшелонированной обороны» (Defense in Depth) данных, освоить распределение обязанностей между клиентской валидацией (UX, регулярные выражения, мгновенная обратная связь, блокировка отправки) и серверным контролем СУБД (декларативные ограничения CHECK, уникальные индексы, триггеры BEFORE INSERT/UPDATE, транзакционная изоляция), а также научиться профессионально перехватывать системные исключения СУБД (коды SQLSTATE) и транслировать их в понятные человеку экранные уведомления, исключая уязвимости внедрения SQL-кода.

Дидактические задачи:

  • Обучающие: систематизировать знания о двухуровневой модели валидации; разобрать синтаксис регулярных выражений для валидации экранных форм (ИНН, ОГРН, email, телефон, маски ввода); изучить механизм работы параметризованных запросов (Prepared Statements) как абсолютной защиты от SQL Injection; освоить классификацию кодов ошибок стандарта SQLSTATE (класс 23 — нарушение целостности, класс 40 — сбои транзакций); изучить синтаксис серверных триггеров бизнес-логики BEFORE INSERT OR UPDATE.
  • Развивающие: развить навыки проектирования пользовательских интерфейсов с мгновенным откликом (UX feedback loop); сформировать аналитическое мышление при обработке конкурентных транзакций (Race Conditions, повторное бронирование, овербукинг); привить культуру безопасной разработки ПО (Secure Software Development).
  • Воспитательные: воспитать профессиональную ответственность за сохранность и непротиворечивость корпоративных баз данных; сформировать нетерпимость к «наивному программированию» (упованию только на клиентские проверки или конкатенацию SQL-строк).

3. Архитектура организации интерфейса и эшелонированного контроля

Центральный теоретический посыл занятия: клиентская валидация предназначена для удобства пользователя (User Experience), а серверная валидация — для обеспечения физической выживаемости и целостности базы данных (Data Integrity).

3.1. Клиентский уровень (Frontend Validation)

Клиентский уровень выполняется в среде браузера или мобильного приложения на стороне пользователя. Его задачи:

  • Мгновенная обратная связь (Instant Feedback): подсветка полей в реальном времени при событиях input и blur (зеленая рамка при успехе, красная с текстом ошибки при нарушении формата).
  • Предотвращение холостых сетевых запросов: блокировка кнопки отправки (disabled) до тех пор, пока все обязательные поля не удовлетворят регулярным выражениям и контрольным суммам.
  • Форматирование и маски ввода: автоматическая расстановка пробелов, дефисов и скобок (например, телефон +7 (999) 000-00-00 или ОГРН из 13 цифр).
Важнейшее правило безопасности: Frontend полностью подконтролен потенциальному злоумышленнику. Любой скрипт JS может быть отключен в браузере, поле формы может быть отредактировано через DevTools, а HTTP-запрос отправлен напрямую через утилиты curl/Postman. Следовательно, клиентская валидация никогда не является барьером безопасности!

3.2. Серверный уровень (Backend & СУБД Validation)

Серверный уровень состоит из API-шлюза (бэкенда) и ядра СУБД:

  • Параметризованные запросы (Prepared Statements): разделение тела SQL-команды и пользовательских данных на уровне протокола СУБД. Предотвращает интерпретацию пользовательских символов как команд SQL.
  • Декларативные ограничения таблицы: CHECK (проверка диапазонов, булевых условий и POSIX-регулярок через ~), NOT NULL, UNIQUE, FOREIGN KEY, EXCLUDE USING gist.
  • Серверные триггеры бизнес-логики: функции BEFORE INSERT OR UPDATE FOR EACH ROW, способные проверить остатки на складе, вычислить сложный баланс или отменить операцию с помощью RAISE EXCEPTION.
  • Транзакционная изоляция: уровни READ COMMITTED, REPEATABLE READ и SERIALIZABLE, а также селекты с блокировкой SELECT ... FOR UPDATE для предотвращения состояния гонки (Race Condition).

3.3. Стандартизация кодов ошибок SQLSTATE и Error Mapping

При нарушении любого правила целостности ядро СУБД генерирует исключение, содержащее стандартный пятисимвольный код SQLSTATE (ISO/IEC 9075):

Код SQLSTATE Имя константы в PostgreSQL Причина возникновения в ядре СУБД Пользовательское сообщение (UX Error Mapping)
23505 unique_violation Попытка вставки дублирующегося значения в поле с ограничением PRIMARY KEY или UNIQUE. «Запись с такими данными уже существует в системе. Проверьте уникальные идентификаторы.»
23514 check_violation Значение строки не удовлетворило булеву предикату ограничения CHECK. «Введенное значение не соответствует допустимому формату или диапазону бизнес-правил.»
23503 foreign_key_violation Ссылка на несуществующую родительскую запись или попытка удаления связанной сущности. «Указанный связанный объект не найден в справочнике системы либо используется другими данными.»
23P01 exclusion_violation Нарушение ограничения исключения EXCLUDE (например, пересечение временных интервалов брони). «Выбранный номер/ресурс уже занят на указанные даты. Пожалуйста, выберите другой интервал.»
40001 serialization_failure Конфликт параллельных транзакций при уровне изоляции SERIALIZABLE / REPEATABLE READ. «Операция временно недоступна из-за параллельного изменения данных. Повторите попытку через пару секунд.»
P0001 raise_exception Пользовательское исключение, выброшенное серверным PL/pgSQL триггером (например, нет товара на складе). Текст ошибки из триггера (например: «Недостаточно товара на складе для оформления заказа»).
Антипаттерн «Сырая ошибка СУБД»: Категорически запрещено выводить пользователю сырой стек-трейс или технический текст СУБД (например: ERROR: duplicate key value violates unique constraint "clients_inn_key"). Это грубейшее нарушение информационной безопасности (раскрытие схемы БД и имен таблиц злоумышленнику) и провал интерфейсной эргономики.

4. Защита от SQL-инъекций через параметризованные запросы

Одной из ключевых тем занятия является демонстрация студентам принципа параметризации. В небрежно спроектированных интерфейсах пользовательский ввод конкатенируется прямо в SQL-строку: 

// КАТАСТРОФИЧЕСКИЙ АНТИПАТТЕРН (Уязвимость SQL Injection):
String sql = "SELECT * FROM users WHERE login = '" + userLogin + "' AND pass = '" + userPass + "'";
// Если userLogin = "admin' --", весь парольный фильтр отсекается комментарием!

Преподаватель объясняет фундаментальный механизм Prepared Statement:

  1. Фаза компиляции (PREPARE): СУБД выполняет синтаксический анализ SQL-шаблона с плейсхолдерами (1, 2 или ?), строит дерево синтаксического разбора (AST) и фиксирует план выполнения. На этом этапе структура запроса запечатывается навсегда.
  2. Фаза подстановки значений (EXECUTE): параметры передаются по бинарному протоколу отдельно от команды. СУБД воспринимает переданные байты строго как литеральные данные. Любые кавычки, точки с запятой или ключевые слова SQL внутри параметра физически не могут изменить структуру дерева AST.
// ПРОМЫШЛЕННЫЙ ЭТАЛОН (Параметризованный запрос):
PreparedStatement ps = conn.prepareStatement("SELECT id, role FROM users WHERE login = 1 AND passhash =2");
ps.setString(1, userLogin);
ps.setString(2, hashedPass);
ResultSet rs = ps.executeQuery();

5. Типовые ошибки студентов и методы их предупреждения

Типовая ошибка студента В чем проявляется дефект Педагогический прием и метод устранения
«Иллюзия клиентской защиты» Студент пишет сложную валидацию на JavaScript и считает, что базу данных защищать ограничениями больше не нужно. На глазах у группы преподаватель открывает терминал и с помощью команды curl -X POST ... отправляет на бэкенд невалидные данные в обход браузера, вызывая сбой БД.
«Сырой вывод SQL-ошибок» Студент выводит в alert() или текстовый блок браузера системное сообщение e.getMessage() от JDBC/PostgreSQL. Преподаватель объясняет риски Information Disclosure (утечка имен колонок, типов, индексов) и демонстрирует архитектурный паттерн Error Mapper Dictionary.
«Неверная обработка Race Condition» Студент проверяет наличие записи обычным SELECT, а затем делает INSERT, не учитывая параллельных пользователей. Разбор классической проблемы Time-of-check to time-of-use (TOCTOU). Демонстрация уникальных индексов, ограничений EXCLUDE и блокировок SELECT FOR UPDATE.
«Забытые якоря в регулярных выражениях» Вместо строгого шаблона ^\d{10}$ студент пишет \d{10}, пропуская строки типа буквы1234567890хвост. Разбор символов начала строки (^) и конца строки ($). Тестирование строк с мусорными символами по краям.

6. Критерии оценивания практической деятельности (4-балльная шкала)

В соответствии с учебным планом СИЭУиП занятие оценивается по 4-балльной шкале:

  • Часть 1. Сценарии клиентской валидации и UX-контроль (2 балла): корректное составление регулярных выражений с якорями ^ и $, математическая проверка контрольных разрядов (для ИНН), логика мгновенной подсветки полей и превентивная блокировка кнопки Submit при некорректных данных.
  • Часть 2. Обработка серверных ошибок и SQLSTATE-маппинг (1 балл): верное определение системного кода SQLSTATE (23505, 23514, 23P01, P0001, 40001), проектирование понятного и безопасного текста уведомления для пользователя без утечки технической информации СУБД.
  • Часть 3. Защита от инъекций и архитектурная самопроверка (1 балл): глубокое обоснование принципа работы Prepared Statements, анализ рисков Race Condition и решение контрольных вопросов.
