Этап 2. Теоретический базис: строки подключения, пул соединений и SSL

Хронометраж: 80 минут — 15 минут | 60 минут — 12 минут
Преподаватель: «Внимание на экран проектора. Давайте разберем, что происходит на физическом уровне, когда клиентская программа пытается отправить запрос в PostgreSQL. Посмотрим на слайд 5 презентации.

Сначала операционная система выполняет тройное рукопожатие TCP: SYN, SYN-ACK, ACK. На это уходит 10–30 миллисекунд. Затем, если мы заботимся о безопасности, инициируется шифрование канала TLS — обмен сертификатами и ключами Диффи-Хеллмана. Это еще 30–70 миллисекунд. Далее следует аутентификация в СУБД по алгоритму SCRAM-SHA-256. И только после выделения отдельного серверного процесса postgres backend база готова исполнить запрос. Суммарно на каждое новое подключение тратится до 200 миллисекунд!

Какое инженерное решение устраняет эту проблему? Вопрос аудитории: как не повторять этот долгий процесс на каждый чих пользователя?»
Студент (Иванов): «Использовать пул соединений! Мы заранее открываем несколько соединений, держим их готовыми в оперативной памяти, а когда приходит запрос — берем готовое соединение на пару миллисекунд и потом возвращаем обратно в пул, не закрывая сокет».
Преподаватель: «Абсолютно верно! Пул соединений — это программный менеджер кэшированных сокетов. Время получения соединения из пула составляет меньше половины миллисекунды. Но здесь есть ключевые параметры, которые вы обязаны уметь рассчитывать:
  • min_connections — базовое количество постоянно прогретых сокетов;
  • max_connections — максимальный лимит соединений, выше которого потоки будут вставать в очередь, предотвращая перегрузку СУБД;
  • idle_timeout — время, по истечении которого лишние простаивающие соединения будут закрыты.
И помните золотое правило методологии 12-Factor App: никаких логинов и паролей внутри файлов исходного кода! Все параметры мы выносим во внешние конфигурационные файлы: config.json, config.yaml или в переменные окружения .env».

Этап 3. Сквозная живая демонстрация (Live Coding)

Хронометраж: 80 минут — 10 минут | 60 минут — 7 минут
Преподаватель: «Сейчас я продемонстрирую вам эталонный скрипт первичной инициализации базы данных. Взгляните на экран: 
// 1. Считывание конфигурации из внешнего файла.env
const config = {
 host: process.env.DB_HOST | '127.0.0.1',
 port: parseInt(process.env.DB_PORT) | 5432,
 database: process.env.DB_NAME | 'warehouse_db',
 user: process.env.DB_USER,
 password: process.env.DB_PASSWORD,
 max: 5, // max_pool_size
 idleTimeoutMillis: 300000,
 connectionTimeoutMillis: 5000
};

// 2. Инициализация пула соединений
const pool = new Pool(config);

// 3. Health Check: первичный пинг СУБД запросом SELECT 1
async function testDatabaseConnection() {
 try {
 const client = await pool.connect();
 const result = await client.query('SELECT 1 AS health_check;');
 client.release(); // ОБЯЗАТЕЛЬНО возвращаем сокет в пул!
 console.log('[INFO] Успешное подключение к СУБД. База данных готова к работе.');
 } catch (err) {
 console.error('[ERROR] [DB_CONN] Сбой подключения к базе данных:', err.message);
 // Логируем инцидент и предотвращаем запуск сломанного приложения
 process.exit(1);
 }
}
Обратите внимание на строку client.release(). Если вы забудете вернуть клиент в пул, в вашем приложении возникнет утечка соединений — Connection Leak. Десять запросов — и ваше приложение намертво зависнет, потому что все сокеты останутся занятыми.

Теперь я намеренно останавливаю службу базы данных через терминал: sudo systemctl stop postgresql и перезапускаю наш скрипт. Смотрите: скрипт не упал с "синим экраном" или аварийным завершением. Блок catch перехватил системную ошибку ECONNREFUSED и красиво записал в лог время, код ошибки и рекомендацию проверить службу PostgreSQL. Именно такого поведения я жду от ваших практических работ!»
