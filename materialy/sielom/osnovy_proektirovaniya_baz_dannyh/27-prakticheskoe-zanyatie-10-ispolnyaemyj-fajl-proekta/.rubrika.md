## 1. Критериальная шкала оценивания (4-балльная модель)

Максимальный итоговый балл за практическое занятие — **4 балла**. Оценка в журнал («5», «4», «3», «2») формируется согласно таблице конвертации:

| Набранные баллы | Оценка в журнал | Уровень освоения компетенций |
| :--- | :---: | :--- |
| **4 балла** | **«5» (отлично)** | Продвинутый уровень: все параметры Connection String вынесены в конфигурацию, размер пула обоснован формулой, предотвращены утечки сокетов, реализован Health Check и отказоустойчивое логирование. |
| **3 балла** | **«4» (хорошо)** | Базовый профессиональный уровень: строка подключения и пул настроены верно, первичная проверка связи работает, но допущены мелкие погрешности в логировании или отсутствие проверки таймаута. |
| **2 балла** | **«3» (удовл.)** | Пороговый уровень: строка подключения сформирована, однако параметры пула не обоснованы либо допущен потенциальный Connection Leak при обработке ошибок. |
| **0–1 балл** | **«2» (неудовл.)** | Неудовлетворительный уровень: хардкод паролей в исходном коде, синтаксический сбой в файле конфигурации, отсутствие обработки ошибок подключения к СУБД. |

### Детализация критериев оценивания:

1. **Критерий 1: Параметры Connection String (максимум 2 балла)**
   * **2 балла:** Полный набор спецификации (драйвер, хост, сетевой порт, имя целевой БД, сервисный логин, пароль, параметры SSL/TLS, таймаут соединения). Полное разделение кода и настроек в соответствии с принципами 12-Factor App (файл `.env`, `config.json` или `config.yaml`). Корректный синтаксис структуры данных.
   * **1 балл:** Конфигурационный файл создан, но пропущены критические параметры надежности (отсутствует `connect_timeout` или параметры шифрования SSL), либо допущены негрубые синтаксические погрешности.
   * **0 баллов:** Параметры подключения захардкожены непосредственно в исполняемом коде программы, либо конфигурационный файл не соответствует формату (невалидный JSON/YAML).

2. **Критерий 2: Архитектура пула соединений Connection Pool (максимум 1 балл)**
   * **1 балл:** Обоснован расчет размера пула соединений (учет ядер CPU, характера нагрузки и типа дисковой подсистемы). Корректно заданы параметры `min_connections`, `max_connections`, `idle_timeout` и `connection_timeout`. Представлена архитектурная защита от Connection Leak (гарантированное освобождение сокетов через `finally / using / with`).
   * **0 баллов:** Размеры пула заданы произвольно без инженерного обоснования (например, завышенный пул на 500+ соединений для локальной базы), отсутствует механизм возврата сокета в пул при падении запроса.

3. **Критерий 3: Обработка ошибок связи и самопроверка Health Check (максимум 1 балл)**
   * **1 балл:** Реализована стартовая процедура самодиагностики связности с СУБД запросом `SELECT 1;`. Корректно перехвачены специфические сетевые исключения (`Connection Refused`, `Timeout`), сформирована информативная запись в лог с таймстемпом и уровнем критичности без аварийного падения процесса.
   * **0 баллов:** Проверка связности отсутствует, ошибки подключения приводят к необработанному аварийному падению программы (Unhandled Exception Crash), лог-запись отсутствует.

#### Задание 1.3. Первичное тестирование связи (Ping / SELECT 1) и отлов сбоев
```python
import sys
import logging

logging.basicConfig(filename='warehouse_app.log', level=logging.INFO,
                    format='%(asctime)s [%(levelname)s] %(message)s')

def test_database_health():
    conn = None
    try:
        # Аренда соединения из пула
        conn = db_pool.getconn()
        with conn.cursor() as cur:
            cur.execute("SELECT 1 AS ping_status;")
            row = cur.fetchone()
            if row and row[0] == 1:
                logging.info("Связь с СУБД PostgreSQL успешно установлена (SELECT 1 OK).")
                print("Складская база данных готова к работе.")
                return True
    except psycopg2.OperationalError as ex:
        err_msg = str(ex).strip()
        logging.error(f"Сбой связи с PostgreSQL при инициализации: {err_msg}")
        if "Connection refused" in err_msg or "could not connect to server" in err_msg:
            print("ОШИБКА: Сервер базы данных PostgreSQL не запущен или порт 5432 закрыт.")
        elif "timeout" in err_msg.lower():
            print("ОШИБКА: Превышено время ожидания ответа сервера СУБД.")
        else:
            print(f"ОШИБКА ПОДКЛЮЧЕНИЯ: {err_msg}")
        return False
    finally:
        # Гарантированный возврат сокета в пул даже при возникновении ошибки!
        if conn is not None:
            db_pool.putconn(conn)

if not test_database_health():
    print("Запуск приложения заблокирован до восстановления связи с базой.")
    sys.exit(1)
```

#### Задание 2.2. Защита от атак Man-in-the-Middle и параметры сертификатов
* **Разница между `sslmode=require` и `sslmode=verify-full`:** В режиме `require` трафик шифруется, но драйвер принимает абсолютно любой сертификат, предъявленный удаленной стороной. Злоумышленник в локальной сети поликлиники может выполнить ARP-спуфинг, выпустить самоподписанный сертификат на лету и перехватить трафик в открытом виде (классический MitM). Режим `verify-full` требует строгой проверки цифровой подписи сертификата сервера доверенным Удостоверяющим Центром (`sslrootcert`), а также строгого совпадения доменного имени `remote-db.med.local` с полем Common Name (CN) или Subject Alternative Name (SAN) в сертификате.
* **Последствия для клиники:** Утечка персональных данных пациентов (ФИО, диагнозы, паспортные данные, номера полисов ОМС), нарушение Федерального закона №152-ФЗ «О персональных данных», штрафы регуляторов и отзыв лицензии медицинской организации.

#### Задание 2.3. Обработка ошибки таймаута связи при падении сервера СУБД
```csharp
using System;
using System.IO;
using Npgsql;

public class MedicalDatabaseClient
{
    private static readonly string LogFile = "/var/log/med_registry/db_events.log";

    public static bool InitializeConnection(string connString)
    {
        try
        {
            using (var conn = new NpgsqlConnection(connString))
            {
                conn.Open();
                using (var cmd = new NpgsqlCommand("SELECT 1;", conn))
                {
                    cmd.CommandTimeout = 3;
                    cmd.ExecuteScalar();
                }
            }
            LogEvent("INFO", "Защищенное SSL-подключение к медицинской БД успешно установлено.");
            return true;
        }
        catch (NpgsqlException ex) when (ex.InnerException is System.TimeoutException || ex.Message.Contains("Timeout"))
        {
            LogEvent("CRITICAL", $"Таймаут подключения к серверу СУБД remote-db.med.local: {ex.Message}");
            // Дружественный вывод для медрегистратора без технических пугающих дампов:
            ShowUserAlert("Внимание: сервер медицинской базы данных временно недоступен. Проверьте подключение к защищенной сети больницы или обратитесь в службу технической поддержки (доб. 102).");
            return false;
        }
        catch (Exception ex)
        {
            LogEvent("ERROR", $"Непредвиденный сбой связи: {ex.Message}");
            ShowUserAlert("Ошибка инициализации рабочего места. Повторите попытку через минуту.");
            return false;
        }
    }

    private static void LogEvent(string level, string message)
    {
        string record = $"[{DateTime.UtcNow:yyyy-MM-dd HH:mm:ss UTC}] [{level}] [DB_SSL_CLIENT] {message}";
        File.AppendAllText(LogFile, record + Environment.NewLine);
    }

    private static void ShowUserAlert(string msg) => Console.WriteLine(msg);
}

```
* **Обоснование параметров:**
  * `maximumPoolSize=10` — строгий лимит для исключения лавинообразной перегрузки центрального сервера процессинга тысячами банкоматов.
  * `minimumIdle=2` — сокеты всегда открыты, операция внесения/выдачи наличных начинается мгновенно без задержки на Handshake.
  * `idleTimeout=300000` (5 мин) — закрытие временных соединений после пиковых часов активности.
  * `connectionTimeout=3000` (3 с) — быстрый отказ (Fail-Fast) при невозможности получить коннект, предотвращающий «зависание» клиента у экрана банкомата.
  * `maxLifetime=1800000` (30 мин) — предотвращение утечек памяти на стороне СУБД и обновление сокетов.
  * `leakDetectionThreshold=2000` (2 с) — автоматическая тревога в логи при удержании сокета потоком дольше 2 секунд.

#### Задание 3.2. Предотвращение критической аварии Connection Leak
* **Код с гарантированным освобождением:**
```java
// Использование конструкции try-with-resources гарантирует вызов close() и возврат в пул
public boolean processCardWithdrawal(String cardHash, BigDecimal amount) {
    String sql = "SELECT * FROM process_atm_withdrawal(?, ?);";
    try (Connection conn = hikariDataSource.getConnection();
         PreparedStatement ps = conn.prepareStatement(sql)) {
        
        ps.setString(1, cardHash);
        ps.setBigDecimal(2, amount);
        try (ResultSet rs = ps.executeQuery()) {
            return rs.next() && rs.getBoolean("is_success");
        }
    } catch (SQLException ex) {
        logToSyslog("CRITICAL", "SQL_TX_FAILED", "Сбой финансовой транзакции: " + ex.getMessage());
        return false;
    }
}
```
* **Последствия Connection Leak для банкомата:** Если из-за необработанного исключения `conn.close()` не будет вызван, уже через 10 операций весь пул банкомата будет исчерпан. Следующий клиент вставит карту, банкомат попытается получить соединение, зависнет на 3 секунды, выбросит ошибку таймаута и перейдет в режим «Вне обслуживания» (Out of Order), заблокировав выдачу наличных.

#### Задание 4.2. Замер задержки установления сессии (Latency Benchmark)
```javascript
import { Pool, Client } from 'pg';
import { performance } from 'perf_hooks';

async function runConnectionBenchmark(dbConfig) {
  console.log('--- ЗАПУСК БЕНЧМАРКА СКОРОСТИ СОЕДИНЕНИЙ ---');

  // 1. Замер чистого прямого подключения (Cold Handshake)
  const directClient = new Client(dbConfig);
  const startDirect = performance.now();
  await directClient.connect();
  await directClient.query('SELECT 1;');
  await directClient.end();
  const directDuration = (performance.now() - startDirect).toFixed(2);
  console.log(`1. Прямое соединение (TCP+TLS+Auth Handshake): ${directDuration} мс`);

  // 2. Инициализация пула соединений
  const pool = new Pool(dbConfig);
  // Прогрев пула
  const warmupClient = await pool.connect();
  warmupClient.release();

  // 3. Замер аренды готового сокета из пула (Warm Pooled Connection)
  const startPool = performance.now();
  const pooledClient = await pool.connect();
  await pooledClient.query('SELECT 1;');
  pooledClient.release(); // возврат в пул
  const poolDuration = (performance.now() - startPool).toFixed(2);
  console.log(`2. Аренда готового соединения из пула: ${poolDuration} мс`);

  console.log(`Ускорение за счет пула соединений: ${(directDuration / poolDuration).toFixed(1)} раз!`);
  await pool.end();
}
```
* **Ожидаемая разница:** Прямое установление соединения занимает **80–180 мс** (L4 сокет + SSL обмен + аутентификация + инициализация бэкенда Postgres). Аренда из пула соединений занимает **0.3–1.5 мс**. Разница составляет от 50 до 200 раз в пользу использования пула!

* **Расчет пула соединений:**
  * Сервер СУБД имеет 8 ядер CPU и RAID-массив SSD (число шпинделей принимается равным 1).
  * Формула PostgreSQL: $	ext{Pool Size} = (	ext{CPU} 	imes 2) + 	ext{Disk Spindles} = (8 	imes 2) + 1 = 17$.
  * Таким образом, оптимальный `max_pool_size` составляет **16–20 соединений**. Увеличение пула свыше 25–30 соединений на 8-ядерном сервере вызовет деградацию throughput из-за постоянных блокировок context switching.
* **Файл `config.json`:**

    "max_pool_size": 18,
    "idle_timeout_ms": 300000,
    "connection_timeout_ms": 3000,
    "leak_detection_threshold_ms": 2000
  }
}

### Задание 2: Диагностика сетевых сбоев и отказоустойчивое логирование
```python
import os
import sys
import time
import logging
import psycopg2
from psycopg2 import pool
from dotenv import load_dotenv

load_dotenv()

logging.basicConfig(
    filename='connection_errors.log',
    level=logging.INFO,
    format='[%(asctime)s] [%(levelname)s] [DB_DIAG] %(message)s'
)

def run_health_check_with_retries(max_retries=3, delay_sec=2):
    db_pool = None
    try:
        db_pool = psycopg2.pool.SimpleConnectionPool(
            minconn=int(os.getenv('DB_POOL_MIN', 2)),
            maxconn=int(os.getenv('DB_POOL_MAX', 10)),
            host=os.getenv('DB_HOST'),
            port=int(os.getenv('DB_PORT', 5432)),
            dbname=os.getenv('DB_NAME'),
            user=os.getenv('DB_USER'),
            password=os.getenv('DB_PASSWORD'),
            sslmode=os.getenv('DB_SSLMODE', 'verify-full'),
            sslrootcert=os.getenv('DB_SSLROOTCERT'),
            connect_timeout=int(os.getenv('DB_CONNECT_TIMEOUT', 4))
        )
    except psycopg2.OperationalError as ex:
        err = str(ex).strip()
        logging.error(f"Не удалось инициализировать пул соединений: {err}")
        return False

    for attempt in range(1, max_retries + 1):
        conn = None
        try:
            conn = db_pool.getconn()
            with conn.cursor() as cur:
                cur.execute("SELECT 1;")
                cur.fetchone()
            logging.info(f"Health Check успешно пройден с попытки {attempt}.")
            print("База данных доступна.")
            db_pool.putconn(conn)
            return True
        except psycopg2.OperationalError as ex:
            err = str(ex).strip()
            if "Connection refused" in err or "could not connect" in err:
                logging.warning(f"Попытка {attempt}/{max_retries}: Connection Refused на порту {os.getenv('DB_PORT')}. "
                                f"Причина: Служба СУБД остановлена или сетевой порт заблокирован экраном.")
            elif "timeout" in err.lower():
                logging.error(f"Попытка {attempt}/{max_retries}: Превышено время ожидания ответа сервера СУБД (таймаут {os.getenv('DB_CONNECT_TIMEOUT')}с).")
            else:
                logging.error(f"Попытка {attempt}/{max_retries}: Сетевой сбой: {err}")

            if conn is not None:
                db_pool.putconn(conn)
            
            if attempt < max_retries:
                time.sleep(delay_sec)
            else:
                logging.critical("Все попытки подключения исчерпаны. Аварийная остановка сервиса.")
                print("КРИТИЧЕСКАЯ ОШИБКА: Сервер СУБД недоступен. Завершение работы.")
                sys.exit(1)

if __name__ == '__main__':
    run_health_check_with_retries()
```

## 4. Классификатор студенческих ошибок и штрафные вычеты

| Категория ошибки | Описание проявления | Штраф | Способ устранения |
| :--- | :--- | :---: | :--- |
| **Критическая: Хардкод секретов** | Пароль к СУБД или путь к ключу прописан прямо в файле с кодом программы. | **-2 балла** | Вынести параметры в `.env` или `config.json`, добавить файл в `.gitignore`, создать `.env.example`. |
| **Критическая: Connection Leak** | Отсутствует блок `finally` или контекстный менеджер при вызове `getconn() / getConnection()`. | **-1 балл** | Обернуть вызовы в `try ... finally` с вызовом `release() / putconn() / Dispose()`. |
| **Архитектурная: Раздутый пул** | Размер пула указан как 500–1000 для локального приложения или слабого сервера. | **-1 балл** | Произвести расчет по формуле $(CPU 	imes 2) + 1$, ограничить пул 10–20 соединениями. |
| **Сетевая: Бесконечный таймаут** | `connect_timeout` опущен или задан равным 0. | **-0.5 балла** | Установить явный лимит таймаута от 2 до 5 секунд для реализации принципа Fail-Fast. |
| **Безопасность: sslmode=disable** | Использование незашифрованного канала в сценарии с персональными данными (медкарта). | **-1 балл** | Задать `sslmode=verify-full` и указать путь к `sslrootcert`. |
| **Диагностическая: Аварийный краш** | Отсутствует блок `try ... catch`, программа «вылетает» с необработанным трассировочным дампом. | **-1 балл** | Перехватывать исключения драйвера СУБД, выводить понятное сообщение пользователю и писать ошибку в лог. |
| **Интерфейсная: Синтаксис JSON/YAML** | Лишняя запятая в конце списка JSON или некорректные отступы табуляцией в YAML. | **-0.5 балла** | Проверить валидатором синтаксиса, исправить отступы пробелами. |
