## 3. Полные закрытые эталоны решений по 4 практическим кейсам

### Вариант 1. Высоконагруженная СУБД интернет-банкинга

#### 1. Анализ предметной области и схемы таблиц
- Таблица `Счета` (`Accounts`): `id_счета` (BIGINT, PK), `id_клиента` (BIGINT), `номер_счета` (VARCHAR(34), UNIQUE), `валюта` (CHAR(3)), `баланс` (NUMERIC(15,2)), `дата_открытия` (DATE).
- Таблица `Транзакции` (`Transactions`): `id_транзакции` (BIGINT, PK), `id_счета` (BIGINT, FK -> Accounts), `дата_транзакции` (TIMESTAMP), `сумма` (NUMERIC(15,2)), `тип_операции` (VARCHAR(20)), `назначение` (TEXT).

#### 2. DDL-скрипт создания связей и индексов
```sql
-- Связывание таблиц внешним ключом
ALTER TABLE Transactions 
  ADD CONSTRAINT fk_transactions_account 
  FOREIGN KEY (id_счета) REFERENCES Accounts(id_счета) 
  ON DELETE RESTRICT ON UPDATE CASCADE;

-- 1. Индексация внешнего ключа (ликвидация Seq Scan при JOIN и блокировок)
CREATE INDEX idx_transactions_account_id 
ON Transactions (id_счета);

-- 2. Оптимизация формирования банковской выписки за период
-- Запрос: SELECT * FROM Transactions WHERE id_счета = ? AND дата_транзакции BETWEEN ? AND ? ORDER BY дата_транзакции DESC;
CREATE INDEX idx_transactions_account_date 
ON Transactions (id_счета, дата_транзакции DESC);
```

#### 3. Инженерное обоснование порядка полей и правила левого префикса
- **Селективность и предикаты:** Поле `id_счета` фильтрует выборку по точному равенству (`=`), мгновенно отсекая 99.999% транзакций чужих клиентов. Поле `дата_транзакции` задает диапазон (`BETWEEN`, `>`, `<`). В сбалансированном B-Tree индексе поля с точным соответствием **обязаны** стоять левее диапазонных полей.
- **Использование сортировки:** Добавление направления `DESC` позволяет СУБД возвращать выписку в хронологическом порядке без выполнения тяжелой оперативной сортировки (`Sort / Top-N Sort`).
- **Левый префикс:** Индекс `(id_счета, дата_транзакции DESC)` полностью обслуживает запросы только по `id_счета`, что делает одиночный индекс на `id_счета` избыточным при наличии составного.

#### 4. Анализ плана EXPLAIN и накладные расходы
- **До индексации:** `Seq Scan on Transactions (cost=0.00..184520.00 rows=45 width=96) Filter: ((id_счета = 1042) AND (дата_транзакции >= ...)) Rows Removed by Filter: 9999955`. Стоимость колоссальна, время выполнения секунды.
- **После индексации:** `Index Scan using idx_transactions_account_date on Transactions (cost=0.43..8.50 rows=45 width=96) Index Cond: ((id_счета = 1042) AND (дата_транзакции >= ...))`. Время выполнения < 1 миллисекунды.
- **DML Overhead:** Банковская система совершает тысячи транзакций в секунду (`TPS`). Каждый `INSERT` транзакции приводит к обновлению индекса первичного ключа и индекса `(id_счета, дата_транзакции)`. При переполнении страниц B-Tree происходит расщепление (Page Split), вызывающее дополнительный ввод-вывод и генерацию WAL-записей. Лишние индексы на поля типа `сумма` или `тип_операции` создавать запрещено.

### Вариант 2. Биллинговая система оператора связи

#### 1. Анализ предметной области и схемы таблиц
- Таблица `Абоненты` (`Subscribers`): `id_абонента` (BIGINT, PK), `номер_телефона` (VARCHAR(15), UNIQUE), `фио` (VARCHAR(100)), `баланс` (NUMERIC(10,2)).
- Таблица `Тарифы` (`Tariffs`): `id_тарифа` (INT, PK), `название` (VARCHAR(50)), `цена_минуты` (NUMERIC(6,2)).
- Таблица `Звонки` (`Calls`): `id_звонка` (BIGINT, PK), `номер_телефона` (VARCHAR(15)), `id_тарифа` (INT, FK), `время_начала` (TIMESTAMP), `длительность` (INT), `статус` (VARCHAR(20)).

#### 2. DDL-скрипт создания индексов и частичного индекса
```sql
-- 1. Индексация внешнего ключа тарифа
CREATE INDEX idx_calls_tariff_id ON Calls (id_тарифа);

-- 2. Индекс на номер телефона для быстрого поиска абонента в реальном времени
CREATE INDEX idx_subscribers_phone ON Subscribers (номер_телефона);

-- 3. ЧАСТИЧНЫЙ ИНДЕКС (Partial Index) на активные вызовы:
-- В реальном времени из 100 млн звонков статус 'ACTIVE' имеют лишь 0.05% (50 тыс.).
CREATE INDEX idx_calls_active 
ON Calls (номер_телефона, время_начала) 
WHERE статус = 'ACTIVE';
```

#### 3. Инженерное обоснование частичного индекса (Partial Index)
- **Объем и компактность:** Стандартный B-Tree индекс на 100 000 000 записей таблицы `Calls` занял бы ~3.5 ГБ оперативной памяти. Частичный индекс с фильтром `WHERE статус = 'ACTIVE'` индексирует всего 50 000 строк и занимает менее 3 МБ, полностью помещаясь в L3-кэш процессора / буферный пул.
- **Накладные расходы при завершении:** При обновлении завершенных звонков (`статус = 'COMPLETED'`) запись автоматически удаляется из частичного индекса, что освобождает индексное дерево от необходимости хранить архивную историю.
- **Поиск в биллинге:** Запрос биллинговой службы `SELECT * FROM Calls WHERE статус = 'ACTIVE' AND номер_телефона = ?` выполняется мгновенно через точечный Index Scan.

#### 4. Анализ плана EXPLAIN и накладные расходы
- **План запроса:** СУБД использует `Index Scan using idx_calls_active on Calls (cost=0.29..4.31 rows=1 width=64) Index Cond: ((номер_телефона = '+79123456789'::text))`. Предикат `WHERE статус = 'ACTIVE'` входит в условия индекса и не требует чтения таблицы.
- **DML Overhead:** Вставка активного звонка добавляет ключ в частичный индекс; завершение звонка удаляет ключ. Это минимальная плата за ускорение мониторинга в 10 000 раз.

### Вариант 3. Каталог недвижимости

#### 1. Анализ предметной области и схемы таблиц
- Таблица `Города` (`Cities`): `город_id` (INT, PK), `название` (VARCHAR(100)).
- Таблица `Риелторы` (`Realtors`): `риелтор_id` (INT, PK), `фио` (VARCHAR(100)), `телефон` (VARCHAR(20)).
- Таблица `Объекты` (`Properties`): `объект_id` (BIGINT, PK), `город_id` (INT, FK), `риелтор_id` (INT, FK), `цена` (NUMERIC(12,2)), `комнат` (INT), `площадь` (NUMERIC(6,2)), `статус` (VARCHAR(20)).

#### 2. DDL-скрипт создания связей и составного индекса по диапазону
```sql
-- Индексация внешних ключей
CREATE INDEX idx_properties_city_fk ON Properties (город_id);
CREATE INDEX idx_properties_realtor_fk ON Properties (риелтор_id);

-- Составной индекс под типовой поисковый запрос витрины:
-- SELECT * FROM Properties WHERE город_id = 42 AND комнат = 2 AND цена BETWEEN 5000000 AND 9000000;
CREATE INDEX idx_properties_search 
ON Properties (город_id, комнат, цена);
```

#### 3. Инженерное обоснование порядка полей по селективности и типу фильтра
- **Золотое правило B-Tree:** Порядок полей в составном индексе строго подчиняется принципу: `[Столбцы точного равенства =] -> [Диапазонные столбцы <, >, BETWEEN] -> [Столбцы сортировки ORDER BY]`.
- **Анализ колонок:**
  1. `город_id` — точное равенство (`=`). Высокая селективность (сразу локализует ветку дерева нужного города).
  2. `комнат` — точное равенство (`=`). Дискретные значения (1, 2, 3, 4). Уточняет поиск внутри города.
  3. `цена` — непрерывный диапазон (`BETWEEN 5M AND 9M`). Стоит **строго последней**!
- **Фатальная ошибка перестановки:** Если поставить индекс как `(цена, город_id, комнат)`, то при запросе `WHERE цена BETWEEN 5M AND 9M AND город_id = 42` СУБД найдет начальную цену 5M, но дальше будет вынуждена сканировать весь массив цен подряд, проверяя `город_id` как обычный фильтр (Index Condition), поскольку упорядоченность по `город_id` внутри диапазона цен разрушена!

#### 4. Анализ плана EXPLAIN и накладные расходы
- **Правильный индекс `(город_id, комнат, цена)`:** `Index Scan using idx_properties_search on Properties (cost=0.42..12.30 rows=18 width=120) Index Cond: ((город_id = 42) AND (комнат = 2) AND (цена >= 5000000) AND (цена <= 9000000))`. Прочитано ровно 18 листовых записей.
- **Ошибочный индекс `(цена, город_id, комнат)`:** `Bitmap Index Scan on idx_bad (cost=120.40..2500.00 rows=18 width=120)`. Приходится проверять сотни тысяч квартир во всех городах диапазона цен.

### Вариант 4. Служба логистики и доставки

#### 1. Анализ предметной области и схемы таблиц
- Таблица `Курьеры` (`Couriers`): `id_курьера` (BIGINT, PK), `фио` (VARCHAR(100)), `транспорт` (VARCHAR(50)).
- Таблица `Маршруты` (`Routes`): `id_маршрута` (BIGINT, PK), `название_зоны` (VARCHAR(100)).
- Таблица `Заказы` (`Shipments`): `id_заказа` (BIGINT, PK), `трек_номер` (VARCHAR(30)), `id_курьера` (BIGINT, FK), `id_маршрута` (BIGINT, FK), `дата_доставки` (DATE), `статус` (VARCHAR(30)).

#### 2. DDL-скрипт создания уникального индекса и индекса для отчетов
```sql
-- 1. Уникальный индекс на трек-номер (бизнес-инвариант и точечный поиск)
CREATE UNIQUE INDEX uq_shipments_tracking_number 
ON Shipments (трек_номер);

-- 2. Индекс внешнего ключа курьера + дата для ежедневных оперативных отчетов:
-- SELECT * FROM Shipments WHERE id_курьера = 15 AND дата_доставки = CURRENT_DATE;
CREATE INDEX idx_shipments_courier_date 
ON Shipments (id_курьера, дата_доставки);

-- 3. Индекс внешнего ключа маршрута
CREATE INDEX idx_shipments_route_id 
ON Shipments (id_маршрута);
```

#### 3. Инженерное обоснование уникального индекса и индекса курьера
- **Уникальный индекс (UNIQUE):** Выполняет одновременно две критические функции: гарантирует целостность данных (исключает дублирование трек-номеров на физическом уровне) и обеспечивает поиск отправления клиентом за $O(\log N)$ операций ввода-вывода (глубина B-Tree дерева 3–4 уровня для сотен миллионов посылок).
- **Индекс по курьеру и дате:** Формирование путевых листов и отчетов по курьерам за рабочий день — наиболее частая транзакция склада. Составной индекс `(id_курьера, дата_доставки)` гарантирует, что логистический диспетчер получает список доставок курьера мгновенно без сканирования всей таблицы посылок.

#### 4. Анализ плана EXPLAIN и накладные расходы
- **Поиск по трек-номеру:** `Index Scan using uq_shipments_tracking_number on Shipments (cost=0.43..8.45 rows=1 width=85) Index Cond: ((трек_номер = 'TRK-987654321-RU'::text))`. Время отклика < 0.1 мс.
- **DML Overhead:** Каждая смена статуса посылки или ее регистрация обновляет уникальный индекс. Проверка уникальности требует предварительного поиска ключа в B-Tree перед каждой операцией вставки (Unique Constraint Check Overhead).

## 4. Полный закрытый эталон решения домашнего задания (domashnee_zadanie.html)

### Задание 1. Роль внешних ключей и физическая необходимость их индексации
- В реляционной теории внешний ключ (`FOREIGN KEY`) задает логическое ограничение ссылочной целостности (`Referential Integrity`).
- Большинство СУБД (PostgreSQL, Oracle, MS SQL Server) **НЕ создают автоматически** физические индексы на столбцы внешних ключей (в отличие от первичных ключей `PRIMARY KEY`).
- **Последствия отсутствия индекса на FK:**
  1. Любое соединение `JOIN Parent p ON c.parent_id = p.id` приводит к медленному полному сканированию дочерней таблицы (`Seq Scan`).
  2. При удалении или обновлении строки в родительской таблице (`DELETE FROM Parent WHERE id = 10`) СУБД вынуждена накладывать тяжелую разделяемую или исключительную блокировку на всю дочернюю таблицу и сканировать ее целиком для проверки отсутствия висячих ссылок, что парализует параллельные транзакции.

### Задание 2. Анализ правила левого префикса для составного индекса (A, B, C)
- Индекс создан как `CREATE INDEX idx_test ON T (A, B, C)`.
1. `WHERE A = 10 AND B = 'X' AND C > 5` — **Индекс используется полностью** (все 3 колонки: A и B точный поиск, C диапазонное сканирование).
2. `WHERE A = 10 AND B = 'X'` — **Индекс используется эффективно** (используется левый префикс `(A, B)`).
3. `WHERE A = 10` — **Индекс используется эффективно** (используется левый префикс `(A)`).
4. `WHERE B = 'X' AND C > 5` — **Индекс НЕ используется** (или используется неэффективно через дорогостоящий `Index Full Scan`), так как отсутствует ведущая колонка `A` (нарушение правила левого префикса).
5. `WHERE C > 5` — **Индекс НЕ используется**, так как отсутствуют колонки `A` и `B`.

### Задание 3. Анализ плана EXPLAIN
```
Seq Scan on orders (cost=0.00..45210.00 rows=12 width=80)
  Filter: ((customer_id = 502) AND (status = 'NEW'))
  Rows Removed by Filter: 1999988
```
- **Проблема:** СУБД выполнила последовательное сканирование всей таблицы `orders` из 2 миллионов записей (`Seq Scan`). Прочитано 2 000 000 строк, из них 1 999 988 отброшено фильтром, чтобы вернуть всего 12 строк! Стоимость составила 45 210 условных единиц.
- **Решение:** Создать составной индекс:
  ```sql
  CREATE INDEX idx_orders_customer_status ON orders (customer_id, status);
  ```
  После создания индекса план переключится на `Index Scan` со стоимостью ~8.50 и мгновенным откликом без чтения лишних страниц данных.

## 5. Классификатор типичных ошибок студентов и штрафные баллы

| Код ошибки | Описание студенческой ошибки | Штрафной вычет |
| :---: | :--- | :---: |
| **ERR-01** | **Игнорирование индексации внешнего ключа:** студент считает, что внешний ключ индексируется СУБД автоматически, и не создает индекс на `FK`. | **-1.0 балла** |
| **ERR-02** | **Нарушение правила левого префикса:** диапазонное поле (`BETWEEN`, `>`, `<`) поставлено в составном индексе раньше поля точного равенства (`=`). | **-1.0 балла** |
| **ERR-03** | **Избыточная индексация («индексы на все поля»):** создание одиночных индексов на каждую колонку таблицы без учета накладных расходов при вставке и обновлении. | **-0.5 балла** |
| **ERR-04** | **Низкая селективность индекса:** создание B-Tree индекса на булево поле или поле с 2–3 значениями (например, `пол` или `статус` в миллионной таблице без частичного индекса). | **-0.5 балла** |
| **ERR-05** | **Ошибочная интерпретация плана EXPLAIN:** утверждение, что `Seq Scan` всегда быстрее `Index Scan` или непонимание метрики `cost`. | **-0.5 балла** |
| **ERR-06** | **Пропуск блока самопроверки:** отсутствие ответов на контрольные вопросы в рабочем листе или ДЗ. | **-0.5 балла** |
