1. Архитектурная проблема: поиск данных в промышленных базах

В реляционных СУБД (PostgreSQL, Oracle, MySQL, MS SQL Server) таблицы физически хранятся в виде неупорядоченного набора страниц (кучи — Heap). Каждая страница (в PostgreSQL по умолчанию 8 КБ) содержит набор кортежей (строк). При добавлении записи СУБД помещает ее на первую попавшуюся страницу, где есть свободное место. Физический порядок строк никак не связан с их логическим значением.

Когда приложение выполняет запрос с фильтрацией (WHERE column = value), перед оптимизатором встает выбор метода доступа к данным. От этого выбора зависит, ответит ли СУБД за 0.05 миллисекунды или зависнет на десятки секунд при нагрузке.

3. Правила проектирования составных индексов под поиск по нескольким полям

3.1. Структура составного B-Tree (Composite Index)

Составной индекс строится по нескольким столбцам: CREATE INDEX idx_name ON table (col1, col2, col3);. Важно понимать, как данные упорядочены внутри дерева:

  • Кортежи индекса отсортированы строго по col1.
  • Значения col2 отсортированы только внутри строк с одинаковым значением col1.
  • Значения col3 отсортированы только внутри строк с одинаковыми значениями col1 и col2.
Золотое правило левого префикса (Left-Prefix Rule):

Индекс (col1, col2, col3) может эффективно использоваться планировщиком для запросов, содержащих в WHERE:

  • Только col1 (префикс длины 1);
  • col1 AND col2 (префикс длины 2);
  • col1 AND col2 AND col3 (полный ключ).

Если в секции WHERE указаны только col2 или col3, индекс НЕ МОЖЕТ быть использован для логарифмического спуска (возможен только Index Full Scan, уступающий прямому Seq Scan).

3.2. Принцип «Равенства вперед, диапазоны в конец» (Equality First, Range Last)

Если поисковый запрос содержит как предикаты точного равенства (=), так и диапазонные условия (<, >, BETWEEN), колонки в составном индексе обязаны располагаться в строгой последовательности:

-- ПРАВИЛЬНО: равенства ставятся первыми, диапазон закрывает индекс
CREATE INDEX idx_orders_client_date ON orders (client_id, status, created_at);

-- Запрос использует индекс на 100% мощности:
SELECT * FROM orders 
WHERE client_id = 1042 
  AND status = 'COMPLETED' 
  AND created_at BETWEEN '2024-01-01' AND '2024-06-30';
Почему нельзя ставить диапазон вперед?

Если создать индекс (created_at, client_id, status), то СУБД спустится в дерево по дате '2024-01-01' и пойдет сканировать все листовые страницы до '2024-06-30'. На этих страницах перемешаны миллионы разных клиентов и статусов! Поля client_id и status будут проверяться как обычный фильтр на лету (Filter condition), а не как ограничитель спуска B-Tree (Index Cond).

3.3. Сопоставление с шаблоном: LIKE и классы операторов

В PostgreSQL для строковых колонок B-Tree использует правила сортировки текущей локали (Collation). При локали ru_RU.UTF-8 стандартный B-Tree индекс не может оптимизировать предикат LIKE 'Иван%', потому что порядок сортировки символов в национальной локали зависит от регистра и составных правил языка.

-- Создание индекса со специальным операторным классом для быстрого LIKE по префиксу:
CREATE INDEX idx_clients_name_pfx ON clients (full_name varchar_pattern_ops);

4. Полнотекстовый поиск (Full-Text Search) и инвертированный индекс GIN

Для поиска фраз и слов в текстовых полях (статьи, книги, описания товаров, жалобы пользователей) реляционная СУБД предоставляет инструментарий полнотекстового поиска:

Векторизация текста (to_tsvector):

Функция разбирает текст на слова, удаляет знаки препинания и стоп-слова («в», «на», «и»), применяет стемминг (приведение к нормальной основе) и сохраняет отсортированный вектор лексем с номерами позиций.

SELECT to_tsvector('russian', 
  'Реляционные базы данных и проектирование');
-- Результат: 'баз':2 'дан':3 'проектирован':5 'реляцион':1
Поисковый запрос (to_tsquery):

Преобразует поисковую строку пользователя в логическую комбинацию лексем с поддержкой операторов & (И), | (ИЛИ), ! (НЕ), :* (префикс).

SELECT to_tsquery('russian', 
  'реляцион:* & баз:*');
-- Оператор проверки соответствия: @@
-- vector @@ query -> TRUE / FALSE

Для ускорения FTS-запросов создается GIN (Generalized Inverted Index):

-- Создание функционального GIN-индекса
CREATE INDEX idx_articles_fts ON articles USING gin (
  to_tsvector('russian', title || ' ' || content)
);

  5. Какую архитектурную задачу решает стемминг в полнотекстовом поиске? Чем инвертированный индекс GIN фундаментально отличается от дерева B-Tree?
  6. Почему в составном индексе столбцы с условиями точного равенства должны располагаться левее столбцов с диапазонами?
