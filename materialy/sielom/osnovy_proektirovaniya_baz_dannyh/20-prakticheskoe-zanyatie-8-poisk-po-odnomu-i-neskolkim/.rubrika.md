# Закрытая критериальная рубрика преподавателя: Поиск по одному и нескольким полям

Данный документ представляет собой закрытый методический инструмент преподавателя дисциплины «ОП.08 Основы проектирования баз данных» (СИЭУиП) и содержит критериальную шкалу оценивания, полные эталонные решения для всех 4 практических кейсов интерактивного листа `zanyatie.html`, эталон резервного домашнего задания `domashnee_zadanie.html` и классификатор типовых студенческих ошибок со шкалой штрафных вычетов.

## 1. Паспорт оценивания занятия

- **Дисциплина:** ОП.08 Основы проектирования баз данных.
- **Тематический раздел:** Тема 3. Этапы проектирования баз данных (§2.2 с.7 программы).
- **Тема занятия:** Практическое занятие №8: поиск по одному и нескольким полям (Занятие 20, завершение семестра 3).
- **Вид занятия:** Практическое занятие (2 академических часа: 80 минут основной регламент / 60 минут сокращенный).
- **Форма контроля:** Проверка индивидуального поискового протокола и аналитического отчета в интерактивном рабочем листе `zanyatie.html` (4 варианта) либо в резервном дистанционном задании `domashnee_zadanie.html`.
- **Критериальная шкала:** 4-балльная шкала:
  * **Часть 1. Поисковые запросы по ключу и диапазону:** **2 балла** (1 балл за мелкие синтаксические неточности SQL при верном плане поиска; 0 баллов при принципиально неверной фильтрации, отсутствии диапазонных условий или непонимании роли первичного ключа).
  * **Часть 2. Поиск по нескольким полям и шаблону:** **1 балл** (0 баллов при некорректном использовании оператора `LIKE`, ведущих символах `%` без обоснования деградации индекса, нарушении булевой логики `AND`/`OR` или отсутствии полнотекстового синтаксиса `@@` / `to_tsvector`).
  * **Часть 3. Анализ эффективности индексов и самопроверка:** **1 балл** (0 баллов при игнорировании различий `Index Scan` vs `Seq Scan`, отсутствии фиксации метрик времени отклика в поисковом протоколе или пропуске блока контрольных вопросов).
- **Срок сдачи:** До начала следующего занятия по расписанию (завершение 3 семестра).

| Балл | Критерий | Показатели выполнения и дескрипторы требований к решению |
| :---: | :--- | :--- |
| **2** | **Поисковые запросы по ключу и диапазону (отлично)** | Безупречно составлены SQL-запросы точечного поиска по первичному/уникальному ключу (`=` / `IN`) и диапазонного поиска (`BETWEEN`, `<`, `>`, `>=`). Продемонстрировано четкое понимание логарифмической сложности $O(\log N)$ поиска в B-Tree. Для диапазонного поиска указаны условия работы `Index Range Scan` и переходы по двусвязному списку листовых страниц B-Tree. Сформирован поисковый протокол с указанием ожидаемого типа плана и селективности. |
| **1** | **Поисковые запросы по ключу и диапазону (хорошо / частично)** | Запросы по ключу и диапазону составлены верно, но допущены мелкие синтаксические неточности, либо границы диапазона заданы нестрого (коллизии с включением крайних значений), либо отсутствует указание на тип сканирования в протоколе. |
| **0** | **Поисковые запросы по ключу и диапазону (неудовлетворительно)** | Запросы содержат грубые ошибки логики; точечный поиск по ключу не реализован; диапазонный предикат сформирован неверно; понимание разницы между $O(1)$, $O(\log N)$ и $O(N)$ отсутствует. |
| **1** | **Поиск по нескольким полям и шаблону (зачтено)** | Корректно составлены комбинированные предикаты по нескольким столбцам с учетом правила левого префикса в составных B-Tree индексах `(поле_равенства, поле_диапазона)`. В запросах с текстовым шаблоном четко разграничено поведение `LIKE 'prefix%'` (работает `Index Range Scan`) и `LIKE '%substr%'` (деградация в `Seq Scan` без триграммного индекса GIN/GiST). Для полнотекстовых сценариев применены конструкции `to_tsvector` и `to_tsquery` с оператором `@@`. |
| **0** | **Поиск по нескольким полям и шаблону (не зачтено)** | Ошибки в булевых операторах комбинированного поиска (путаница `AND`/`OR`); использование `%шаблон%` с утверждением, что B-Tree индекс ускорит поиск; игнорирование стемминга и стоп-слов при текстовом поиске; отсутствие полнотекстовых конструкций в профильных вариантах. |
| **1** | **Анализ эффективности индексов и самопроверка (зачтено)** | Заполнен полный поисковый протокол: сопоставлены реальные/ожидаемые типы сканирования (`Seq Scan`, `Index Scan`, `Bitmap Index Scan`, `Bitmap Heap Scan`, `GIN Scan`), время отклика (Execution Time) и количество прочитанных блоков (Shared Hit Blocks). Даны развернутые и научно аргументированные ответы на все контрольные вопросы самопроверки. |
| **0** | **Анализ эффективности индексов и самопроверка (не зачтено)** | Поисковый протокол пуст либо содержит шаблонные отписки без метрик времени и планов EXPLAIN; блок самопроверки не заполнен или ответы содержат грубые заблуждения («индекс ускоряет любой запрос с LIKE %...%»). |

## 3. Полные закрытые эталоны решений по 4 практическим кейсам

### Вариант 1. Поисковая система клиентской базы банка

#### 1. Анализ схемы и поисковых сценариев
- Таблица `bank_clients`: `client_id` (BIGINT, PK), `contract_number` (VARCHAR(30), UNIQUE), `full_name` (VARCHAR(200)), `region` (VARCHAR(80)), `status` (VARCHAR(20)), `monthly_income` (NUMERIC(12,2)), `created_at` (DATE).
- Запрос 1: Точечный поиск по точному номеру договора.
- Запрос 2: Поиск по маске ФИО `LIKE 'Иван%'`.
- Запрос 3: Комбинированный поиск по сочетанию: Регион + Статус + Диапазон доходов.

#### 2. SQL-запросы и структура индексов
```sql
-- 1. Точечный поиск по уникальному номеру договора (Index Scan, O(log N))
CREATE UNIQUE INDEX idx_bank_clients_contract ON bank_clients (contract_number);

SELECT client_id, full_name, region, status, monthly_income
FROM bank_clients
WHERE contract_number = 'DOG-2024-98412';

-- 2. Поиск по маске ФИО с левым префиксом (Index Range Scan)
-- Требуется btree индекс с текстовым классом операторов varchar_pattern_ops для non-C локалей
CREATE INDEX idx_bank_clients_fullname_prefix ON bank_clients (full_name varchar_pattern_ops);

SELECT client_id, full_name, contract_number, status
FROM bank_clients
WHERE full_name LIKE 'Иван%';

-- 3. Комбинированный фильтр: Регион + Статус + Диапазон доходов
-- Индекс формируется по правилу: равенства вперед, диапазон в конец
CREATE INDEX idx_bank_clients_composite ON bank_clients (region, status, monthly_income);

SELECT client_id, full_name, contract_number, monthly_income
FROM bank_clients
WHERE region = 'ХМАО-Югра'
  AND status = 'ACTIVE'
  AND monthly_income BETWEEN 80000 AND 150000;
```

#### 3. Эталонный поисковый протокол
| № | Тип поискового сценария | Предикат WHERE | Используемый индекс | Ожидаемый узел плана EXPLAIN | Ожидаемое время отклика |
| :-: | :--- | :--- | :--- | :--- | :--- |
| 1 | Точечный поиск по ключу | `contract_number = '...'` | `idx_bank_clients_contract` | `Index Scan` (1 строка) | < 0.05 мс |
| 2 | Поиск по левому префиксу | `full_name LIKE 'Иван%'` | `idx_bank_clients_fullname_prefix` | `Index Range Scan` | 0.15–0.45 мс |
| 3 | Комбинированный поиск | `region = ... AND status = ... AND monthly_income BETWEEN ...` | `idx_bank_clients_composite` | `Index Scan` / `Bitmap Index Scan` | 0.20–0.80 мс |
| 4 | Антипаттерн: поиск с середины | `full_name LIKE '%Иван%'` | Отсутствует (или `gin_trgm`) | `Seq Scan` (чтение всей таблицы) | 120–450 мс |

### Вариант 2. Каталог научной библиотеки

#### 1. Анализ схемы и поисковых сценариев
- Таблица `books`: `book_id` (BIGINT, PK), `isbn` (VARCHAR(20), UNIQUE), `author_name` (VARCHAR(150)), `title` (VARCHAR(250)), `annotation` (TEXT), `publication_year` (INT), `language_code` (CHAR(2)).
- Запрос 1: Поиск по ISBN.
- Запрос 2: Поиск по фамилии автора.
- Запрос 3: Полнотекстовый поиск по названию и аннотации с GIN-индексом.

#### 2. SQL-запросы и структура индексов
```sql
-- 1. Точечный поиск по международному стандартному номеру книги
CREATE UNIQUE INDEX idx_books_isbn ON books (isbn);

SELECT book_id, title, author_name, publication_year
FROM books
WHERE isbn = '978-5-97060-845-6';

-- 2. Поиск по автору (равенство или префикс)
CREATE INDEX idx_books_author ON books (author_name varchar_pattern_ops);

SELECT book_id, title, publication_year
FROM books
WHERE author_name = 'Дейт К. Дж.' OR author_name LIKE 'Дейт%';

-- 3. Полнотекстовый поиск по названию и аннотации через to_tsvector и to_tsquery
-- Добавление сгенерированной колонки или функциональный GIN-индекс
CREATE INDEX idx_books_fts ON books USING gin (
  to_tsvector('russian', title || ' ' || COALESCE(annotation, ''))
);

SELECT book_id, title, author_name, 
       ts_rank(to_tsvector('russian', title || ' ' || COALESCE(annotation, '')), to_tsquery('russian', 'реляционн:* & проек预* | нормализац:*')) AS rank
FROM books
WHERE to_tsvector('russian', title || ' ' || COALESCE(annotation, '')) @@ to_tsquery('russian', 'реляционн:* & нормализац:*')
ORDER BY rank DESC;
```

#### 3. Эталонный поисковый протокол
| № | Тип поискового сценария | Предикат WHERE | Используемый индекс | Ожидаемый узел плана EXPLAIN | Ожидаемое время отклика |
| :-: | :--- | :--- | :--- | :--- | :--- |
| 1 | Поиск по ISBN | `isbn = '...'` | `idx_books_isbn` (B-Tree Unique) | `Index Scan` | < 0.05 мс |
| 2 | Поиск по фамилии автора | `author_name = '...'` | `idx_books_author` (B-Tree) | `Index Scan` | 0.08–0.25 мс |
| 3 | Полнотекстовый поиск | `... @@ to_tsquery(...)` | `idx_books_fts` (GIN) | `Bitmap Index Scan on idx_books_fts` + `Bitmap Heap Scan` | 0.8–2.5 мс |
| 4 | Антипаттерн: LIKE по аннотации | `annotation LIKE '%реляцион%'` | B-Tree бесполезен | `Seq Scan` (полное сканирование мегабайтов текста) | 250–900 мс |

### Вариант 3. Реестр медицинских карт поликлиники

#### 1. Анализ схемы и поисковых сценариев
- Таблица `medical_records`: `record_id` (BIGINT, PK), `policy_number` (CHAR(16), UNIQUE), `patient_name` (VARCHAR(150)), `department_code` (VARCHAR(20)), `visit_date` (TIMESTAMP), `diagnosis_code` (VARCHAR(10)), `doctor_id` (INT).
- Запрос 1: Поиск по 16-значному номеру полиса ОМС.
- Запрос 2: Поиск визитов пациента в заданном диапазоне дат.
- Запрос 3: Комбинированный поиск по отделению и диагнозу с сортировкой по дате.

#### 2. SQL-запросы и структура индексов
```sql
-- 1. Точечный поиск по полису ОМС
CREATE UNIQUE INDEX idx_med_policy ON medical_records (policy_number);

SELECT record_id, patient_name, visit_date, department_code, diagnosis_code
FROM medical_records
WHERE policy_number = '8600001234567890';

-- 2. Диапазонный поиск по дате визита в рамках пациента/отделения
CREATE INDEX idx_med_patient_date ON medical_records (policy_number, visit_date DESC);

SELECT record_id, visit_date, diagnosis_code, doctor_id
FROM medical_records
WHERE policy_number = '8600001234567890'
  AND visit_date BETWEEN '2024-01-01 00:00:00' AND '2024-06-30 23:59:59';

-- 3. Комбинированный поиск по отделению и диагнозу (МКБ-10)
CREATE INDEX idx_med_dept_diagnosis ON medical_records (department_code, diagnosis_code, visit_date);

SELECT record_id, policy_number, patient_name, visit_date
FROM medical_records
WHERE department_code = 'CARDIOLOGY'
  AND diagnosis_code = 'I20.0'
  AND visit_date >= '2024-09-01';
```

#### 3. Эталонный поисковый протокол
| № | Тип поискового сценария | Предикат WHERE | Используемый индекс | Ожидаемый узел плана EXPLAIN | Ожидаемое время отклика |
| :-: | :--- | :--- | :--- | :--- | :--- |
| 1 | Точечный поиск по ОМС | `policy_number = '...'` | `idx_med_policy` (Unique B-Tree) | `Index Scan` | < 0.05 мс |
| 2 | Диапазон дат визита | `policy_number = ... AND visit_date BETWEEN ...` | `idx_med_patient_date` | `Index Range Scan` (без сортировки) | 0.10–0.30 мс |
| 3 | Отделение + Диагноз + Дата | `department_code = ... AND diagnosis_code = ...` | `idx_med_dept_diagnosis` | `Index Scan` | 0.15–0.40 мс |
| 4 | Ошибка: диапазон перед равенством | `visit_date BETWEEN ... AND department_code = ...` | Индекс `(visit_date, department_code)` | `Index Range Scan` с фильтрацией на лету | 2.5–10.0 мс |

### Вариант 4. Служба поддержки пользователей IT-сервиса (Service Desk)

- Запрос 1: Точечный поиск тикета по числовому ID или UUID.
- Запрос 2: Поиск по теме тикета (префиксный или полнотекстовый).
- Запрос 3: Комбинированная фильтрация по приоритету, исполнителю и статусу решения.

#### 2. SQL-запросы и структура индексов

-- 1. Точечный поиск по идентификатору тикета
SELECT ticket_id, subject, priority, status, created_at
FROM support_tickets
WHERE ticket_id = 459102;

CREATE INDEX idx_tickets_subject_pfx ON support_tickets (subject varchar_pattern_ops);

SELECT ticket_id, subject, priority, status
FROM support_tickets
WHERE subject LIKE 'VPN%';

-- 3. Комбинированный фильтр очереди инженера
CREATE INDEX idx_tickets_queue ON support_tickets (assigned_engineer_id, status, priority, created_at DESC);

SELECT ticket_id, subject, priority, created_at
FROM support_tickets
WHERE assigned_engineer_id = 42
  AND status = 'IN_PROGRESS'
  AND priority IN ('HIGH', 'CRITICAL')
ORDER BY created_at DESC;

## 4. Эталон резервного домашнего задания `domashnee_zadanie.html`

### 1. Постановка комплексного фильтра
Проектирование мультипоисковой системы для онлайн-агрегатора коммерческой недвижимости `commercial_realty`:
- Поля: `object_id` (PK), `cadastral_number` (UNIQUE), `city`, `district`, `deal_type` ('RENT', 'SALE'), `area_sqm`, `price_rub`, `status` ('ACTIVE', 'ARCHIVED'), `description`.
- Задача: Реализовать быстрый поисковый фильтр с произвольным сочетанием параметров: Город + Район + Тип сделки + Диапазон площади + Диапазон цены.

### 2. Эталонное DDL и индексное решение
```sql
-- 1. Точечный кадастровый поиск
CREATE UNIQUE INDEX idx_realty_cadastre ON commercial_realty (cadastral_number);

-- 2. Частичный составной индекс под актуальные объявления (исключаем архив)
-- Порядок: Равенства (city, deal_type, district) -> Диапазоны (price_rub, area_sqm)
CREATE INDEX idx_realty_active_search 
ON commercial_realty (city, deal_type, district, price_rub, area_sqm)
WHERE status = 'ACTIVE';

-- 3. GIN-индекс для полнотекстового поиска по описанию объекта
CREATE INDEX idx_realty_fts ON commercial_realty USING gin (to_tsvector('russian', description));
```

### 3. Сравнительный анализ планов EXPLAIN
- **Без составного индекса:** Планировщик выбирает `Seq Scan`, читает 1 500 000 строк с диска, время выполнения 1 850 мс, расход памяти 45 МБ.
- **С частичным составным B-Tree индексом:** Планировщик выбирает `Index Scan`, фильтрует 99.8% данных в листьях дерева за 3 операции ввода-вывода (24 КБ), извлекает ровно 14 подходящих записей, время выполнения **0.62 мс** (ускорение в ~3 000 раз!).

## 5. Классификатор типовых студенческих ошибок и штрафные баллы

| Код ошибки | Сущность ошибки | Снятие баллов |
| :---: | :--- | :---: |
| **ERR-01** | **Иллюзия B-Tree на маску `%text%`:** Студент утверждает, что стандартный B-Tree индекс ускоряет поиск с ведущим процентом (`LIKE '%строка%'`). Причина ошибки — непонимание того, что B-Tree упорядочивает ключи лексикографически слева направо. | **-1.0 балл** |
| **ERR-02** | **Нарушение правила левого префикса в составном индексе:** Размещение диапазонного поля перед полем точного равенства `(created_at, status)` вместо `(status, created_at)`. В результате поле равенства не участвует в бинарном поиске по дереву. | **-0.5 балла** |
| **ERR-03** | **Смешение LIKE и полнотекстового поиска (FTS):** Попытка искать слова в различных словоформах через `LIKE` вместо стемминга `to_tsvector`/`to_tsquery`. Игнорирование стоп-слов, морфологии русского языка и инвертированного индекса GIN. | **-0.5 балла** |
| **ERR-04** | **Отсутствие поискового протокола / пустые графы времени:** В протоколе не зафиксированы сравнительные метрики времени отклика и типы сканирования (`Seq Scan` vs `Index Scan`). | **-1.0 балл** |
| **ERR-05** | **Игнорирование локали (COLLATE / varchar_pattern_ops):** Использование B-Tree по строковому полю с оператором `LIKE 'А%'` в локали `ru_RU.UTF-8` без создания индекса с операторным классом `varchar_pattern_ops` (в PostgreSQL стандартный B-Tree в не-C локали не поддерживает оптимизацию LIKE). | **-0.5 балла** |
| **ERR-06** | **Пропуск блока самопроверки:** Отсутствие ответов на теоретические контрольные вопросы в рабочем листе или домашнем задании. | **-0.5 балла** |
