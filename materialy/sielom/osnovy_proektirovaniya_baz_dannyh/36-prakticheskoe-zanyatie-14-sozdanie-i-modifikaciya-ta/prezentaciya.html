Создание и модификация таблиц БД

Цель: схема, которая защищает данные

Проектируем связанные сущности, задаём ключи и ограничения, затем меняем структуру без потери данных.

Сначала — факты и зависимости

  • Одна строка описывает один экземпляр сущности.
  • Атомарные атрибуты; повторяющиеся группы — отдельные строки.
  • Атрибут зависит от ключа именно этой таблицы.

Составной или суррогатный ключ?

Составной ключ задаёт уникальность сочетания. Суррогатный идентификатор стабилен, но не заменяет бизнес-правило UNIQUE.

PRIMARY KEY (book_id, copy_no)
booking_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY

Три сущности — один связный домен

Салоны → автомобили → сделки. Разделите независимые факты; задайте FK; решите, где хранится история и кто является владельцем зависимых записей.

Ограничения — исполнимые правила

  • NOT NULL: значение обязательно.
  • UNIQUE: нет повторяющегося бизнес-ключа.
  • CHECK: допустимый диапазон или согласованность полей.
  • FOREIGN KEY: ссылка ведёт к существующей строке.

Удаление родителя: три политики

CASCADE удаляет зависимых потомков; RESTRICT блокирует удаление при ссылках; SET NULL сохраняет потомка без ссылки, если FK допускает NULL.

Выбирайте по смыслу и сохранности истории, а не по краткости SQL.

DDL строится в порядке зависимостей

CREATE TABLE salon (...);
CREATE TABLE vehicle (
  salon_id bigint NOT NULL REFERENCES salon(salon_id)
    ON DELETE RESTRICT
);

Сначала родительская таблица; FK указывает на PK или UNIQUE.

ALTER TABLE: управляемая эволюция

ALTER TABLE member ADD COLUMN status text;
ALTER TABLE member RENAME COLUMN status TO state;
ALTER TABLE member DROP COLUMN obsolete_note;
ALTER TABLE member ADD CONSTRAINT ck_period
  CHECK (valid_to > valid_from);

Новые правила проверяют старые строки

Перед CHECK ищите нарушителей. Перед NOT NULL — пропуски. Перед UNIQUE — дубликаты. Перед FK — «осиротевшие» ссылки. Исправление данных требует согласованного решения, не автоматического удаления.

Безопасный план миграции

  1. Резервная копия и план отката.
  2. Инвентаризация значений и зависимостей.
  3. Подготовка и проверка данных.
  4. Изменение схемы, контроль результата.
  5. Фиксация после успешных проверок.

Изменение типа: где скрыта потеря?

Сужение длины может отвергнуть или обрезать значения; смена точности — округлить; парсинг даты — выявить некорректный формат. Проверьте диапазон и явное преобразование на фактических данных.

Практика: четыре предметных контекста

  • Автодилер: VIN, комиссия, судьба сделок.
  • Фитнес: сроки действия и статусы.
  • Библиотека: выдачи и лимит книг.
  • Отель: категории номеров, вместимость, даты.

Чек-лист перед сдачей

  • Есть 3–4 нормализованные сущности.
  • PK, FK и уникальность соответствуют требованиям.
  • Действие удаления обосновано.
  • Изменения учитывают существующие значения.
  • Названы проверки и способ восстановления.
