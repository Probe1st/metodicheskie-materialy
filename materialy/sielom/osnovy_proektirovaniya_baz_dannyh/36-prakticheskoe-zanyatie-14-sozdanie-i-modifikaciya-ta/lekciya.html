Тема 5. Организация запросов SQL: создание и модификация таблиц БД

Теоретический конспект. DDL описывает структуру базы данных и декларативные правила, которым должны соответствовать данные. Примеры ориентированы на PostgreSQL; отдельные формы команд зависят от СУБД.

1. От предметной области к отношениям

Сущность — различимый объект предметной области; атрибут описывает его свойство; связь отражает отношение между объектами. Преобразование модели в таблицы начинается с определения фактов, их владельцев и кратности связи. Для связи «один ко многим» внешний ключ размещают на стороне многих. Для «многие ко многим» создают связующую таблицу, обычно с двумя внешними ключами и составным первичным ключом.

Нормализация помогает не хранить один факт многократно и исключать аномалии вставки, обновления и удаления. Первая нормальная форма предполагает атомарное значение атрибута и отсутствие повторяющихся групп. При проектировании проверяют, что атрибут описывает именно ключ своей таблицы, а не другую сущность. Справочные значения, повторяемые и имеющие собственные свойства, выделяют в отдельные отношения. Нормализация не запрещает осознанную денормализацию ради измеримой задачи, но она требует обоснования и правил согласования.

2. Идентификация: первичный и альтернативный ключ

Первичный ключ однозначно идентифицирует строку, не допускает NULL и повторов. Составной ключ состоит из нескольких атрибутов; он естественен, когда уникальность существует только у сочетания, например пара «книга — экземпляр». Суррогатный ключ — технический идентификатор, например bigint GENERATED ALWAYS AS IDENTITY. Он стабилен и компактен, но не заменяет бизнес-ограничения. VIN, номер документа или код домена по-прежнему должен иметь UNIQUE, если уникален по требованиям.

CREATE TABLE salon (
  salon_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL,
  city text NOT NULL,
  CONSTRAINT uq_salon_name_city UNIQUE (name, city)
);

CREATE TABLE vehicle (
  vin char(17) PRIMARY KEY,
  salon_id bigint NOT NULL REFERENCES salon(salon_id) ON DELETE RESTRICT,
  model text NOT NULL,
  price numeric(12, 2) NOT NULL CHECK (price > 0)
);

Внешний ключ обеспечивает ссылочную целостность. Ссылаемые столбцы должны образовывать первичный или уникальный ключ; число столбцов и совместимость типов должны совпадать. Именованные ограничения проще диагностировать и изменять.

3. Действия при удалении родителя

Выбор выражает политику жизненного цикла данных, а не удобство выполнения команды. Для аудита вместо физического удаления часто применяют признак архивности. История, нужная для отчётности или юридического учёта, не должна исчезать каскадно без явного основания.

4. Декларативные ограничения

  • NOT NULL запрещает отсутствие значения. NULL не равен нулю, пустой строке или логическому FALSE.
  • UNIQUE запрещает повторение ключа/набора столбцов; правила учёта NULL могут зависеть от СУБД.
  • CHECK проверяет логическое условие на строке, например CHECK (valid_to > valid_from). Выражение CHECK должно быть истинным или неизвестным; поэтому обязательность полей при необходимости задают отдельно через NOT NULL.
  • FOREIGN KEY связывает допустимые значения с ключом родительской таблицы.
  • DEFAULT задаёт значение при пропуске столбца, но само по себе не запрещает NULL, явно переданный пользователем.

5. Создание таблиц и порядок зависимостей

Сначала создают таблицы-родители, затем дочерние; альтернативно сначала создают все таблицы, а внешние ключи добавляют позднее. Схему связывающей таблицы «посещение клиента» можно определить составным ключом:

CREATE TABLE visit (
  client_id bigint NOT NULL REFERENCES client(client_id) ON DELETE RESTRICT,
  visited_at timestamptz NOT NULL,
  club_id bigint NOT NULL REFERENCES club(club_id) ON DELETE RESTRICT,
  CONSTRAINT pk_visit PRIMARY KEY (client_id, visited_at)
);

Добавляйте ограничение на предметный инвариант. Уникальный индекс полезен для уникальности и поиска, но не исправляет ошибку в выборе бизнес-ключа. Имя ограничения делает миграции и сообщения об ошибках понятнее.

6. Изменение схемы через ALTER TABLE

ALTER TABLE membership ADD COLUMN status text;
ALTER TABLE membership RENAME COLUMN status TO state;
ALTER TABLE membership DROP COLUMN legacy_note;

ALTER TABLE membership
  ADD CONSTRAINT ck_membership_period CHECK (valid_to > valid_from);
ALTER TABLE membership
  ADD CONSTRAINT ck_membership_fee CHECK (fee >= 0);
ALTER TABLE membership DROP CONSTRAINT ck_membership_fee;

ALTER TABLE booking ALTER COLUMN guest_count SET NOT NULL;
ALTER TABLE booking ALTER COLUMN guest_count DROP NOT NULL;

ALTER TABLE deal ADD CONSTRAINT fk_deal_salon
  FOREIGN KEY (salon_id) REFERENCES salon(salon_id) ON DELETE CASCADE;
ALTER TABLE deal DROP CONSTRAINT fk_deal_salon;

Перед удалением столбца исследуют представления, запросы, приложения, триггеры и другие зависимости. Переименование сохраняет значения, но может сломать потребителей по старому имени. Снятие ограничения временно допускает состояние, ранее запрещённое, и должно быть ограничено по времени.

7. Безопасная миграция существующих данных

  1. Определить цель и контракт: какие строки должны пройти после миграции, какие клиенты используют столбец.
  2. Создать резервную копию и проверить восстановление; определить транзакционный режим и допустимую блокировку.
  3. Измерить данные: NULL, дубликаты, значения вне нового диапазона, длины строк, точность чисел, связанные строки.
  4. Сначала исправить или согласовать проблемные данные; не удалять их автоматически ради прохождения ограничения.
  5. Для обязательного нового поля безопасно добавить nullable-столбец, заполнить корректными значениями, проверить отсутствие NULL, затем установить NOT NULL.
  6. Перед CHECK/UNIQUE/FK найти конфликтующие строки. Для большого объёма продумать поэтапное создание и валидацию поддерживаемыми СУБД средствами.
  7. Для преобразования типа оценить диапазон, формат, округление, временную зону, локаль и потери точности; выполнить проверяемое явное преобразование на копии/транзакции.
  8. Проверить результат запросами, лог приложения и план отката. Зафиксировать только после успешных проверок.

Изменение varchar(100) на varchar(20) опасно, если существуют длинные значения. Преобразование точного numeric в целое может округлить/отбросить дробную часть в зависимости от конкретного выражения и СУБД. Смена текстовой даты на дату требует диагностики неверных форматов. Не предполагайте поведение — проверьте на фактических значениях в используемой СУБД.

8. Комплексный контроль проектного решения

  1. Каждая сущность хранит один тип фактов; повторяющаяся группа вынесена в строки/связующую таблицу.
  2. У каждой таблицы выбран устойчивый PK; бизнес-уникальность отдельно закреплена.
  3. FK соответствует кратности и совместим по типу; действие удаления согласовано с сохранностью истории.
  4. NOT NULL, CHECK, UNIQUE и DEFAULT не противоречат друг другу и смыслу данных.
  5. ALTER TABLE сохраняет значения и учитывает старые строки и внешние зависимости.
  6. План включает резерв, проверку, выполнение, подтверждение результата и откат.

Термины

DDL — язык определения данных; PK — первичный ключ; FK — внешний ключ; ограничение — правило допустимого состояния данных; миграция — управляемое изменение схемы и/или данных с контролем результата.
