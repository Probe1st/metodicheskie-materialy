# Закрытая критериальная рубрика преподавателя: Операторы манипулирования данными (DML)

Данный документ представляет собой закрытый методический инструмент преподавателя дисциплины «ОП.08 Основы проектирования баз данных» (СИЭУиП) и содержит критериальную шкалу оценивания, полные эталонные решения для всех 4 практических вариантов рабочего листа `zanyatie.html`, эталон резервного домашнего задания `domashnee_zadanie.html` и классификатор типовых студенческих ошибок со шкалой штрафных вычетов.

## 1. Паспорт оценивания занятия

- **Дисциплина:** ОП.08 Основы проектирования баз данных.
- **Тематический раздел:** Тема 5. Организация запросов SQL (§2.2 с.7–8 программы).
- **Тема занятия:** Операторы манипулирования данными (Занятие №31).
- **Вид занятия:** Урок с объяснением теории (2 академических часа: 80 минут основной регламент / 60 минут сокращенный).
- **Форма контроля:** Проверка индивидуального аналитического и проектного продукта в интерактивном рабочем листе `zanyatie.html` (4 дифференцированных варианта) либо в резервном дистанционном задании `domashnee_zadanie.html`.
- **Критериальная шкала:** 4-балльная шкала (составление INSERT/UPDATE/DELETE — 2 б., применение RETURNING и UPSERT — 1 б., выводы и самопроверка — 1 б.):
  * **Часть 1. Составление базовых операторов манипулирования (INSERT, UPDATE, DELETE):** **2 балла** (1 балл при наличии синтаксических неточностей или неоптимальных предикатов; 0 баллов при отсутствии обязательного предиката WHERE или неработоспособном запросе).
  * **Часть 2. Применение расширенных механизмов (RETURNING и UPSERT / ON CONFLICT):** **1 балл** (0.5 балла при синтаксических помарках в EXCLUDED или пропуске возвращаемых колонок; 0 баллов при отсутствии механизма слияния).
  * **Часть 3. Архитектурное обоснование, выводы и самопроверка:** **1 балл** (0.5 балла при неполном ответе; 0 баллов при отсутствии ответа или ошибочном понимании транзакционных механизмов WAL/блокировок).
- **Итоговая оценка:**
  * **4 балла** — «Отлично» (работа выполнена полностью, запросы безошибочны, аргументация логична);
  * **3 балла** — «Хорошо» (запросы в целом верны, допущены мелкие погрешности в оформлении или аргументации);
  * **2 балла** — «Удовлетворительно» (написаны только простейшие DML-запросы, механизмы UPSERT/RETURNING не освоены);
  * **0–1 балл** — «Не зачтено» (грубые ошибки, фатальное повреждение данных из-за отсутствия WHERE).

## 3. Эталоны решений рабочего листа `zanyatie.html`

### Вариант 1: Складской логистический комплекс

#### Задание 1.1: Пакетная вставка (Batch INSERT) с получением идентификаторов
```sql
INSERT INTO warehouse_stock (
  sku, 
  item_name, 
  stock_quantity, 
  purchase_price
) VALUES 
  ('SKU-CPU-01', 'Intel Core i5-13400', 10, 18500.00),
  ('SKU-MB-02', 'ASUS TUF Gaming B760-PLUS', 8, 14200.00),
  ('SKU-RAM-03', 'Kingston Fury DDR5 32GB Kit', 25, 9600.00),
  ('SKU-SSD-04', 'Samsung 980 Pro 1TB NVMe', 15, 8900.00),
  ('SKU-PSU-05', 'DeepCool DQ750-M-V2L 750W', 12, 7800.00)
RETURNING id, sku, last_received_at;
```

#### Задание 1.2: Атомарное обновление остатка при повторной накладной (UPSERT)
```sql
INSERT INTO warehouse_stock (
  sku, 
  item_name, 
  stock_quantity, 
  purchase_price
) VALUES (
  'SKU-CPU-01', 
  'Intel Core i5-13400', 
  5, 
  17900.00
)
ON CONFLICT (sku) 
DO UPDATE SET 
  stock_quantity = warehouse_stock.stock_quantity + EXCLUDED.stock_quantity,
  purchase_price = EXCLUDED.purchase_price,
  last_received_at = CURRENT_TIMESTAMP
RETURNING id, sku, stock_quantity, purchase_price;
```

#### Задание 1.3: Аналитическое обоснование
**Эталонный ответ:**
Предварительная проверка наличия записи через `SELECT` на стороне приложения не защищает от состояния гонки (Race Condition). Если два параллельных клиентских процесса одновременно выполнят проверку одного и того же артикула, оба увидят отсутствие записи и оба попытаются выполнить обычный `INSERT`. Один из запросов неизбежно упадет с ошибкой `unique_violation` (duplicate key), прервав транзакцию. Конструкция `ON CONFLICT DO UPDATE` переносит разрешение конфликта внутрь ядра СУБД: захватывается строчная блокировка (Row-Level Lock) на существующий кортеж, исключаются коллизии, и операция слияния выполняется строго атомарно без сбоя клиентского приложения.

### Вариант 2: Информационная система медицинской клиники

#### Задание 2.1: Модификация записей по соединению (UPDATE ... FROM)
```sql
UPDATE medical_appointments AS a
SET 
  appointment_status = 'CONFIRMED',
  confirmed_at = i.payment_time
FROM appointment_invoices AS i
WHERE a.appointment_id = i.appointment_id
  AND a.appointment_status = 'AWAITING_PAYMENT'
  AND i.payment_status = 'PAID'
RETURNING a.appointment_id, a.patient_id, a.appointment_status;
```

#### Задание 2.2: Селективное удаление отмененных приемов (DELETE ... RETURNING)
```sql
DELETE FROM medical_appointments
WHERE appointment_status = 'CANCELLED' 
  AND created_at < CURRENT_DATE - INTERVAL '1 year'
RETURNING appointment_id, patient_id, created_at;
```

#### Задание 2.3: Аналитическое обоснование
**Эталонный ответ:**
В синтаксисе PostgreSQL целевая обновляемая таблица неявно присутствует в контексте запроса. Если разработчик укажет `medical_appointments` повторно в секции `FROM` (например, `UPDATE medical_appointments a ... FROM medical_appointments a2, appointment_invoices i`), СУБД воспримет второе упоминание как независимый второй экземпляр таблицы и построит декартово произведение (Cartesian Product) строк таблицы самой на себя. Это приведет к многократной непредсказуемой перезаписи одних и тех же строк и колоссальной просадке производительности.

### Вариант 3: Банковский транзакционный процессинг

#### Задание 3.1: Перенос исторических данных (INSERT INTO ... SELECT)
```sql
INSERT INTO loan_contracts_archive (
  contract_num, 
  client_id, 
  total_settled
)
SELECT 
  c.contract_num, 
  c.client_id, 
  c.issued_amount
FROM loan_contracts AS c
WHERE c.status = 'CLOSED' 
  AND c.closed_at < CURRENT_DATE - INTERVAL '1 year';
```

#### Задание 3.2: Массовое начисление процентов по кредитам
```sql
UPDATE loan_contracts
SET current_debt = current_debt + (current_debt * 0.0005)
WHERE status = 'ACTIVE' 
  AND current_debt > 0
RETURNING contract_num, client_id, current_debt;
```

#### Задание 3.3: Аналитическое обоснование
**Эталонный ответ:**
Массовый `UPDATE` по миллиону строк в единой транзакции крайне опасен в высоконагруженных OLTP-системах по нескольким причинам:
1. **Блокировки и задержки:** Транзакция удерживает экспансивные строчные блокировки `ROW EXCLUSIVE` на миллион строк, блокируя любые параллельные транзакции, пытающиеся изменить те же договоры, что провоцирует дедлоки (Deadlocks) и накопление очередей подключений.
2. **Переполнение журнала WAL:** В модели MVCC операция `UPDATE` создает новую копию каждой строки. Модификация 1 млн строк сгенерирует сотни мегабайт или гигабайты записей в WAL, перегрузит подсистему дискового ввода/вывода (I/O) и вызовет затяжные контрольные точки (Checkpoints).
3. **Раздувание таблицы (Table Bloat) и нагрузка на VACUUM:** Миллион старых версий строк мгновенно становятся «мертвыми кортежами» (dead tuples). Процессу autovacuum потребуется длительное время для их очистки, а размер файлов таблицы и B-Tree индексов на диске увеличится вдвое. Решение: пакетная обработка порциями по 1 000 – 5 000 строк.

### Вариант 4: Образовательный портал колледжа

#### Задание 4.1: Идемпотентная фиксация оценок (UPSERT)
```sql
INSERT INTO student_grades (
  student_id, 
  discipline_id, 
  grade_value, 
  teacher_id
) VALUES (
  45, 
  8, 
  5, 
  12
)
ON CONFLICT (student_id, discipline_id) 
DO UPDATE SET 
  grade_value = EXCLUDED.grade_value,
  teacher_id = EXCLUDED.teacher_id,
  assigned_at = CURRENT_TIMESTAMP
RETURNING grade_id, student_id, grade_value, assigned_at;
```

#### Задание 4.2: Очистка неподтвержденных профилей
```sql
DELETE FROM portal_registration_requests
WHERE is_email_verified = FALSE 
  AND created_at < CURRENT_TIMESTAMP - INTERVAL '30 days'
RETURNING email;
```

#### Задание 4.3: Аналитическое обоснование
**Эталонный ответ:**
1. **Счетчик автоинкремента:** `DELETE FROM student_grades;` сохраняет текущее значение генератора последовательности (SEQUENCE / IDENTITY), поэтому следующая вставленная строка получит ID, продолжающий нумерацию. Напротив, `TRUNCATE TABLE student_grades RESTART IDENTITY;` обнуляет счетчик генератора к единице (по умолчанию при `CONTINUE IDENTITY` значение сохраняется).
2. **Блокировки:** `DELETE` использует блокировку `ROW EXCLUSIVE`, позволяя параллельным пользователям читать таблицу и выполнять операции над другими строками. `TRUNCATE` требует монопольной блокировки `ACCESS EXCLUSIVE`, которая блокирует абсолютно любые операции с таблицей, включая простые `SELECT`, делая портал временно недоступным для чтения ведомостей.

## 4. Эталон резервного домашнего задания `domashnee_zadanie.html`

### Задание 1: Комплексный запрос UPSERT для лицевых счетов
```sql
INSERT INTO client_bank_accounts (
  account_number, 
  client_id, 
  balance, 
  transactions_count, 
  last_activity_at
) VALUES (
  '40817810000012345678', 
  1054, 
  4500.00, 
  1, 
  CURRENT_TIMESTAMP
)
ON CONFLICT (account_number) 
DO UPDATE SET 
  balance = client_bank_accounts.balance + EXCLUDED.balance,
  transactions_count = client_bank_accounts.transactions_count + 1,
  last_activity_at = CURRENT_TIMESTAMP
RETURNING account_number, balance, transactions_count;
```

### Задание 2: Массовый UPDATE по ДМС со скидкой и RETURNING
```sql
UPDATE doctor_appointments AS a
SET 
  status = 'APPROVED_BY_INSURANCE',
  cost = a.cost * 0.90,
  updated_at = CURRENT_TIMESTAMP
FROM patient_insurances AS ins
WHERE a.patient_id = ins.patient_id
  AND a.status = 'PENDING_APPROVAL'
  AND ins.is_vip = TRUE
  AND ins.expires_at >= CURRENT_DATE
RETURNING a.appointment_id, a.patient_id, a.cost, a.status;
```

### Задание 3: Инженерное обоснование позиции DBA (25 млн строк логов)
**Ключевые тезисы:**
1. `DELETE FROM http_access_logs` потребует последовательного сканирования 25 млн кортежей, создания 25 млн dead tuples, записи гигабайтов информации в WAL (что может забить диск архивации WAL-логов) и займет от 10 до 30 минут с блокировкой I/O.
2. `TRUNCATE TABLE http_access_logs RESTART IDENTITY` выполняет системную операцию создания нового файла таблицы (`relfilenode`), сбрасывает счетчик IDENTITY и завершается за доли секунды без нагрузки на дисковый журнал WAL и процессор.

## 5. Классификатор типичных студенческих ошибок и штрафные баллы

| Ошибка | Описание и проявление | Штраф |
| :--- | :--- | :--- |
| **Отсутствие секции WHERE** | Фатальная ошибка: попытка выполнить UPDATE или DELETE над всей таблицей. | **-2.0 б.** (аннулирование задания) |
| **Игнорирование псевдотаблицы EXCLUDED** | В выражении `DO UPDATE SET` студент пишет `balance = balance + balance` вместо `EXCLUDED.balance`. | **-0.5 б.** |
| **Пропуск явного списка столбцов в INSERT** | Использование синтаксиса `INSERT INTO t VALUES (...)` без указания полей. | **-0.5 б.** |
| **Неверный синтаксис JOIN при UPDATE** | Попытка написать `UPDATE t JOIN t2 ON ...` вместо диалекта PostgreSQL `UPDATE t SET ... FROM t2 WHERE ...`. | **-0.5 б.** |
| **Пропуск секции RETURNING** | Запрос не возвращает сгенерированные идентификаторы или обновленные данные. | **-0.5 б.** |
| **Поверхностный аналитический ответ** | Отсутствие упоминания WAL, уровней блокировок или механизма MVCC при анализе производительности. | **-0.5 б.** |
