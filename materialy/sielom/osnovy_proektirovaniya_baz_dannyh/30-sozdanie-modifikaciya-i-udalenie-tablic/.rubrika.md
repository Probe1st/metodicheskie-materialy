## 2. Критериальная шкала оценивания (0–4 балла)

| Балл | Критерий | Показатели выполнения и дескрипторы требований к решению |
| :---: | :--- | :--- |
| **2** | **Написание DDL CREATE/ALTER (отлично)** | DDL-скрипт полностью синтаксически корректен и исполняем в PostgreSQL. Созданы все требуемые таблицы с корректными первичными ключами, типами данных и значениями по умолчанию. Операторы `ALTER TABLE` безупречны: добавление столбцов выполнено с `DEFAULT`, переименование атрибутов через `RENAME COLUMN`, а изменение типов данных (например, `INTEGER` в `NUMERIC(10,2)`) сопровождается обязательным явным преобразованием `USING колонка::NUMERIC(10,2)`. Создание временных таблиц выполнено через `CREATE TEMPORARY TABLE`. |
| **1** | **Написание DDL CREATE/ALTER (хорошо / частично)** | Допущены незначительные огрехи, не приводящие к фатальному сбою: пропущен `IF NOT EXISTS` / `IF EXISTS`, забыто указание значения `DEFAULT` при добавлении столбца `NOT NULL` (что вызовет ошибку на непустой таблице в старых версиях СУБД), либо опечатка в имени переименовываемой колонки при сохранении общей логики. |
| **0** | **Написание DDL CREATE/ALTER (неудовлетворительно)** | Грубые концептуальные ошибки: синтаксический брак в командах DDL; попытка изменить тип данных столбца с несовместимыми данными без конструкции `USING`; создание таблицы без первичного ключа; смешение DDL (`ALTER TABLE`) и DML (`UPDATE`). |
| **1** | **Модификация ограничений и CASCADE / RESTRICT (зачтено)** | Архитектурно верно реализовано управление ограничениями целостности: корректно применены конструкции `ADD CONSTRAINT` (с явным именованием ограничений) и `DROP CONSTRAINT`. Полноценно раскрыты опции ссылочной целостности: обосновано поведение `ON DELETE RESTRICT` (блокировка удаления при наличии дочерних строк) и `DROP TABLE ... CASCADE` (автоматический сброс зависимых ограничений и представлений). Понимание рисков неконтролируемого каскадирования в production. |
| **0** | **Модификация ограничений и CASCADE / RESTRICT (не зачтено)** | Ограничения создаются безымянными, что делает невозможным их безопасный последующий `DROP CONSTRAINT`; непонимание семантики `CASCADE` (иллюзия, что удаляются только данные, а не структура схемы); отсутствие понимания блокировки `RESTRICT`. |
| **1** | **Анализ DDL, TRUNCATE vs DELETE и самопроверка (зачтено)** | Дано исчерпывающее сравнение `TRUNCATE TABLE` и `DELETE` (разница на уровне физических страниц/экстентов, отсутствие записи WAL на каждую строку, сброс high water mark, невызов триггеров на строку). Корректно использована опция `RESTART IDENTITY`. Полноценно раскрыто влияние тяжелых DDL-операций на production-базу: блокировка `AccessExclusiveLock`, накопление очереди транзакций и методы миграции без простоя сервиса. На все вопросы самопроверки даны аргументированные ответы. |
| **0** | **Анализ DDL, TRUNCATE vs DELETE и самопроверка (не зачтено)** | Студент утверждает, что «TRUNCATE и DELETE — это одно и то же»; не может объяснить опцию `RESTART IDENTITY`; не понимает, почему добавление ограничения без `NOT VALID` вешает боевой сервис; контрольные вопросы оставлены без ответа. |

## 3. Закрытые эталонные решения по вариантам рабочего листа `zanyatie.html`

### Вариант 1. Складской логистический терминал

#### 1. Эталонный DDL-скрипт
```sql
-- 1. Создание основной таблицы складских комплексов
CREATE TABLE IF NOT EXISTS warehouses (
    warehouse_id SERIAL PRIMARY KEY,
    warehouse_name VARCHAR(100) NOT NULL,
    city VARCHAR(60) NOT NULL,
    total_area_sqm NUMERIC(10, 2) NOT NULL CHECK (total_area_sqm > 0),
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 2. Создание временной сессионной таблицы оперативной отгрузки
CREATE TEMPORARY TABLE IF NOT EXISTS temp_daily_shipments (
    shipment_id INT,
    warehouse_id INT,
    item_barcode VARCHAR(50),
    quantity INT CHECK (quantity > 0),
    scanned_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ON COMMIT PRESERVE ROWS;

-- 3. Добавление столбца температурного режима с дефолтным значением
ALTER TABLE warehouses 
    ADD COLUMN temperature_zone VARCHAR(20) NOT NULL DEFAULT 'STANDARD';

-- 4. Переименование столбца total_area_sqm в usable_area_sqm
ALTER TABLE warehouses 
    RENAME COLUMN total_area_sqm TO usable_area_sqm;

-- 5. Безопасное удаление временной таблицы отгрузки
DROP TABLE IF EXISTS temp_daily_shipments;
```

#### 2. Анализ опций и блокировок
- **Назначение DEFAULT 'STANDARD':** Начиная с PostgreSQL 11 добавление столбца с константным значением `DEFAULT` обновляет метаданные каталога (`pg_attribute`) мгновенно за $O(1)$ без полной перезаписи таблицы на диске. Это исключает длительную блокировку.
- **Временные таблицы (CREATE TEMPORARY TABLE):** Размещаются в специальной схеме `pg_temp_*`, видны строго внутри текущей сессии и автоматически уничтожаются при разрыве соединения. Блокировки и очистка не влияют на другие сессии.

### Вариант 2. Гостиничный сервис (модификация типов и CHECK)

#### 1. Эталонный DDL-скрипт
```sql
-- Исходное состояние таблицы (базовый контекст задачи)
CREATE TABLE IF NOT EXISTS hotel_rooms (
    room_id SERIAL PRIMARY KEY,
    room_number VARCHAR(10) NOT NULL,
    category VARCHAR(50) NOT NULL,
    price_per_night INTEGER NOT NULL,
    is_available BOOLEAN NOT NULL DEFAULT TRUE
);

-- 1. Изменение типа столбца price_per_night с INTEGER на NUMERIC(10, 2) с явным приведением USING
ALTER TABLE hotel_rooms 
    ALTER COLUMN price_per_night TYPE NUMERIC(10, 2) 
    USING price_per_night::NUMERIC(10, 2);

-- 2. Наложение именованного проверочного ограничения CHECK
ALTER TABLE hotel_rooms 
    ADD CONSTRAINT chk_hotel_rooms_positive_price 
    CHECK (price_per_night > 0.00);

-- 3. Проверка метаданных каталога
-- SELECT column_name, data_type, numeric_precision, numeric_scale 
-- FROM information_schema.columns 
-- WHERE table_name = 'hotel_rooms' AND column_name = 'price_per_night';
```

#### 2. Анализ эволюции схемы без простоя
- **Зачем нужен USING:** Без выражения `USING` СУБД выдаст ошибку `cannot be cast automatically`, если прямое двоичное преобразование невозможно. Конструкция `USING price_per_night::NUMERIC(10,2)` инструктирует ядро, как именно вычислить новое значение для каждой строки.
- **Предотвращение простоя (NOT VALID + VALIDATE):** Добавление `CHECK` на многомиллионной таблице в режиме `NOT VALID` не сканирует всю таблицу сразу, удерживая короткую блокировку. Затем фоновая команда `ALTER TABLE hotel_rooms VALIDATE CONSTRAINT chk_hotel_rooms_positive_price;` валидирует данные с блокировкой `ShareUpdateExclusiveLock`, позволяя параллельным `SELECT`, `INSERT`, `UPDATE` выполняться без ожидания.

### Вариант 3. Банковская система (ссылочная целостность и CASCADE)

#### 1. Эталонный DDL-скрипт
```sql
-- 1. Таблица учетных записей клиентов
CREATE TABLE IF NOT EXISTS bank_clients (
    client_id SERIAL PRIMARY KEY,
    passport_hash VARCHAR(64) NOT NULL UNIQUE,
    full_name VARCHAR(150) NOT NULL,
    registered_at DATE NOT NULL DEFAULT CURRENT_DATE
);

-- 2. Таблица расчетных счетов
CREATE TABLE IF NOT EXISTS bank_accounts (
    account_id SERIAL PRIMARY KEY,
    account_number VARCHAR(20) NOT NULL,
    client_id INT NOT NULL,
    balance NUMERIC(15, 2) NOT NULL DEFAULT 0.00,
    currency CHAR(3) NOT NULL DEFAULT 'RUB',
    CONSTRAINT unq_account_number UNIQUE (account_number)
);

-- 3. Таблица архивных журналов аудита
CREATE TABLE IF NOT EXISTS transaction_audit_logs (
    log_id BIGSERIAL PRIMARY KEY,
    account_id INT NOT NULL REFERENCES bank_accounts(account_id) ON DELETE CASCADE,
    action_type VARCHAR(30) NOT NULL,
    logged_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 4. Добавление внешнего ключа в bank_accounts с опцией ON DELETE RESTRICT
ALTER TABLE bank_accounts 
    ADD CONSTRAINT fk_bank_accounts_client 
    FOREIGN KEY (client_id) 
    REFERENCES bank_clients(client_id) 
    ON DELETE RESTRICT;

-- 5. Удаление устаревшего ограничения уникальности unq_account_number
ALTER TABLE bank_accounts 
    DROP CONSTRAINT unq_account_number;

-- 6. Безопасное удаление архивной таблицы с каскадным снятием зависимостей
DROP TABLE IF EXISTS transaction_audit_logs CASCADE;
```

#### 2. Анализ последствий CASCADE и RESTRICT
- **ON DELETE RESTRICT:** Блокирует удаление записи из `bank_clients`, если у клиента есть хотя бы один открытый счет в `bank_accounts`. СУБД возвращает ошибку `violates foreign key constraint`.
- **DROP TABLE ... CASCADE:** Удаляет саму таблицу `transaction_audit_logs` и автоматически сбрасывает все внешние ключи других таблиц, ссылающиеся на нее, а также зависимые представления (`VIEW`). Важно: данные в ссылающихся таблицах не удаляются, удаляются только ссылающиеся ограничения (foreign key constraints)!

### Вариант 4. Образовательный университетский портал (UNIQUE и TRUNCATE)

#### 1. Эталонный DDL-скрипт
```sql
-- 1. Создание таблицы академических дисциплин
CREATE TABLE IF NOT EXISTS disciplines (
    discipline_id SERIAL PRIMARY KEY,
    discipline_code VARCHAR(20) NOT NULL,
    title VARCHAR(150) NOT NULL,
    semester_num SMALLINT NOT NULL CHECK (semester_num BETWEEN 1 AND 12),
    total_hours INT NOT NULL CHECK (total_hours > 0),
    is_mandatory BOOLEAN NOT NULL DEFAULT TRUE
);

-- 2. Добавление составного уникального ограничения UNIQUE(discipline_code, semester_num)
ALTER TABLE disciplines 
    ADD CONSTRAINT unq_discipline_code_semester 
    UNIQUE (discipline_code, semester_num);

-- 3. Создание оперативной таблицы посещаемости
CREATE TABLE IF NOT EXISTS student_attendance_log (
    log_id BIGSERIAL PRIMARY KEY,
    discipline_id INT NOT NULL REFERENCES disciplines(discipline_id),
    student_id INT NOT NULL,
    attended_at DATE NOT NULL DEFAULT CURRENT_DATE,
    presence_status BOOLEAN NOT NULL DEFAULT FALSE
);

-- 4. Высокоскоростная очистка таблицы посещаемости со сбросом автоинкремента
TRUNCATE TABLE student_attendance_log RESTART IDENTITY;
```

#### 2. Анализ TRUNCATE TABLE vs DELETE
- **Механика TRUNCATE:** В отличие от `DELETE`, который построчно удаляет кортежи, пишет каждую строку в журнал предзаписи (WAL) и оставляет «мертвые кортежи» (dead tuples) до запуска VACUUM, `TRUNCATE TABLE`:
  1. Выделяет новый пустой файл данных (relfilenode) на диске.
  2. Моментально освобождает дисковое пространство за $O(1)$.
  3. Не активирует построчные триггеры `AFTER DELETE`.
  4. Опция `RESTART IDENTITY` обнуляет привязанную последовательность `BIGSERIAL` (счетчик `log_id` снова начнется с 1, а не продолжится с последнего значения).

## 4. Эталон резервного домашнего задания `domashnee_zadanie.html`

### Техническое задание
Разработать единый комплексный DDL-скрипт миграции базы данных системы логистики маркетплейса:
1. Создать базовую таблицу контрагентов `logistics_partners`.
2. Модифицировать таблицу рейсов `freight_routes`: добавить столбец `max_weight_kg`, переименовать столбец `driver` в `assigned_driver_fio`, конвертировать тип тарифа `base_rate` в `NUMERIC(12,2)` через `USING`.
3. Добавить внешний ключ с правилом `ON DELETE RESTRICT`.
4. Создать и очистить временный буфер отгрузки `TRUNCATE TABLE buffer_delivery RESTART IDENTITY`.
5. Безопасно удалить архивные таблицы с опцией `CASCADE`.

### Эталонный SQL-скрипт
```sql
-- 1. Создание таблицы партнеров
CREATE TABLE IF NOT EXISTS logistics_partners (
    partner_id SERIAL PRIMARY KEY,
    inn VARCHAR(12) NOT NULL UNIQUE,
    company_name VARCHAR(150) NOT NULL,
    rating NUMERIC(3, 2) NOT NULL DEFAULT 5.00 CHECK (rating BETWEEN 0.00 AND 5.00),
    is_active BOOLEAN NOT NULL DEFAULT TRUE
);

-- 2. Базовая таблица рейсов (контекст миграции)
CREATE TABLE IF NOT EXISTS freight_routes (
    route_id SERIAL PRIMARY KEY,
    partner_id INT NOT NULL,
    route_name VARCHAR(100) NOT NULL,
    driver VARCHAR(100) NOT NULL,
    base_rate INTEGER NOT NULL
);

-- 3. Комплексная миграция ALTER TABLE
ALTER TABLE freight_routes 
    ADD COLUMN max_weight_kg NUMERIC(8, 2) NOT NULL DEFAULT 1500.00,
    RENAME COLUMN driver TO assigned_driver_fio;

ALTER TABLE freight_routes 
    ALTER COLUMN base_rate TYPE NUMERIC(12, 2) USING base_rate::NUMERIC(12, 2);

-- 4. Наложение внешнего ключа с опцией ON DELETE RESTRICT
ALTER TABLE freight_routes 
    ADD CONSTRAINT fk_freight_routes_partner 
    FOREIGN KEY (partner_id) 
    REFERENCES logistics_partners(partner_id) 
    ON DELETE RESTRICT;

-- 5. Буферная таблица и мгновенная очистка со сбросом счетчика
CREATE TABLE IF NOT EXISTS buffer_delivery (
    packet_id BIGSERIAL PRIMARY KEY,
    raw_payload TEXT NOT NULL,
    received_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

TRUNCATE TABLE buffer_delivery RESTART IDENTITY;

-- 6. Безопасное удаление устаревших артефактов
DROP TABLE IF EXISTS legacy_freight_archive CASCADE;
```

## 5. Классификатор студенческих ошибок и штрафные вычеты

| Код ошибки | Описание выявленной ошибки студента | Штрафной вычет |
| :---: | :--- | :---: |
| **ERR-01** | **Синтаксический сбой DDL:** грубая ошибка в ключевых словах `ALTER TABLE`, пропуск запятых или некорректный порядок параметров. | **-1.0 балл** |
| **ERR-02** | **Отсутствие USING при смене типа:** попытка выполнить `ALTER COLUMN ... TYPE` с несовместимым типом без выражения `USING`, приводящая к фатальной ошибке СУБД. | **-0.5 балла** |
| **ERR-03** | **Безымянные ограничения:** добавление `CHECK`, `UNIQUE` или `FOREIGN KEY` без конструкции `CONSTRAINT <name>`, затрудняющее дальнейшую поддержку схемы. | **-0.5 балла** |
| **ERR-04** | **Непонимание CASCADE / RESTRICT:** неверная трактовка поведения связей при удалении родительской таблицы, либо путаница между удалением схемы и данных. | **-0.5 балла** |
| **ERR-05** | **Игнорирование RESTART IDENTITY:** выполнение `TRUNCATE TABLE` без указания `RESTART IDENTITY`, что приводит к продолжению нумерации счетчика автоинкремента. | **-0.5 балла** |
| **ERR-06** | **Отсутствие DEFAULT при добавлении NOT NULL:** попытка добавить столбец с ограничением `NOT NULL` без указания `DEFAULT` на существующей таблице с данными. | **-0.5 балла** |
| **ERR-07** | **Непонимание AccessExclusiveLock:** неспособность объяснить, почему изменение структуры таблицы блокирует операции чтения `SELECT` и записи в production. | **-0.5 балла** |
| **ERR-08** | **Пропуск контрольных вопросов самопроверки:** не заполнен аналитический блок рабочего листа. | **-0.5 балла** |
