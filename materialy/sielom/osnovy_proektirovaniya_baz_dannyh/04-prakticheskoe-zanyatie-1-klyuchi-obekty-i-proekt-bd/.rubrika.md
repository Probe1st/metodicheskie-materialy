### 3. Эталонные решения практических заданий (`zanyatie.html`)

#### Вариант 1: Проект БД «Учет автопарка логистической компании»
1. **Перечень и структура таблиц:**
   - Таблица `avtomobili` (Автомобили компании):
     - `id_avto INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` (или `SERIAL PRIMARY KEY`) — суррогатный идентификатор.
     - `gos_nomer VARCHAR(12) NOT NULL UNIQUE` — государственный регистрационный номер (естественный альтернативный ключ).
     - `vin VARCHAR(17) NOT NULL UNIQUE` — идентификационный номер VIN (17 символов, стандарт ISO 3779).
     - `marka_model VARCHAR(100) NOT NULL` — марка и модель ТС.
     - `god_vypuska SMALLINT NOT NULL CHECK (god_vypuska >= 1990 AND god_vypuska <= EXTRACT(YEAR FROM CURRENT_DATE) + 1)`
     - `tekushchiy_probeg INT NOT NULL DEFAULT 0 CHECK (tekushchiy_probeg >= 0)`
     - `is_aktivnyy BOOLEAN NOT NULL DEFAULT TRUE`
   - Таблица `voditeli` (Водительский состав):
     - `id_voditelya INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
     - `nomer_udostovereniya VARCHAR(20) NOT NULL UNIQUE` — серия и номер ВУ.
     - `familiya VARCHAR(50) NOT NULL`
     - `imya VARCHAR(50) NOT NULL`
     - `otchestvo VARCHAR(50)`
     - `kategoriya_prav VARCHAR(10) NOT NULL`
     - `stazh_let SMALLINT NOT NULL DEFAULT 0 CHECK (stazh_let >= 0)`
     - `telefon VARCHAR(20) NOT NULL UNIQUE`
     - `is_v_shtate BOOLEAN NOT NULL DEFAULT TRUE`
   - Таблица `putevye_listy` (Учет рейсов и путевых листов):
     - `id_putevogo_lista BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
     - `nomer_dokumenta VARCHAR(30) NOT NULL UNIQUE`
     - `id_avto INT NOT NULL REFERENCES avtomobili(id_avto) ON UPDATE CASCADE ON DELETE RESTRICT`
     - `id_voditelya INT NOT NULL REFERENCES voditeli(id_voditelya) ON UPDATE CASCADE ON DELETE RESTRICT`
     - `data_vyezda TIMESTAMP NOT NULL`
     - `data_vozvrashcheniya TIMESTAMP`
     - `probeg_pri_vyezde INT NOT NULL CHECK (probeg_pri_vyezde >= 0)`
     - `probeg_pri_vozvrashchenii INT CHECK (probeg_pri_vozvrashchenii >= probeg_pri_vyezde)`
     - `toplivo_pri_vyezde NUMERIC(6,2) NOT NULL CHECK (toplivo_pri_vyezde >= 0)`
     - `toplivo_pri_vozvrashchenii NUMERIC(6,2) CHECK (toplivo_pri_vozvrashchenii >= 0)`
     - `toplivo_zapravleno NUMERIC(6,2) NOT NULL DEFAULT 0.00 CHECK (toplivo_zapravleno >= 0)`
     - `rashod_topliva NUMERIC(6,2) GENERATED ALWAYS AS (toplivo_pri_vyezde + toplivo_zapravleno - toplivo_pri_vozvrashchenii) STORED`
2. **Обоснование ключей и ссылочной целостности:**
   - *Почему для `avtomobili` выбран суррогатный ключ `id_avto`, а не госномер или VIN:*
     Госномер ТС может измениться при смене региона, перерегистрации автопарка или получении дубликата. VIN-номер состоит из 17 символов и занимает в индексах внешних ключей в 4 раза больше памяти, чем целочисленный 4-байтовый `INTEGER`. Суррогатный автоинкрементный `id_avto` неизменяем (immutable), обеспечивает минимальный размер B-Tree индексов и ускоряет операцию соединения таблиц (`JOIN`). При этом на `gos_nomer` и `vin` обязательно накладывается ограничение `UNIQUE`.
   - *Каскадные действия:*
     Для внешних ключей `id_avto` и `id_voditelya` установлено `ON DELETE RESTRICT` (или `NO ACTION`), поскольку физическое удаление автомобиля или уволенного водителя из системы недопустимо, если в архиве существуют связанные с ними финансовые и путевые документы (нарушение юридической отчетности). Для деактивации используется мягкое логическое удаление (`is_aktivnyy = FALSE`). При этом `ON UPDATE CASCADE` позволяет синхронизировать идентификатор при технологической миграции данных.
3. **Ограничения целостности (CHECK и бизнес-логика):**
   - `CHECK (probeg_pri_vozvrashchenii >= probeg_pri_vyezde)` — исключает физически невозможный отрицательный пробег за рейс.
   - `CHECK (data_vozvrashcheniya IS NULL OR data_vozvrashcheniya >= data_vyezda)` — гарантирует временную последовательность.
   - `CHECK (toplivo_pri_vyezde + toplivo_zapravleno >= toplivo_pri_vozvrashchenii)` — объем оставшегося топлива не может превышать суммарно имевшееся и заправленное.

#### Вариант 2: Проект БД «Гостиничный комплекс»
1. **Перечень и структура таблиц:**
   - Таблица `kategorii_nomerov` (Справочник категорий):
     - `id_kategorii SMALLINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
     - `nazvanie VARCHAR(50) NOT NULL UNIQUE` (Стандарт, Люкс, Делюкс, Апартаменты)
     - `vmestimost_mest SMALLINT NOT NULL CHECK (vmestimost_mest BETWEEN 1 AND 10)`
     - `bazovaya_cena_za_sutki NUMERIC(10,2) NOT NULL CHECK (bazovaya_cena_za_sutki > 0)`
   - Таблица `nomera` (Номерной фонд):
     - `id_nomera INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
     - `nomer_komnaty VARCHAR(10) NOT NULL UNIQUE`
     - `etazh SMALLINT NOT NULL CHECK (etazh BETWEEN 1 AND 50)`
     - `id_kategorii SMALLINT NOT NULL REFERENCES kategorii_nomerov(id_kategorii) ON UPDATE CASCADE ON DELETE RESTRICT`
     - `status VARCHAR(20) NOT NULL DEFAULT 'доступен' CHECK (status IN ('доступен', 'занят', 'уборка', 'ремонт'))`
   - Таблица `gosti` (Анкеты проживающих):
     - `id_gostya INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
     - `pasport_seriya_nomer VARCHAR(30) NOT NULL UNIQUE`
     - `familiya VARCHAR(50) NOT NULL`
     - `imya VARCHAR(50) NOT NULL`
     - `otchestvo VARCHAR(50)`
     - `telefon VARCHAR(20) NOT NULL`
     - `email VARCHAR(100)`
     - `data_rozhdeniya DATE NOT NULL CHECK (data_rozhdeniya <= CURRENT_DATE - INTERVAL '18 years')`
   - Таблица `bronirovaniya` (Журнал бронирования и проживания):
     - `id_broni BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
     - `id_nomera INT NOT NULL REFERENCES nomera(id_nomera) ON UPDATE CASCADE ON DELETE RESTRICT`
     - `id_gostya INT NOT NULL REFERENCES gosti(id_gostya) ON UPDATE CASCADE ON DELETE RESTRICT`
     - `data_zaezda DATE NOT NULL`
     - `data_vyezda DATE NOT NULL`
     - `itogovaya_stoimost NUMERIC(10,2) NOT NULL CHECK (itogovaya_stoimost >= 0)`
     - `status_broni VARCHAR(20) NOT NULL DEFAULT 'создано' CHECK (status_broni IN ('создано', 'подтверждено', 'заселен', 'завершено', 'отменено'))`
     - `sozdano_v TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`
     - `CONSTRAINT chk_dates CHECK (data_vyezda > data_zaezda)`
2. **Обоснование ключей и ссылочной целостности:**
   - *Составной ключ `(id_nomera, data_zaezda)` vs Суррогатный `id_broni`:*
     Хотя теоретически пара `(id_nomera, data_zaezda)` могла бы идентифицировать бронь при запрете заселения двух гостей в один день, на практике составной естественный ключ создает огромные проблемы:
     1. При изменении дат проживания (продлении) первичный ключ пришлось бы обновлять, что нарушает неизменность идентификатора.
     2. Если на бронирование оформляются платежные транзакции или счета в дочерних таблицах (`platezhi_po_broni`), использование составного ключа из нескольких полей раздувает внешний ключ дочерних таблиц и усложняет запросы.
     Поэтому безусловным эталоном является суррогатный `BIGSERIAL id_broni`, а запрет наложения броней решается логикой приложения или исключением `EXCLUDE USING gist (id_nomera WITH =, daterange(data_zaezda, data_vyezda) WITH &&)`.
   - *Каскадные действия:*
     Категории номеров защищены `ON DELETE RESTRICT`, так как нельзя удалить категорию, если в ней числятся реальные номера. Удаление номера или гостя при наличии броней также блокируется `ON DELETE RESTRICT`.
3. **Ограничения целостности:**
   - `CHECK (data_vyezda > data_zaezda)` — дата выезда строго позже даты заезда (минимальное проживание — 1 сутки).
   - `CHECK (data_rozhdeniya <= CURRENT_DATE - INTERVAL '18 years')` — бронирование допускается только совершеннолетними лицами.

#### Вариант 3: Проект БД «Электронная библиотека»
1. **Перечень и структура таблиц:**
   - Таблица `knigi` (Библиографическое описание произведений):
     - `id_knigi INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
     - `isbn VARCHAR(20) NOT NULL UNIQUE` — международный стандартный книжный номер (естественный ключ издания).
     - `nazvanie VARCHAR(255) NOT NULL`
     - `avtory VARCHAR(255) NOT NULL`
     - `god_izdaniya SMALLINT NOT NULL CHECK (god_izdaniya BETWEEN 1500 AND EXTRACT(YEAR FROM CURRENT_DATE))`
     - `izdatelstvo VARCHAR(100)`
     - `kolichestvo_stranic INT CHECK (kolichestvo_stranic > 0)`
   - Таблица `ekzemplyary` (Физические единицы хранения):
     - `id_ekzemplyara INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
     - `inventarnyy_nomer VARCHAR(30) NOT NULL UNIQUE` — уникальный инвентарный штрихкод конкретной книги на полке.
     - `id_knigi INT NOT NULL REFERENCES knigi(id_knigi) ON UPDATE CASCADE ON DELETE RESTRICT`
     - `status VARCHAR(20) NOT NULL DEFAULT 'в_фонде' CHECK (status IN ('в_фонде', 'на_руках', 'в_реставрации', 'списан'))`
     - `mesto_hraneniya VARCHAR(50) NOT NULL` (зал, стеллаж, полка)
   - Таблица `chitateli` (Читательские билеты):
     - `id_chitatelya INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
     - `nomer_chit_bileta VARCHAR(20) NOT NULL UNIQUE`
     - `familiya VARCHAR(50) NOT NULL`
     - `imya VARCHAR(50) NOT NULL`
     - `telefon VARCHAR(20) NOT NULL`
     - `data_registracii DATE NOT NULL DEFAULT CURRENT_DATE`
     - `status_kartochki VARCHAR(20) NOT NULL DEFAULT 'активен' CHECK (status_kartochki IN ('активен', 'заблокирован'))`
   - Таблица `vydachi` (Журнал книговыдачи):
     - `id_vydachi BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
     - `id_ekzemplyara INT NOT NULL REFERENCES ekzemplyary(id_ekzemplyara) ON UPDATE CASCADE ON DELETE RESTRICT`
     - `id_chitatelya INT NOT NULL REFERENCES chitateli(id_chitatelya) ON UPDATE CASCADE ON DELETE RESTRICT`
     - `data_vydachi DATE NOT NULL DEFAULT CURRENT_DATE`
     - `srok_vozvrata DATE NOT NULL`
     - `fakticheskaya_data_vozvrata DATE`
     - `sostoyanie_pri_voz狡ate VARCHAR(100)`
     - `CONSTRAINT chk_srok CHECK (srok_vozvrata >= data_vydachi)`,
     - `CONSTRAINT chk_fakt CHECK (fakticheskaya_data_vozvrata IS NULL OR fakticheskaya_data_vozvrata >= data_vydachi)`
2. **Обоснование ключей и ссылочной целостности:**
   - *Естественный ключ ISBN vs Инвентарный номер экземпляра:*
     ISBN описывает типографское издание в целом (одно название, один тираж). В библиотеке может храниться 20 физических копий («Война и мир»), имеющих абсолютно одинаковый ISBN. Поэтому ISBN не может идентифицировать конкретный том, который берет читатель домой. Для физических единиц вводится сущность `ekzemplyary` с уникальным инвентарным номером `inventarnyy_nomer`. В журнал `vydachi` передается внешний ключ именно физического экземпляра `id_ekzemplyara`, а не книги.
   - *Каскадное удаление:*
     Удаление книг и читателей блокируется (`RESTRICT`), пока есть записи в истории выдачи. При списании ветхого тома экземпляр не удаляется физически (`DELETE`), а переводится в статус `'списан'`.
3. **Ограничения целостности:**
   - `CHECK (srok_vozvrata >= data_vydachi)` — нормативный срок возврата не может предшествовать дню выдачи книги.
   - `CHECK (fakticheskaya_data_vozvrata >= data_vydachi)` — фактический возврат не может произойти в прошлом до выдачи.

#### Вариант 4: Проект БД «Сервисный центр по ремонту электроники»
1. **Перечень и структура таблиц:**
   - Таблица `klienty` (Физические и юридические лица):
     - `id_klienta INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
     - `familiya_ili_kompaniya VARCHAR(100) NOT NULL`
     - `telefon VARCHAR(20) NOT NULL UNIQUE`
     - `email VARCHAR(100)`
     - `sozdan_v TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`
   - Таблица `mastera` (Сервисные инженеры):
     - `id_mastera INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
     - `fio VARCHAR(100) NOT NULL`
     - `specializaciya VARCHAR(100) NOT NULL` (пайка BGA, модульный ремонт, восстановление данных)
     - `kvalifikaciya VARCHAR(30) NOT NULL DEFAULT 'инженер'`
     - `is_dostupen BOOLEAN NOT NULL DEFAULT TRUE`
   - Таблица `komplektuyushchie` (Склад запасных частей):
     - `id_detali INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
     - `artikul VARCHAR(50) NOT NULL UNIQUE`
     - `nazvanie VARCHAR(150) NOT NULL`
     - `kolichestvo_na_sklade INT NOT NULL DEFAULT 0 CHECK (kolichestvo_na_sklade >= 0)`
     - `cena_zakupki NUMERIC(10,2) NOT NULL CHECK (cena_zakupki >= 0)`
     - `cena_prodazhi NUMERIC(10,2) NOT NULL CHECK (cena_prodazhi >= cena_zakupki)`
   - Таблица `zakazy` (Квитанции на ремонт):
     - `id_zakaza BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
     - `nomer_kvitancii VARCHAR(30) NOT NULL UNIQUE`
     - `id_klienta INT NOT NULL REFERENCES klienty(id_klienta) ON UPDATE CASCADE ON DELETE RESTRICT`
     - `id_mastera INT REFERENCES mastera(id_mastera) ON UPDATE CASCADE ON DELETE SET NULL`
     - `tip_ustroystva VARCHAR(50) NOT NULL` (смартфон, ноутбук, планшет)
     - `model_seriynyy_nomer VARCHAR(100) NOT NULL`
     - `zayavlennaya_neispravnost TEXT NOT NULL`
     - `status_zakaza VARCHAR(25) NOT NULL DEFAULT 'принят' CHECK (status_zakaza IN ('принят', 'диагностика', 'согласование', 'в_работе', 'готов_к_выдаче', 'выдан', 'отказ'))`
     - `predvaritelnaya_stoimost NUMERIC(10,2) CHECK (predvaritelnaya_stoimost >= 0)`
     - `itogovaya_stoimost NUMERIC(10,2) CHECK (itogovaya_stoimost >= 0)`
     - `data_priema TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`
     - `data_vydachi TIMESTAMP`
     - `CONSTRAINT chk_vydacha CHECK (data_vydachi IS NULL OR data_vydachi >= data_priema)`
   - Таблица `ispolzovannye_detali` (Списание запчастей в наряд):
     - `id_pozicii BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
     - `id_zakaza BIGINT NOT NULL REFERENCES zakazy(id_zakaza) ON UPDATE CASCADE ON DELETE CASCADE`
     - `id_detali INT NOT NULL REFERENCES komplektuyushchie(id_detali) ON UPDATE CASCADE ON DELETE RESTRICT`
     - `kolichestvo INT NOT NULL DEFAULT 1 CHECK (kolichestvo > 0)`
     - `cena_v_zakaze NUMERIC(10,2) NOT NULL CHECK (cena_v_zakaze >= 0)`
2. **Обоснование ключей и ссылочной целостности:**
   - *Каскадное удаление `CASCADE` vs Запрет `RESTRICT` vs `SET NULL`:*
     - `klienty -> zakazy`: строго `ON DELETE RESTRICT`. Нельзя удалить клиента, пока в базе хранятся договоры и гарантийные квитанции на технику.
     - `mastera -> zakazy`: оптимально `ON DELETE SET NULL`. Если мастер уволился и его профиль удаляется/архивируется, выполненный 2 года назад заказ не должен стираться; поле `id_mastera` зануляется или переназначается.
     - `zakazy -> ispolzovannye_detali`: допустимо `ON DELETE CASCADE`. Строки расхода деталей являются зависимой подчиненной спецификацией квитанции: если черновой заказ аннулируется и удаляется, удаляются и строки его спецификации.
     - `komplektuyushchie -> ispolzovannye_detali`: строго `ON DELETE RESTRICT`. Нельзя удалить артикул детали из номенклатуры, если она была списана в выполненных ремонтах.
3. **Ограничения целостности:**
   - `CHECK (status_zakaza IN (...))` — гарантирует конечность множества допустимых состояний жизненного цикла ремонта.
   - `CHECK (cena_prodazhi >= cena_zakupki)` — защищает от убыточной реализации комплектующих.
   - `CHECK (data_vydachi >= data_priema)` — хронологическая состоятельность.

### 4. Типичные ошибки студентов и педагогические приемы коррекции

1. **Ошибка «Универсальный VARCHAR»:**
   - *Проявление:* Студент задает `VARCHAR(255)` для всех полей: даты, пробег, цены, логические флаги ('true'/'false').
   - *Педагогический прием:* Задать вопрос: «Как СУБД отсортирует строки '100', '20', '5'? Число 100 окажется меньше 20! А как сложить два текстовых поля с ценами без потери производительности?».
2. **Ошибка «Плавающая точка для денег»:**
   - *Проявление:* Использование `REAL`, `FLOAT`, `DOUBLE PRECISION` для денежных сумм.
   - *Педагогический прием:* Продемонстрировать арифметику стандарта IEEE 754: $0.1 + 0.2 = 0.30000000000000004$. Объяснить, почему банки и бухгалтерия используют только `NUMERIC(p,s)` с фиксированной точностью.
3. **Ошибка «Все каскадом» (Blind CASCADE):**
   - *Проявление:* Навешивание `ON DELETE CASCADE` на все внешние ключи.
   - *Педагогический прием:* Спросить: «Что произойдет, если директор автопарка нажмет кнопку Удалить марку автомобиля? Удалятся все 200 машин, все 50 000 путевых листов и вся финансовая отчетность за 5 лет!».
4. **Ошибка «Суррогатный ключ как панацея без UNIQUE»:**
   - *Проявление:* Ввели `id INT PRIMARY KEY`, но забыли повесить `UNIQUE` на паспорт, VIN, email или инвентарный номер.
   - *Педагогический прием:* Показать, что система позволит зарегистрировать двух разных людей с одинаковым паспортом или две одинаковые машины, что приведет к разрушению бизнес-логики.
