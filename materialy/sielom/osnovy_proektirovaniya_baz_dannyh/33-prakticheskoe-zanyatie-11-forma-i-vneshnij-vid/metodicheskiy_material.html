1. Концепция занятия и дидактические цели

Практическое занятие №11 посвящено важнейшему звену прикладной разработки баз данных — трансформации необработанных реляционных кортежей в человеко-читаемые экранные формы и регламентные отчеты. В реальных информационных системах (ERP, CRM, медицинских и банковских АРМ) оператор взаимодействует не с сырыми данными типов NUMERIC или TIMESTAMPTZ, а с отформатированными карточками, таблицами DataGrid и сводками.

Ключевая дидактическая цель: Научить студентов инструментам СУБД, отвечающим за эстетику, читаемость, логическую валидацию и производительность экранных интерфейсов:

  • Форматирование числовых, валютных и финансовых значений с разделением групп разрядов, денежными префиксами/суффиксами и фиксированной точностью через TO_CHAR.
  • Преобразование временных меток и дат в канонические локализованные форматы (DD.MM.YYYY HH24:MI, вывод дня недели и локализованных названий месяцев).
  • Построение вычисляемых и условных столбцов с помощью стандартизированного SQL-выражения CASE WHEN... THEN... ELSE... END для визуального цветового кодирования и категоризации (бейджи статусов, уровни критичности, градация стипендий).
  • Проектирование безопасной и масштабируемой постраничной навигации в таблицах DataGrid: архитектурный выбор между OFFSET / LIMIT и курсорной/ключевой пагинацией (Keyset pagination).
  • Эргономика вычисляемых колонок: агрегация ФИО с инициалами (Фамилия И.О.), расчет длительности периодов и финансовых итогов прямо в выборке.

3. Методология форматирования данных и SQL-шаблоны

3.1. Форматирование числовых и финансовых данных (TO_CHAR)

Стандартный числовой тип NUMERIC(15, 2) при выводе через чистый SELECT формирует неразрывную строку цифр (12500450.70), что крайне затрудняет восприятие больших сумм оператором-бухгалтером. Функция TO_CHAR(значение, шаблон) решает эту задачу:

-- Преобразование числа с разделителем групп разрядов и фиксированной дробной частью
SELECT 
 sum_raw,
 TRIM(TO_CHAR(sum_raw, 'FM999G999G999D00')) | ' руб.' AS formatted_currency
FROM invoices;

-- Где модификаторы означают:
-- FM (Fill Mode) — подавляет лидирующие и концевые пробелы, которые PostgreSQL резервирует под знак;
-- 9 — знакоместо цифры (выводится только при наличии);
-- G — разделитель групп разрядов (тысяч) в соответствии с текущей локалью (или пробел);
-- D — десятичный разделитель (запятая/точка по локали);
-- 0 — обязательный разряд (даже если ноль, выводит 0).

3.2. Форматирование дат и временных меток

Отображение меток времени в российских учетных системах строго регламентировано стандартами ГОСТ (день.месяц.год часы:минуты). Преобразование из типа TIMESTAMP / TIMESTAMPTZ выполняется шаблоном:

SELECT 
 created_at,
 TO_CHAR(created_at, 'DD.MM.YYYY HH24:MI') AS ru_datetime,
 TO_CHAR(created_at, 'TMDy, DD TMMonth YYYY') AS ru_human_date
FROM patient_records;

Модификатор TM (Translation Mode) позволяет получать локализованные названия дней недели и месяцев при соответствующей настройке lc_time.

3.3. Логическая условная стилизация строк (CASE WHEN)

Выражение CASE — мощнейший декларативный механизм, позволяющий реализовать логику ветвления прямо в проекции SQL. В интерфейсах СУБД CASE используется для:

  1. Преобразования технических кодов в читаемые бейджи: замена целочисленных статусов (0, 1, 2) на понятные строковые маркеры ('В обработке', 'В пути', 'Доставлен').
  2. Вычисления CSS-классов или цветовых индикаторов: генерация служебной колонки для визуализатора интерфейса (badge-success, badge-danger).
  3. Расчета динамических показателей: начисление стипендий, расчет пени или скидок.
SELECT 
 order_id,
 total_amount,
 status_code,
 CASE status_code
 WHEN 'D' THEN 'Доставлен'
 WHEN 'S' THEN 'В пути'
 WHEN 'C' THEN 'Отменен'
 ELSE 'Черновик'
 END AS status_text,
 CASE 
 WHEN status_code = 'D' THEN 'badge-success'
 WHEN status_code = 'S' THEN 'badge-warning'
 WHEN status_code = 'C' THEN 'badge-danger'
 ELSE 'badge-secondary'
 END AS status_badge_class
FROM customer_orders;

3.4. Архитектура постраничной навигации в таблицах DataGrid

Эргономичная экранная форма обязана порционировать выборку. Преподавателю необходимо разобрать со студентами два фундаментальных подхода:

Параметр OFFSET / LIMIT (Классический) Keyset pagination (Курсорный / По ключу)
Синтаксис SELECT... LIMIT 25 OFFSET 50; SELECT... WHERE id > 50 ORDER BY id LIMIT 25;
Принцип работы СУБД считывает 75 строк с диска/буфера, отбрасывает 50 первых и отдает 25. СУБД выполняет мгновенный спуск по B-Tree индексу к ключу id = 51 и считывает 25 строк.
Сложность (OFFSET + LIMIT)$ — резкая деградация на глубоких страницах. (\log N + LIMIT)$ — стабильно быстро при любых объемах данных.
Поведение при вставках Возникает сдвиг строк (строка может продублироваться на следующей странице). Стабильная выборка без дубликатов и пропусков.
Область применения Админ-панели с малым числом страниц и прямым переходом на страницу N. Высоконагруженные ленты, бесконечный скролл, мобильные клиенты.

4. Типовые ошибки студентов и педагогические приемы

Типовая ошибка студента Техническая причина и последствия Педагогический прием и контрмера
Пропуск модификатора FM в TO_CHAR В строке перед числом появляется лишний лидирующий пробел: ' 125 000.00' вместо '125 000.00'. При конкатенации строки смещаются. Показать через LENGTH(TO_CHAR(...)), что СУБД резервирует 1 байт под потенциальный знак минус. Объяснить назначение FM (Fill Mode).
Забытый блок ELSE в CASE Если значение не попало ни под одну ветку WHEN, выражение вернет NULL, разрушив строковую форму отчета или упав в UI. Привить студентам инженерное правило: каждое выражение CASE обязано завершаться защитным ELSE (дефолтное состояние).
Сортировка по отформатированной строке Студент делает ORDER BY formatted_sum. Строка '100 000' оказывается раньше '20 000' по лексикографическому порядку. Показать разницу между строковой и числовой сортировкой. Напомнить, что сортировка в ORDER BY должна выполняться по исходному сырому полю или алиасу до форматирования.
Использование OFFSET на миллионных таблицах Запрос OFFSET 1000000 LIMIT 20 уходит в глубокий I/O deadlock или работает секунды. Демонстрация EXPLAIN ANALYZE в терминале: показать, сколько кортежей вынуждена прочитать СУБД при классическом смещении.

5. Дифференцированные практические сценарии

В рабочем листе zanyatie.html реализованы 4 производственных кейса, покрывающих ключевые предметные области:

  • Вариант 1: Бухгалтерский финансовый отчет — агрегация оборотов дебиторской задолженности, форматирование денежных сумм (999 999 999.00 руб.), индикатор риска должников через CASE WHEN debt > 100000 THEN 'Критический' ELSE 'Норма' END, организация пагинации по 25 строк.
  • Вариант 2: Больничный реестр госпитализаций — преобразование временных меток в стандарт ГОСТ (DD.MM.YYYY HH24:MI), вычисление койко-дней через разницу дат, цветовая маркировка степени тяжести больного.
  • Вариант 3: Мониторинг заказов маркетплейса — генерация красивых бейджей статуса ('Доставлен' [зеленый], 'В пути' [желтый], 'Отменен' [красный]), стандартизация телефонных номеров и маскирование трек-номеров.
  • Вариант 4: Ведомость успеваемости деканата — конкатенация фамилии и инициалов (Иванов И.И.), расчет вычисляемого поля стипендии через поисковый CASE по среднему баллу, сортировка по ранжиру.
