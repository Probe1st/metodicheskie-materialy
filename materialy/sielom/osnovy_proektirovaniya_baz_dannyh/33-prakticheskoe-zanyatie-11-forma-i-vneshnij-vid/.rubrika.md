# Закрытая критериальная рубрика преподавателя: Практическое занятие №11 — Форма и внешний вид

Данный документ представляет собой закрытый методический инструмент преподавателя дисциплины «ОП.08 Основы проектирования баз данных» (СИЭУиП) и содержит критериальную шкалу оценивания, полные эталонные решения для всех 4 практических вариантов рабочего листа `zanyatie.html`, эталон резервного домашнего задания `domashnee_zadanie.html` и классификатор типовых студенческих ошибок со шкалой штрафных вычетов.

## 1. Паспорт оценивания занятия

- **Дисциплина:** ОП.08 Основы проектирования баз данных.
- **Тематический раздел:** Тема 5. Организация запросов SQL (§2.2 с.7–8 программы).
- **Тема занятия:** Практическое занятие №11: форма и внешний вид (Занятие №33).
- **Вид занятия:** Практическое занятие (2 академических часа: 80 минут основной регламент / 60 минут сокращенный).
- **Форма контроля:** Проверка индивидуального проектного продукта в интерактивном рабочем листе `zanyatie.html` (4 дифференцированных варианта) либо в резервном задании `domashnee_zadanie.html`.
- **Критериальная шкала:** 4-балльная шкала (форматирование полей TO_CHAR — 2 б., условная логика CASE и пагинация — 1 б., эргономика формы и самопроверка — 1 б.):
  * **Часть 1. Форматирование числовых, валютных и календарных полей (TO_CHAR):** **2 балла** (1 балл при пропуске модификатора FM, мелких ошибках в маске разделителей; 0 баллов при нерабочем запросе или отсутствии форматирования).
  * **Часть 2. Условная логика (CASE WHEN) и пагинация (OFFSET/LIMIT / Keyset):** **1 балл** (0.5 балла при отсутствии обязательного блока ELSE или неоптимальной пагинации; 0 баллов при синтаксическом сломе конструкции).
  * **Часть 3. Эргономика экранной формы, валидация полей и самопроверка:** **1 балл** (0.5 балла при неполном теоретическом обосновании; 0 баллов при отсутствии ответа или ошибочном суждении).
- **Итоговая оценка:**
  * **4 балла** — «Отлично» (запросы полностью рабочие, соблюдены стандарты ГОСТ, применен FM, ветка ELSE обязательна, теоретическое обоснование аргументировано);
  * **3 балла** — «Хорошо» (запросы верны, но допущены мелкие недочеты: пропущен FM, не учтены лидирующие пробелы);
  * **2 балла** — «Удовлетворительно» (выполнены только базовые выборки, условная логика CASE не завершена, ошибки в пагинации);
  * **0–1 балл** — «Не зачтено» (грубые ошибки синтаксиса, работа не сдана или списана).

## 3. Эталоны решений рабочего листа `zanyatie.html`

### Вариант 1: Финансовый отчет бухгалтерии

#### Задание 1.1: Проектирование SQL-запроса отчета (TO_CHAR + CASE)
```sql
SELECT 
  client_id,
  company_name,
  contract_code,
  TO_CHAR(last_payment_date, 'DD.MM.YYYY') AS formatted_payment_date,
  TRIM(TO_CHAR(outstanding_debt, 'FM999G999G999D00')) || ' руб.' AS formatted_debt,
  CASE 
    WHEN outstanding_debt > 100000.00 THEN 'Критический'
    ELSE 'Норма'
  END AS debt_status
FROM accounting_receivables;
```

#### Задание 1.2: Организация пагинации и сортировки
```sql
-- Вторая страница реестра (порция 25 строк)
ORDER BY outstanding_debt DESC
LIMIT 25 OFFSET 25;
```

#### Задание 1.3: Аналитический вывод
**Эталонный ответ:**
Сортировка по отформатированному текстовому столбцу выполняется лексикографически (посимвольно по кодам ASCII), а не по числовому значению. В результате строка `'100 000.00 руб.'` окажется раньше строки `'20 000.00 руб.'`, а строка `'9 000.00 руб.'` встанет выше, чем `'120 000.00 руб.'`. Кроме того, текстовая колонка не может использовать B-Tree индекс по числовому полю `outstanding_debt`, что приводит к тяжелому последовательному сканированию таблицы (Seq Scan) и внешней сортировке на диске.

### Вариант 2: Реестр госпитализаций больницы

#### Задание 2.1: Проектирование SQL-запроса журнала (TO_CHAR + CASE)
```sql
SELECT 
  stay_id,
  patient_name,
  TO_CHAR(admission_timestamp, 'DD.MM.YYYY HH24:MI') AS ru_admission_time,
  (COALESCE(discharge_date, CURRENT_DATE) - admission_timestamp::date) AS bed_days_count,
  CASE severity_level
    WHEN 3 THEN 'Тяжелое (ОИТР)'
    WHEN 2 THEN 'Средней тяжести'
    ELSE 'Удовлетворительное'
  END AS severity_status
FROM hospital_stays;
```

#### Задание 2.2: Организация курсорной навигации (Keyset Pagination)
```sql
-- Выборка следующих 20 пациентов после stay_id = 1420
WHERE stay_id > 1420
ORDER BY stay_id ASC
LIMIT 20;
```

#### Задание 2.3: Самопроверка и защита от NULL
**Эталонный ответ:**
Пока пациент находится на лечении в стационаре, дата его выписки `discharge_date` имеет значение `NULL`. В реляционной алгебре любая арифметическая операция со значением NULL возвращает NULL (`NULL - date = NULL`). Функция `COALESCE(discharge_date, CURRENT_DATE)` заменяет неопределенное значение текущей календарной датой, что позволяет динамически и корректно рассчитать фактическое количество проведенных в стационаре суток на момент формирования отчета.

### Вариант 3: Мониторинг заказов интернет-магазина

#### Задание 3.1: Проектирование SQL-запроса мониторинга (TO_CHAR + CASE)
```sql
SELECT 
  'TRK-' || LPAD(order_id::text, 8, '0') AS formatted_tracking_no,
  customer_phone,
  TO_CHAR(order_created_at, 'DD.MM.YYYY HH24:MI') AS created_display,
  TRIM(TO_CHAR(total_cost, 'FM999G999D00')) || ' руб.' AS formatted_cost,
  CASE order_status
    WHEN 'D' THEN 'Доставлен'
    WHEN 'S' THEN 'В пути'
    WHEN 'C' THEN 'Отменен'
    ELSE 'Новый'
  END AS status_title,
  CASE order_status
    WHEN 'D' THEN 'badge-green'
    WHEN 'S' THEN 'badge-yellow'
    WHEN 'C' THEN 'badge-red'
    ELSE 'badge-gray'
  END AS ui_badge_class
FROM ecommerce_orders;
```

#### Задание 3.2: Порционирование и фильтрация
```sql
ORDER BY order_created_at DESC
LIMIT 30 OFFSET 0;
```

#### Задание 3.3: Аналитический вывод
**Эталонный ответ:**
Если в конструкции `CASE` опустить защитную секцию `ELSE`, то при появлении любого непредусмотренного статуса (например, новый статус `'R'` — возврат, или ошибочный ввод) выражение молча возвратит значение `NULL`. В веб-интерфейсе это приведет либо к пустой ячейке таблицы, либо к возникновению критической ошибки JavaScript при попытке манипулировать свойствами `null`, что разрушит пользовательский интерфейс.

### Вариант 4: Ведомость успеваемости учебной группы

#### Задание 4.1: Проектирование SQL-запроса ведомости (TO_CHAR + CASE)
```sql
SELECT 
  student_id,
  last_name || ' ' || LEFT(first_name, 1) || '.' || LEFT(patronymic, 1) || '.' AS short_fio,
  TO_CHAR(avg_score, 'FM9D00') AS score_display,
  CASE 
    WHEN avg_score >= 4.75 THEN 'Повышенная (10 000 руб.)'
    WHEN avg_score >= 4.00 THEN 'Академическая (4 500 руб.)'
    ELSE 'Не начисляется'
  END AS scholarship_type
FROM student_grades;
```

#### Задание 4.2: Ранжирование и постраничный вывод
```sql
ORDER BY avg_score DESC, last_name ASC
LIMIT 25 OFFSET 0;
```

#### Задание 4.3: Самопроверка и последовательность условий
**Эталонный ответ:**
Поисковое выражение `CASE` вычисляет условия строго последовательно сверху вниз до первого совпадения. Если поставить условие `avg_score >= 4.00` первым, то студент с баллом `4.90` выполнит это первое условие и получит `'Академическая (4 500 руб.)'`, а ветка с повышенной стипендией станет недостижимым «мертвым кодом». Поэтому диапазоны обязаны упорядочиваться от более строгих к менее строгим (по убыванию порога).

## 4. Эталон резервного домашнего задания `domashnee_zadanie.html`

```sql
SELECT 
  '#SH-' || LPAD(shipment_id::text, 8, '0') AS formatted_shipment_no,
  driver_fio,
  TO_CHAR(departure_time, 'DD.MM.YYYY HH24:MI') AS ru_departure_date,
  TRIM(TO_CHAR(contract_price, 'FM999G999G999D00')) || ' руб.' AS formatted_price,
  TRIM(TO_CHAR(contract_price - COALESCE(advance_paid, 0), 'FM999G999G999D00')) || ' руб.' AS formatted_balance,
  CASE delivery_status
    WHEN 'D' THEN 'Доставлен'
    WHEN 'T' THEN 'В пути'
    WHEN 'W' THEN 'Ожидает погрузки'
    WHEN 'C' THEN 'Отменен'
    ELSE 'Неизвестно'
  END AS status_title,
  CASE 
    WHEN delivery_status = 'C' OR (contract_price - COALESCE(advance_paid, 0)) > 150000.00 THEN 'badge-danger'
    WHEN delivery_status = 'T' THEN 'badge-warning'
    WHEN delivery_status = 'D' AND (contract_price - COALESCE(advance_paid, 0)) <= 0.00 THEN 'badge-success'
    ELSE 'badge-secondary'
  END AS ui_badge_class
FROM fleet_shipments
ORDER BY departure_time DESC
LIMIT 20 OFFSET 0;
```

## 5. Классификатор ошибок и штрафные вычеты

| Ошибка студента | Суть дефекта | Штраф |
| :--- | :--- | :--- |
| **Пропуск модификатора FM** | В строке появляется паразитный лидирующий пробел: `' 150 000.00 руб.'`. | **-0.5 б.** |
| **Сортировка по отформатированному полю** | Указание в `ORDER BY` текстового алиаса вместо исходной числовой колонки (лексикографический сбой). | **-1.0 б.** |
| **Отсутствие секции ELSE в CASE** | Риск скрытого возврата `NULL` при несовпадении условий. | **-0.5 б.** |
| **Нарушение порядка условий в CASE** | Менее строгий предикат перекрывает более строгий (отличники получают базовую стипендию). | **-0.5 б.** |
| **Формат времени HH вместо HH24** | 12-часовой формат без AM/PM (утрата информативности для оператора). | **-0.5 б.** |
| **Отсутствие обработки NULL (COALESCE)** | Конкатенация с NULL или вычитание NULL стирает результат. | **-0.5 б.** |
| **Поверхностный теоретический ответ** | Отсутствие аргументации о различии типов и механизмах индексного поиска. | **-0.5 б.** |
