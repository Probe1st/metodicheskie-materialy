# Закрытая рубрика и эталон оценивания: Реляционная модель данных: таблицы и ограничения

Данный документ предназначен строго для преподавателя дисциплины «ОП.08 Основы проектирования баз данных» и содержит закрытые критерии оценивания индивидуального продукта обучающихся, эталоны решений по 4 практическим отраслевым вариантам и методику разбора типовых ошибок.

| Балл | Показатель | Описание требований к ответу |
| :---: | :--- | :--- |
| **2** | **Спецификация отношений (отлично)** | Полностью и технически корректно спроектированы две таблицы предметной области (родительская и дочерняя). Атрибуты названы в соответствии со стандартами snake_case. Типы данных выбраны оптимально с точки зрения занимаемой памяти (INT/SERIAL, VARCHAR с ограничением длины, NUMERIC для денег и дозировок, DATE для дат). Полностью соблюдено 4-е свойство отношений (1НФ — атомарность значений). |

| **0** | **Спецификация отношений (неудовлетворительно)** | Спецификация не заполнена, перепутаны родительская и дочерняя таблицы, отсутствуют ключевые атрибуты предметной области. |
| **1** | **Первичные и внешние ключи** | Однозначно определены первичные ключи (Primary Key) в обеих таблицах. Корректно спроектирован внешний ключ (Foreign Key) в дочерней таблице, ссылающийся строго на первичный (или уникальный) ключ родителя. Дано исчерпывающее профессиональное обоснование выбора правила ссылочной целостности (`ON DELETE RESTRICT` или `ON DELETE CASCADE`) с учетом рисков предметной области. |
| **0** | **Первичные и внешние ключи (неудовлетворительно)** | Не указан первичный ключ (нарушение 1-го свойства отношений), внешний ключ ссылается на неуникальный атрибут, выбрано деструктивное правило каскадного удаления без обоснования. |
| **1** | **Ограничения целостности и самопроверка** | Безошибочно сформулированы декларативные предикаты `CHECK` (проверка неотрицательности остатка $\ge 0$, терапевтического диапазона дозировки $\le 500$, балла от 0 до 100). Верно указаны ограничения `NOT NULL` и `UNIQUE`. Даны аргументированные ответы на вопросы глубокой самопроверки о фундаментальных свойствах отношений. |
| **0** | **Ограничения целостности (неудовлетворительно)** | Ограничения CHECK не сформулированы или содержат синтаксические/логические ошибки (перепутаны знаки неравенства), отсутствует понимание механизма отмены транзакции ядром СУБД. |

## 3. Эталонное содержание индивидуального продукта по 4 вариантам

### Вариант 1: Складской комплекс (Товары и Складские_остатки)
1. **Спецификация отношений**:
   - Родительская таблица `products`: `sku` VARCHAR(20) PRIMARY KEY, `name` VARCHAR(150) NOT NULL, `category` VARCHAR(50) NOT NULL, `unit_price` NUMERIC(10,2) NOT NULL CHECK (unit_price > 0).
   - Дочерняя таблица `inventory`: `inventory_id` SERIAL PRIMARY KEY, `sku` VARCHAR(20) NOT NULL, `warehouse_zone` VARCHAR(10) NOT NULL, `quantity` INT NOT NULL DEFAULT 0.
   - *Арность и мощность*: Таблица `products` имеет арность 4; `inventory` — арность 4.
2. **Первичные и внешние ключи**:
   - Внешний ключ: `FOREIGN KEY (sku) REFERENCES products(sku)`.
   - *Правило ON DELETE*: Строго **ON DELETE RESTRICT** (или `NO ACTION`).
   - *Обоснование*: Удаление товара, по которому на складе фактически числится ненулевой физический остаток, приведет к финансовой недостаче, искажению инвентаризационных ведомостей и нарушению материальной ответственности кладовщика. Каскадное удаление (`CASCADE`) здесь категорически недопустимо, так как оно молча сотрет данные об остатках на складе.
3. **Ограничения целостности и самопроверка**:
   - Предикат CHECK: `CHECK (quantity >= 0)`. При попытке списать больше единиц товара, чем есть в наличии, ядро СУБД вернет исключение `check constraint violation` и прервет транзакцию (ROLLBACK), не допустив отрицательного остатка.
   - Уникальность ячейки: Ограничение `UNIQUE (sku, warehouse_zone)`. Если допустить две строки с одинаковым товаром в одной зоне, нарушится фундаментальное 1-е свойство математического отношения (отсутствие дубликатов кортежей), что приведет к рассинхронизации остатков.

---

### Вариант 2: Медицинская клиника (Пациенты и Назначения)
1. **Спецификация отношений**:
   - Родительская таблица `patients`: `patient_id` SERIAL PRIMARY KEY, `full_name` VARCHAR(150) NOT NULL, `birth_date` DATE NOT NULL CHECK (birth_date <= CURRENT_DATE), `snils` VARCHAR(14) NOT NULL UNIQUE.
   - Дочерняя таблица `prescriptions`: `prescription_id` SERIAL PRIMARY KEY, `patient_id` INT NOT NULL, `medication_name` VARCHAR(100) NOT NULL, `dosage_mg` NUMERIC(6,2) NOT NULL.
2. **Первичные и внешние ключи**:
   - Внешний ключ: `FOREIGN KEY (patient_id) REFERENCES patients(patient_id)`.
   - *Обоснование NOT NULL*: Назначение сильнодействующего препарата не может быть «анонимным» (NULL). Если поле `patient_id` будет содержать NULL, медсестра в процедурном кабинете не сможет определить, кому вводить препарат, что несет прямую угрозу жизни человека.
3. **Ограничения целостности и самопроверка**:
   - Предикат CHECK: `CHECK (dosage_mg > 0 AND dosage_mg <= 500)`.
   - *Защита на уровне ядра СУБД*: Проверка на фронтенде или в коде клиентского приложения недостаточна: баг в мобильном клиенте медсестры, прямой сетевой сбой или прямой SQL-запрос оператора могут пропустить летальную дозу (например, 5000 мг вместо 50 мг). Ограничение CHECK на уровне СУБД делает невозможной запись невалидной дозировки в базу физически.
   - *Политика ON DELETE*: Строго **ON DELETE RESTRICT**. Медицинские карты и назначения подлежат архивному учету (хранение от 25 до 75 лет по законодательству РФ). Удаление пациента каскадно вместе с его назначениями уничтожит историю лечения и доказательную базу при врачебной ошибке.

### Вариант 3: Автосервис (Автомобили и Акты_дефектовки)
1. **Спецификация отношений**:
   - Родительская таблица `vehicles`: `vehicle_id` SERIAL PRIMARY KEY, `vin` CHAR(17) NOT NULL UNIQUE CHECK (LENGTH(vin) = 17), `license_plate` VARCHAR(12) NOT NULL, `mileage` INT NOT NULL CHECK (mileage >= 0).
   - Дочерняя таблица `inspection_reports`: `report_id` SERIAL PRIMARY KEY, `vehicle_id` INT NOT NULL, `defect_description` TEXT NOT NULL, `estimated_cost` NUMERIC(10,2) NOT NULL CHECK (estimated_cost >= 0).
2. **Первичные и внешние ключи**:
   - Внешний ключ: `FOREIGN KEY (vehicle_id) REFERENCES vehicles(vehicle_id)`.
   - *Сравнение ключей (VIN vs vehicle_id)*: Использование суррогатного целочисленного ключа `vehicle_id` (4 байта) вместо естественного `vin` (17 байт CHAR) ускоряет операции соединения таблиц (`JOIN`) в 3–4 раза и значительно экономит память B-Tree индексов. Кроме того, если оператор допустит опечатку в VIN-коде при оформлении, исправление VIN в родительской таблице не потребует дорогостоящего каскадного обновления сотен внешних ключей в дочерних актах дефектовки.
3. **Ограничения целостности и самопроверка**:
   - Ограничение UNIQUE: Гарантирует уникальность автомобиля в базе. При повторной попытке завести автомобиль с тем же VIN ядро СУБД вернет ошибку `duplicate key value violates unique constraint "uq_vin"`.
   - *Политика ON DELETE*: **ON DELETE RESTRICT**. При продаже автомобиля новому владельцу запись авто не удаляется: в системе фиксируется смена собственника, а вся история предыдущих актов дефектовки и ремонтов сохраняется для сервисной книжки и юридической гарантии.

### Вариант 4: Онлайн-курсы (Студенты и Сдача_заданий)
1. **Спецификация отношений**:
   - Родительская таблица `students`: `student_id` SERIAL PRIMARY KEY, `email` VARCHAR(100) NOT NULL UNIQUE, `full_name` VARCHAR(120) NOT NULL, `registration_date` DATE NOT NULL DEFAULT CURRENT_DATE.
   - Дочерняя таблица `submissions`: `submission_id` SERIAL PRIMARY KEY, `student_id` INT NOT NULL, `task_id` INT NOT NULL, `score` INT NOT NULL.
2. **Первичные и внешние ключи**:
   - Внешний ключ: `FOREIGN KEY (student_id) REFERENCES students(student_id)`.
   - Альтернативный составной ключ: `UNIQUE (student_id, task_id)`. Это ограничение предотвращает повторную запись оценки за одно и то же задание для одного студента, обеспечивая 1-е фундаментальное свойство отношений (уникальность строк в теле отношения).
3. **Ограничения целостности и самопроверка**:
   - Предикат CHECK: `CHECK (score BETWEEN 0 AND 100)`. Защищает от ввода отрицательных баллов или баллов свыше 100 при ошибочном импорте результатов тестов.
   - *Политика ON DELETE*: В академической системе допустимы две модели в зависимости от регламента:
     * Модель академического архива: **ON DELETE RESTRICT** — профиль студента нельзя удалить из базы, если за ним числятся зачетные ведомости (вместо удаления применяется флаг `status = 'expelled'`).
     * Модель персональных данных (GDPR / 152-ФЗ): **ON DELETE CASCADE** — если студент воспользовался правом на отзыв персональных данных, система удаляет его аккаунт и связанные результаты сдачи. В ответе студента засчитывается любой из вариантов при наличии обоснования.

## 4. Типовые ошибки студентов и штрафные санкции

1. **Создание внешнего ключа на неуникальный атрибут**:
   - *Суть ошибки*: Студент объявляет внешний ключ на поле `medication_name` или `full_name`.
   - *Комментарий*: Внешний ключ обязан ссылаться строго на первичный ключ (`PRIMARY KEY`) или альтернативный уникальный ключ (`UNIQUE`). В противном случае нарушается правило гарантированного доступа Кодда (невозможно однозначно определить родительскую строку).
   - *Штраф*: **-1 балл** в Части 2.
2. **Использование каскадного удаления (`CASCADE`) для финансовых и материальных таблиц**:
   - *Суть ошибки*: Студент указывает `ON DELETE CASCADE` для складских остатков или медицинских назначений без понимания рисков.
   - *Комментарий*: Удаление карточки товара не должно уничтожать физический складской остаток.
   - *Штраф*: **-0.5 балла** в Части 2.
3. **Отсутствие проверки CHECK на неотрицательность физических величин**:
   - *Суть ошибки*: Поле `quantity`, `price` или `mileage` объявлено как обычный `INT` без ограничения `CHECK (>= 0)`.
   - *Комментарий*: СУБД допустит отрицательные остатки и цены, что приводит к логическому краху бизнес-системы.
   - *Штраф*: **-0.5 балла** в Части 3.
4. **Хранение составных списков в текстовом поле (нарушение 1НФ)**:
   - *Суть ошибки*: Студент создает в таблице студентов поле `phones VARCHAR(255)`, куда планирует писать номера через запятую.
   - *Комментарий*: Грубое нарушение Первой нормальной формы (1НФ) и 4-го фундаментального свойства отношений (атомарность значений).
   - *Штраф*: **-1 балл** в Части 1.
