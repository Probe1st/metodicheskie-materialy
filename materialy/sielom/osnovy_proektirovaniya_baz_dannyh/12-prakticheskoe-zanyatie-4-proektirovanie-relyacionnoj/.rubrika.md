## 2. Критериальная шкала оценивания (0–4 балла)

| Балл | Критерий | Показатели выполнения и дескрипторы требований к решению |
| :---: | :--- | :--- |
| **2** | **Нормализация схемы до 3NF (отлично)** | Полностью выявлены и устранены все транзитивные функциональные зависимости вида $X \to Y \to Z$. Схема декомпозирована без потерь информации (теорема Хита) на 3–4 логически непротиворечивые таблицы. Четко разграничены независимые сущности-справочники и зависимые операционные таблицы. Обосновано выполнение критериев 3NF/BCNF. |
| **1** | **Нормализация схемы до 3NF (хорошо / частично)** | Транзитивные зависимости в основном устранены, выделены ключевые справочники, однако допущены неточности: оставлен второстепенный избыточный атрибут в операционной таблице (например, адрес или статус), либо нарушено свойство атомарности (1NF) в одном из полей. |
| **0** | **Нормализация схемы (неудовлетворительно)** | Грубое нарушение 3NF: ключевая транзитивная зависимость (оклад от должности, страна от производителя, тариф от города) сохранена в единой плоской таблице. Архитектурная избыточность не устранена. |
| **1** | **DDL-спецификация и ключи (зачтено)** | DDL-скрипт ANSI SQL синтаксически корректен, соблюден строгий топологический порядок создания таблиц (DAG зависимостей). Явно объявлены первичные ключи `PRIMARY KEY` и внешние ключи `FOREIGN KEY ... REFERENCES`. Выбраны безопасные политики ссылочной целостности (`ON DELETE RESTRICT` для справочников). Корректно заданы машинные типы (`NUMERIC` для денег/тарифов, `VARCHAR(N)` с ограничением длины) и ограничения `NOT NULL`, `UNIQUE`, `CHECK`. |
| **0** | **DDL-спецификация и ключи (не зачтено)** | Ошибки топологии (попытка сослаться на еще не созданную таблицу), использование типа FLOAT для денежных величин, слепое навешивание `ON DELETE CASCADE` на сущности-справочники, отсутствие ограничений CHECK на физически неотрицательные величины. |
| **1** | **Тестовые данные и самопроверка (зачтено)** | Сформирован пакет из не менее чем 5 согласованных операторов `INSERT INTO`, наполняющих таблицы строго в топологической последовательности. Представлены граничные проверки предикатов CHECK и закомментированный негативный контрпример с пояснением ошибки ядра СУБД. Даны исчерпывающие и аргументированные ответы на блок вопросов самоконтроля. |
| **0** | **Тестовые данные и самопроверка (не зачтено)** | Внешние ключи в операторах INSERT ссылаются на несуществующие идентификаторы (Foreign Key Violation), отсутствуют граничные тесты, вопросы самопроверки пропущены или содержат принципиальные ошибки. |

## 3. Полные закрытые эталоны решений по 4 практическим вариантам

### Вариант 1. БД «Отдел кадров предприятия»

#### 1. Анализ функциональных зависимостей и схема 3NF
- Исходное отношение: `(emp_id, full_name, phone, passport_data, dept_name, building, room_number, pos_title, base_salary, order_number, appointment_date, work_rate)`.
- Выявленные транзитивные функциональные зависимости:
  1. `emp_id → pos_id → (pos_title, base_salary)`: Базовый оклад должности зависит от наименования должности, а не от личности конкретного сотрудника. Устраняется выносом в таблицу `positions`.
  2. `emp_id → dept_id → (dept_name, building, room_number)`: Подразделение и место его размещения не зависят от конкретного сотрудника. Устраняется выносом в таблицу `departments`.
- Итоговая реляционная схема в 3NF (4 таблицы):
  1. `departments` (`dept_id` PK, `dept_name` UNIQUE, `building`, `room_number`) — независимый справочник.
  2. `positions` (`pos_id` PK, `title` UNIQUE, `base_salary`, `is_active`) — независимый справочник.
  3. `employees` (`emp_id` PK, `full_name`, `phone`, `passport_data` UNIQUE, `dept_id` FK) — операционная таблица сотрудников.
  4. `appointment_orders` (`order_id` PK, `order_number` UNIQUE, `emp_id` FK, `pos_id` FK, `appointment_date`, `work_rate`) — таблица кадровых назначений.

#### 2. Эталонный DDL-скрипт (ANSI SQL)
```sql
-- Очистка схемы (в обратном топологическом порядке)
DROP TABLE IF EXISTS appointment_orders CASCADE;
DROP TABLE IF EXISTS employees CASCADE;
DROP TABLE IF EXISTS positions CASCADE;
DROP TABLE IF EXISTS departments CASCADE;

-- 1. Справочник подразделений (независимый)
CREATE TABLE departments (
    dept_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    dept_name VARCHAR(120) NOT NULL UNIQUE,
    building VARCHAR(30) NOT NULL,
    room_number VARCHAR(10) NOT NULL
);

-- 2. Справочник должностей со штатным окладом (устранение транзитивности)
CREATE TABLE positions (
    pos_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title VARCHAR(100) NOT NULL UNIQUE,
    base_salary NUMERIC(10, 2) NOT NULL,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    CONSTRAINT chk_salary_positive CHECK (base_salary >= 19242.00)
);

-- 3. Таблица сотрудников
CREATE TABLE employees (
    emp_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(150) NOT NULL,
    phone VARCHAR(20) NOT NULL,
    passport_data VARCHAR(30) NOT NULL UNIQUE,
    dept_id INT NOT NULL,
    CONSTRAINT fk_emp_dept FOREIGN KEY (dept_id) 
        REFERENCES departments(dept_id) ON DELETE RESTRICT
);

-- 4. Таблица приказов о назначении (связующая спецификация)
CREATE TABLE appointment_orders (
    order_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(50) NOT NULL UNIQUE,
    emp_id INT NOT NULL,
    pos_id INT NOT NULL,
    appointment_date DATE NOT NULL,
    work_rate NUMERIC(3, 2) NOT NULL DEFAULT 1.00,
    CONSTRAINT fk_order_emp FOREIGN KEY (emp_id) 
        REFERENCES employees(emp_id) ON DELETE RESTRICT,
    CONSTRAINT fk_order_pos FOREIGN KEY (pos_id) 
        REFERENCES positions(pos_id) ON DELETE RESTRICT,
    CONSTRAINT chk_work_rate_range CHECK (work_rate BETWEEN 0.25 AND 1.50)
);
```

#### 4. Эталон ответов на вопросы самоконтроля
1. *Почему вынос оклада в positions устраняет Update Anomaly?* Потому что при индексации оклада для 200 инженеров обновляется ровно одна строка в таблице `positions`, а не 200 строк в `employees`. Риск частичного обновления и рассинхронизации данных сведен к нулю.
2. *Почему для связи `employees → positions` недопустим `CASCADE`?* Если отдел кадров решит закрыть вакантную ставку или архивировать должность, `ON DELETE CASCADE` молча удалил бы из базы всех действующих сотрудников и их персональные данные. Правило `RESTRICT` блокирует удаление должности, пока на ней числится хотя бы один сотрудник.

### Вариант 2. БД «Аптечный склад»

#### 1. Анализ функциональных зависимостей и схема 3NF
- Исходное отношение: `(med_id, trade_name, dosage_form, dosage_mg, mfr_name, country, license_num, batch_number, mfg_date, expiry_date, quantity, invoice_num, ship_date, pharmacy_dest)`.
- Транзитивные зависимости:
  1. `med_id → mfr_id → (mfr_name, country, license_num)`: Страна и номер фармацевтической лицензии зависят от завода-изготовителя, а не от каждого отдельного лекарства. Устраняется выносом в `manufacturers`.
  2. `batch_id → med_id, mfg_date, expiry_date, quantity`: Сроки годности и количество на остатке жестко привязаны к конкретной физической партии.
- Итоговая реляционная схема в 3NF (4 таблицы):
  1. `manufacturers` (`mfr_id` PK, `mfr_name` UNIQUE, `country`, `license_num` UNIQUE).
  2. `medicines` (`med_id` PK, `trade_name`, `dosage_form`, `dosage_mg`, `mfr_id` FK).
  3. `batches` (`batch_id` PK, `batch_number` UNIQUE, `med_id` FK, `mfg_date`, `expiry_date`, `quantity_boxes`).
  4. `sales_invoices` (`invoice_id` PK, `invoice_number` UNIQUE, `batch_id` FK, `shipment_date`, `quantity_shipped`, `pharmacy_dest`).

#### 2. Эталонный DDL-скрипт (ANSI SQL)
```sql
DROP TABLE IF EXISTS sales_invoices CASCADE;
DROP TABLE IF EXISTS batches CASCADE;
DROP TABLE IF EXISTS medicines CASCADE;
DROP TABLE IF EXISTS manufacturers CASCADE;

-- 1. Справочник производителей
CREATE TABLE manufacturers (
    mfr_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    mfr_name VARCHAR(150) NOT NULL UNIQUE,
    country VARCHAR(80) NOT NULL,
    license_num VARCHAR(50) NOT NULL UNIQUE
);

-- 2. Номенклатура медикаментов
CREATE TABLE medicines (
    med_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    trade_name VARCHAR(120) NOT NULL,
    dosage_form VARCHAR(50) NOT NULL,
    dosage_mg NUMERIC(8, 2) NOT NULL,
    mfr_id INT NOT NULL,
    CONSTRAINT fk_med_mfr FOREIGN KEY (mfr_id) 
        REFERENCES manufacturers(mfr_id) ON DELETE RESTRICT,
    CONSTRAINT chk_dosage_positive CHECK (dosage_mg > 0)
);

-- 3. Учет складских партий
CREATE TABLE batches (
    batch_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    batch_number VARCHAR(40) NOT NULL UNIQUE,
    med_id INT NOT NULL,
    mfg_date DATE NOT NULL,
    expiry_date DATE NOT NULL,
    quantity_boxes INT NOT NULL DEFAULT 0,
    CONSTRAINT fk_batch_med FOREIGN KEY (med_id) 
        REFERENCES medicines(med_id) ON DELETE RESTRICT,
    CONSTRAINT chk_batch_qty CHECK (quantity_boxes >= 0),
    CONSTRAINT chk_expiry_valid CHECK (expiry_date > mfg_date)
);

-- 4. Расходные накладные
CREATE TABLE sales_invoices (
    invoice_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    invoice_number VARCHAR(50) NOT NULL UNIQUE,
    batch_id INT NOT NULL,
    shipment_date DATE NOT NULL,
    quantity_shipped INT NOT NULL,
    pharmacy_dest VARCHAR(150) NOT NULL,
    CONSTRAINT fk_inv_batch FOREIGN KEY (batch_id) 
        REFERENCES batches(batch_id) ON DELETE RESTRICT,
    CONSTRAINT chk_shipped_positive CHECK (quantity_shipped > 0)
);
```

#### 4. Эталон ответов на вопросы самоконтроля
1. *К какой аномалии привело бы хранение лицензии завода в строке партии?* К аномалии обновления: при продлении лицензии завода пришлось бы обновлять десятки тысяч строк складских партий; и к аномалии вставки: нельзя внести в базу нового поставщика, пока у него не закуплена первая партия товара.
2. *Зачем CHECK на уровне СУБД для срока годности?* Клиентские приложения могут содержать ошибки валидации или подвергнуться сбою. Ограничение на уровне ядра базы данных физически исключает попадание в аптечную сеть партий с невалидными датами.

### Вариант 3. БД «Учебный центр дополнительного образования»

#### 1. Анализ функциональных зависимостей и схема 3NF
- Исходное отношение: `(student_id, full_name, phone, email, group_id, course_name, total_fee, total_hours, start_date, payment_id, pay_date, pay_amount, pay_status)`.
- Транзитивные зависимости:
  1. `group_id → course_id → (course_name, total_fee, total_hours)`: Стоимость обучения и академические часы жестко регламентированы учебной программой курса и не зависят от конкретной группы или набора слушателей. Выносится в `courses`.
  2. `group_id → (course_id, start_date)`: Группа привязана к курсу и фиксирует расписание старта.
- Итоговая реляционная схема в 3NF (4 таблицы):
  1. `courses` (`course_id` PK, `course_name` UNIQUE, `total_hours`, `course_fee`).
  2. `study_groups` (`group_id` PK, `group_code` UNIQUE, `course_id` FK, `start_date`, `max_capacity`).
  3. `students` (`student_id` PK, `full_name`, `phone`, `email` UNIQUE, `group_id` FK).
  4. `payments` (`payment_id` PK, `receipt_num` UNIQUE, `student_id` FK, `payment_date`, `amount`, `payment_method`).

#### 2. Эталонный DDL-скрипт (ANSI SQL)
```sql
DROP TABLE IF EXISTS payments CASCADE;
DROP TABLE IF EXISTS students CASCADE;
DROP TABLE IF EXISTS study_groups CASCADE;
DROP TABLE IF EXISTS courses CASCADE;

-- 1. Каталог учебных курсов
CREATE TABLE courses (
    course_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    course_name VARCHAR(150) NOT NULL UNIQUE,
    total_hours INT NOT NULL,
    course_fee NUMERIC(10, 2) NOT NULL,
    CONSTRAINT chk_hours_positive CHECK (total_hours > 0),
    CONSTRAINT chk_fee_positive CHECK (course_fee >= 5000.00)
);

-- 2. Учебные группы
CREATE TABLE study_groups (
    group_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    group_code VARCHAR(30) NOT NULL UNIQUE,
    course_id INT NOT NULL,
    start_date DATE NOT NULL,
    max_capacity INT NOT NULL DEFAULT 15,
    CONSTRAINT fk_group_course FOREIGN KEY (course_id) 
        REFERENCES courses(course_id) ON DELETE RESTRICT,
    CONSTRAINT chk_capacity CHECK (max_capacity BETWEEN 5 AND 35)
);

-- 3. Слушатели курсов
CREATE TABLE students (
    student_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(150) NOT NULL,
    phone VARCHAR(20) NOT NULL,
    email VARCHAR(100) NOT NULL UNIQUE,
    group_id INT NOT NULL,
    CONSTRAINT fk_stud_group FOREIGN KEY (group_id) 
        REFERENCES study_groups(group_id) ON DELETE RESTRICT
);

-- 4. Платежи и кассовые чеки
CREATE TABLE payments (
    payment_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    receipt_num VARCHAR(50) NOT NULL UNIQUE,
    student_id INT NOT NULL,
    payment_date DATE NOT NULL,
    amount NUMERIC(10, 2) NOT NULL,
    payment_method VARCHAR(30) NOT NULL DEFAULT 'Банковская карта',
    CONSTRAINT fk_pay_student FOREIGN KEY (student_id) 
        REFERENCES students(student_id) ON DELETE RESTRICT,
    CONSTRAINT chk_amount_positive CHECK (amount > 0)
);
```

### Вариант 4. БД «Станция техобслуживания (СТО)»

#### 1. Анализ функциональных зависимостей и схема 3NF
- Исходное отношение: `(vehicle_id, license_plate, vin, make_model, model_year, client_name, client_phone, order_num, order_date, mileage, issue_desc, work_id, work_name, labor_hours, hourly_rate)`.
- Транзитивные зависимости:
  1. `vehicle_id → client_id → (client_name, client_phone)`: Контактные данные автовладельца зависят от самого человека, а не от технического состояния автомобиля. Клиент может владеть 3 автомобилями.
  2. `order_id → (vehicle_id, order_date, mileage)`: Заказ-наряд привязан к конкретному автомобилю и моменту времени.
  3. `work_item_id → order_id, work_name, labor_hours, hourly_rate`: Перечень выполненных операций формирует дочернюю спецификацию заказ-наряда (1:M).
- Итоговая реляционная схема в 3NF (4 таблицы):
  1. `clients` (`client_id` PK, `full_name`, `phone` UNIQUE, `created_at`).
  2. `vehicles` (`vehicle_id` PK, `vin` UNIQUE, `license_plate` UNIQUE, `make_model`, `model_year`, `client_id` FK).
  3. `repair_orders` (`order_id` PK, `order_number` UNIQUE, `vehicle_id` FK, `order_date`, `mileage`, `issue_desc`, `status`).
  4. `work_items` (`item_id` PK, `order_id` FK, `work_name`, `labor_hours`, `hourly_rate`).

#### 2. Эталонный DDL-скрипт (ANSI SQL)
```sql
DROP TABLE IF EXISTS work_items CASCADE;
DROP TABLE IF EXISTS repair_orders CASCADE;
DROP TABLE IF EXISTS vehicles CASCADE;
DROP TABLE IF EXISTS clients CASCADE;

-- 1. Таблица клиентов
CREATE TABLE clients (
    client_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(150) NOT NULL,
    phone VARCHAR(20) NOT NULL UNIQUE,
    registration_date DATE NOT NULL DEFAULT CURRENT_DATE
);

-- 2. Таблица автомобилей
CREATE TABLE vehicles (
    vehicle_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    vin CHAR(17) NOT NULL UNIQUE,
    license_plate VARCHAR(12) NOT NULL UNIQUE,
    make_model VARCHAR(80) NOT NULL,
    model_year INT NOT NULL,
    client_id INT NOT NULL,
    CONSTRAINT fk_veh_client FOREIGN KEY (client_id) 
        REFERENCES clients(client_id) ON DELETE RESTRICT,
    CONSTRAINT chk_vin_length CHECK (LENGTH(vin) = 17),
    CONSTRAINT chk_year_valid CHECK (model_year BETWEEN 1980 AND 2027)
);

-- 3. Заказ-наряды СТО
CREATE TABLE repair_orders (
    order_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    vehicle_id INT NOT NULL,
    order_date DATE NOT NULL,
    mileage INT NOT NULL,
    issue_desc TEXT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'в работе',
    CONSTRAINT fk_order_veh FOREIGN KEY (vehicle_id) 
        REFERENCES vehicles(vehicle_id) ON DELETE RESTRICT,
    CONSTRAINT chk_mileage_positive CHECK (mileage >= 0),
    CONSTRAINT chk_status_valid CHECK (status IN ('принят', 'в работе', 'готов', 'выдан'))
);

-- 4. Выполненные работы по заказ-наряду (спецификация: мастер-детали)
CREATE TABLE work_items (
    item_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id INT NOT NULL,
    work_name VARCHAR(150) NOT NULL,
    labor_hours NUMERIC(4, 2) NOT NULL,
    hourly_rate NUMERIC(10, 2) NOT NULL DEFAULT 2200.00,
    CONSTRAINT fk_item_order FOREIGN KEY (order_id) 
        REFERENCES repair_orders(order_id) ON DELETE CASCADE,
    CONSTRAINT chk_hours_pos CHECK (labor_hours > 0),
    CONSTRAINT chk_rate_pos CHECK (hourly_rate >= 500.00)
);
```

#### 4. Эталон ответов на вопросы самоконтроля
1. *Почему для `work_items` допустим CASCADE, а для `vehicles` запрещен?* Потому что строки выполненных работ не имеют самостоятельного смысла вне своего заказ-наряда: при аннулировании ошибочного черновика наряда каскадное удаление его строк логично и безопасно. В то же время удаление клиента не должно уничтожать историю ремонтов его машины (машина сохраняется в архиве СТО).
2. *Зачем суррогатный ключ `vehicle_id INT`, если есть VIN?* Целочисленный ключ занимает 4 байта вместо 17 байт строкового VIN, что значительно ускоряет операции соединений `JOIN` и снижает объем оперативной памяти под индексы B-Tree. Кроме того, при исправлении оператором опечатки в VIN-коде не требуется дорогостоящее каскадное обновление внешних ключей в тысячах исторических заказ-нарядов.
