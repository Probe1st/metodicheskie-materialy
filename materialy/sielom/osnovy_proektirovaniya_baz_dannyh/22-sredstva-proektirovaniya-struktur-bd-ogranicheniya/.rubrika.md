## 2. Критериальная шкала оценивания (0–4 балла)

| Балл | Критерий | Показатели выполнения и дескрипторы требований к решению |
| :---: | :--- | :--- |
| **2** | **Спецификация ограничений CHECK/EXCLUDE (отлично)** | DDL-скрипт полностью работоспособен и синтаксически безупречен. Корректно использовано расширение `btree_gist`, интервальный тип `tsrange`/`daterange`, операторы равенства `=` и перекрытия `&&` в секции `EXCLUDE USING gist`. Регулярные выражения POSIX содержат обязательные якоря начала `^` и конца `$` строки. В предикатах CHECK корректно учтена трехзначная логика SQL и семантика `NULL`. |
| **1** | **Спецификация ограничений CHECK/EXCLUDE (хорошо / частично)** | В DDL допущены мелкие огрехи: забыта команда `CREATE EXTENSION IF NOT EXISTS btree_gist`, либо в регулярном выражении опущен один из якорей (например, только `^` без `$`), но логическая структура ограничений и типы данных выбраны верно. |
| **0** | **Спецификация ограничений CHECK/EXCLUDE (неудовлетворительно)** | Грубые концептуальные ошибки: попытка реализовать проверку непересечения интервалов через простой `UNIQUE (room_id, start_time)`; синтаксически неверный DDL; полное отсутствие понимания операторов регулярных выражений. |
| **1** | **Отложенные ограничения DEFERRABLE (зачтено)** | Архитектурно верно решена проблема циклической зависимости: внешний ключ объявлен с параметром `DEFERRABLE INITIALLY DEFERRED` (или `INITIALLY IMMEDIATE` с явным переключением). Составлен корректный транзакционный блок `BEGIN ... INSERT ... INSERT ... COMMIT`, обоснован момент проверки связей ядром СУБД. |
| **0** | **Отложенные ограничения DEFERRABLE (не зачтено)** | Отложенные ограничения не использованы; студент предлагает снять ограничение `NOT NULL` и вручную обновлять поле вторым запросом `UPDATE`, либо пытается объявить `CHECK ... DEFERRABLE`, что не поддерживается стандартом. |
| **1** | **Выявление конфликтов и самопроверка (зачтено)** | Дано исчерпывающее объяснение природы Race Condition при наивном `SELECT COUNT(*)`. Безошибочно выявлены логические противоречия и взаимоисключающие предикаты в тестовых заданиях. На все контрольные вопросы даны аргументированные ответы. |
| **0** | **Выявление конфликтов и самопроверка (не зачтено)** | Студент заявляет, что «проверки в JavaScript на клиенте достаточно»; не видит очевидного логического тупика в несовместных условиях; блок вопросов самопроверки оставлен пустым. |

## 3. Закрытые эталонные решения по вариантам рабочего листа `zanyatie.html`

### Вариант 1. Система бронирования конференц-залов (EXCLUDE USING gist)

#### 1. Эталонный DDL-скрипт
```sql
-- 1. Подключение расширения для поддержки скалярных операторов (=) в GiST
CREATE EXTENSION IF NOT EXISTS btree_gist;

-- 2. Таблица бронирования конференц-залов
CREATE TABLE conference_room_bookings (
    booking_id BIGSERIAL PRIMARY KEY,
    room_id INT NOT NULL,
    booking_slot TSRANGE NOT NULL,
    organizer_fio VARCHAR(120) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    
    -- Ограничение корректности временного интервала
    CONSTRAINT chk_slot_bounds CHECK (
        NOT isempty(booking_slot) AND lower(booking_slot) < upper(booking_slot)
    ),
    
    -- Ограничение исключения: для одного зала интервалы не перекрываются
    CONSTRAINT exc_room_no_double_booking EXCLUDE USING gist (
        room_id WITH =,
        booking_slot WITH &&
    )
);
```

#### 2. Анализ Race Condition vs EXCLUDE
Запрос `SELECT COUNT(*) WHERE room_id = 1 AND booking_slot && ...` выполняется в снимке данных (Snapshot) текущей транзакции. При параллельных запросах обе транзакции видят, что конфликтных строк еще нет (COUNT = 0), и обе отправляют команду `INSERT`. На уровне уровня изоляции Read Committed ни одна из транзакций не блокирует другую на чтении. В результате возникает аномалия овербукинга.
Ограничение `EXCLUDE USING gist` поддерживается на уровне структур физического GiST-индекса СУБД. При вставке второй строки СУБД выполняет предикатную блокировку узла индекса, обнаруживает пересечение интервалов и генерирует исключение `23P01 exclusion_violation`, гарантируя 100% защиту от двойного бронирования без необходимости ручной блокировки всей таблицы (`LOCK TABLE`).

#### 3. Тестовый сценарий
```sql
-- Первая бронь зала №101: 14:00 - 16:00 (УСПЕШНО)
INSERT INTO conference_room_bookings (room_id, booking_slot, organizer_fio)
VALUES (101, tsrange('2026-10-01 14:00:00', '2026-10-01 16:00:00', '[)'), 'Иванов И.И.');

-- Вторая бронь зала №101: 15:30 - 17:00 (ОШИБКА exclusion_violation!)
INSERT INTO conference_room_bookings (room_id, booking_slot, organizer_fio)
VALUES (101, tsrange('2026-10-01 15:30:00', '2026-10-01 17:00:00', '[)'), 'Петров П.П.');
-- СУБД вернет: ERROR: conflicting key value violates exclusion constraint "exc_room_no_double_booking"
```

### Вариант 2. Регистрация клиентов банковского портала (СНИЛС, паспорт, regex)

#### 1. Эталонный DDL-скрипт
```sql
CREATE TABLE bank_clients (
    client_id BIGSERIAL PRIMARY KEY,
    full_name VARCHAR(150) NOT NULL,
    snils CHAR(14) NOT NULL,
    passport_series CHAR(4) NOT NULL,
    passport_number CHAR(6) NOT NULL,
    birth_date DATE NOT NULL,
    phone_number VARCHAR(12) NOT NULL,
    registration_date TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    
    -- СНИЛС: ХХХ-ХХХ-ХХХ ХХ
    CONSTRAINT chk_client_snils 
        CHECK (snils ~ '^\d{3}-\d{3}-\d{3} \d{2}$'),
        
    -- Паспорт РФ: 4 цифры серии и 6 цифр номера
    CONSTRAINT chk_passport_series 
        CHECK (passport_series ~ '^\d{4}$'),
    CONSTRAINT chk_passport_number 
        CHECK (passport_number ~ '^\d{6}$'),
        
    -- Телефон: формат +7XXXXXXXXXX (11 цифр с префиксом +7)
    CONSTRAINT chk_phone_format 
        CHECK (phone_number ~ '^\+7\d{10}$'),
        
    -- Совершеннолетие: клиенту должно исполниться 18 лет
    CONSTRAINT chk_adult_client 
        CHECK (birth_date <= CURRENT_DATE - INTERVAL '18 years')
);
```

#### 2. Анализ отсутствия якорей `^` и `$`
Если регулярное выражение записано как `snils ~ '\d{3}-\d{3}-\d{3} \d{2}'`, СУБД производит поиск совпадения подстроки в любом месте входного значения. В результате строка `'СНИЛС: 123-456-789 00 (выдан в 2020)'` или `'ABC123-456-789 00XYZ'` будет признана полностью валидной, что разрушает строгую типизацию и требования интеграции с государственными сервисами ЕСИА/СМЭВ. Якоря `^` (начало строки) и `$` (конец строки) гарантируют, что строка содержит строго регламентированную последовательность символов.

#### 3. Трехзначная логика SQL и NULL в CHECK
В реляционных базах данных булевы выражения оперируют тремя значениями: `TRUE`, `FALSE` и `UNKNOWN`. Ограничение целостности `CHECK` отвергает строку **исключительно в случае, когда предикат возвращает FALSE**. Если поле равно `NULL` и в таблице не объявлено ограничение `NOT NULL`, результат выражения `NULL ~ '^\d{4}$'` равен `UNKNOWN`. Поскольку результат не равен `FALSE`, СУБД разрешит вставку пустой строки. Именно поэтому для обязательных атрибутов критически важно совмещать `CHECK` с декларацией `NOT NULL`.

### Вариант 3. Отели и гостиницы (циклическая ссылка DEFERRABLE)

#### 1. Эталонный DDL-скрипт
```sql
-- 1. Таблица отелей (ссылается на номер, который еще не создан)
CREATE TABLE hotels (
    hotel_id INT PRIMARY KEY,
    hotel_name VARCHAR(100) NOT NULL,
    presidential_suite_id INT NOT NULL
);

-- 2. Таблица номеров (ссылается на отель)
CREATE TABLE hotel_rooms (
    room_id INT PRIMARY KEY,
    hotel_id INT NOT NULL REFERENCES hotels(hotel_id) ON DELETE CASCADE,
    room_number VARCHAR(20) NOT NULL,
    category VARCHAR(50) NOT NULL DEFAULT 'Standard'
);

-- 3. Добавление внешнего ключа с отложенной валидацией
ALTER TABLE hotels 
    ADD CONSTRAINT fk_hotel_presidential_suite
    FOREIGN KEY (presidential_suite_id) REFERENCES hotel_rooms(room_id)
    DEFERRABLE INITIALLY DEFERRED;
```

#### 2. Атомарная бесконфликтная транзакция вставки
```sql
BEGIN;
    -- Шаг 1: Вставляем отель со ссылкой на несуществующий пока номер 501
    -- Благодаря INITIALLY DEFERRED ошибка НЕ генерируется!
    INSERT INTO hotels (hotel_id, hotel_name, presidential_suite_id)
    VALUES (1, 'Grand Palace Resort & Spa', 501);

    -- Шаг 2: Вставляем президентский номер 501 с ссылкой на созданный отель 1
    INSERT INTO hotel_rooms (room_id, hotel_id, room_number, category)
    VALUES (501, 1, 'Suite 501', 'Presidential');

    -- Шаг 3: Фиксация транзакции
    -- В этот момент СУБД проверяет fk_hotel_presidential_suite: номер 501 найден!
COMMIT;
```

#### 3. Сравнение режимов INITIALLY DEFERRED и INITIALLY IMMEDIATE
* `INITIALLY IMMEDIATE`: ограничение может быть отложено, но по умолчанию проверяется немедленно в конце каждой DML-инструкции (`INSERT/UPDATE/DELETE`). Если выполнить вставку отеля без предварительного переключения режима, транзакция моментально завершится ошибкой внешнего ключа. Чтобы отложить проверку, разработчик обязан явно вызвать в начале транзакции: `SET CONSTRAINTS fk_hotel_presidential_suite DEFERRED;`.
* `INITIALLY DEFERRED`: проверка автоматически откладывается до момента выполнения команды `COMMIT`. Внутри транзакции данные могут временно нарушать ссылочную целостность. Ошибка `foreign_key_violation` возникает строго на этапе `COMMIT`, если к концу транзакции родительская запись так и не была создана.

### Вариант 4. Электронный маркетплейс (скидки, артикулы SKU)

#### 1. Эталонный DDL-скрипт
```sql
CREATE TABLE marketplace_goods (
    product_id BIGSERIAL PRIMARY KEY,
    sku VARCHAR(20) NOT NULL,
    title VARCHAR(200) NOT NULL,
    base_price NUMERIC(10, 2) NOT NULL,
    sale_price NUMERIC(10, 2),
    discount_percent NUMERIC(5, 2),
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    
    -- Артикул: 3 заглавные буквы, дефис, 6 цифр
    CONSTRAINT chk_sku_format 
        CHECK (sku ~ '^[A-Z]{3}-\d{6}$'),
        
    -- Базовая стоимость строго больше 0
    CONSTRAINT chk_base_price_positive 
        CHECK (base_price > 0),
        
    -- Процент скидки от 0 до 90%
    CONSTRAINT chk_discount_percent_range 
        CHECK (discount_percent IS NULL OR (discount_percent >= 0 AND discount_percent <= 90)),
        
    -- Цена по акции строго меньше базовой цены
    CONSTRAINT chk_sale_price_less_than_base 
        CHECK (sale_price IS NULL OR sale_price < base_price),
        
    -- Связанность скидочных реквизитов: либо оба заданы, либо оба NULL
    CONSTRAINT chk_discount_pair_integrity 
        CHECK ((sale_price IS NULL AND discount_percent IS NULL) OR 
               (sale_price IS NOT NULL AND discount_percent IS NOT NULL))
);
```

#### 2. Пример логического тупика (взаимоисключающие предикаты)
Пример фатального проектирования:
```sql
CONSTRAINT chk_deadlock_condition CHECK (base_price > 5000 AND base_price < 1000)
```
Данное логическое выражение никогда не вернет `TRUE`, так как не существует вещественного числа, которое одновременно строго больше 5000 и строго меньше 1000. Таблица с таким ограничением полностью блокируется для операций `INSERT` и `UPDATE`. Другой пример — конфликт внешнего ключа: `FOREIGN KEY (category_id) REFERENCES categories(id)` в сочетании с `CHECK (category_id < 0)`, если первичные ключи категорий начинаются с 1.

#### 3. Тестовые проверочные запросы
```sql
-- Тест 1: Успешная вставка валидного товара
INSERT INTO marketplace_goods (sku, title, base_price, sale_price, discount_percent)
VALUES ('ELC-109283', 'Игровая мышь Wireless Pro', 4500.00, 3600.00, 20.00);

-- Тест 2: Ошибка формата артикула (маленькие буквы вместо заглавных)
INSERT INTO marketplace_goods (sku, title, base_price)
VALUES ('elc-109283', 'Клавиатура', 2500.00);
-- Ошибка: violates check constraint "chk_sku_format"

-- Тест 3: Ошибка скидочной цены (цена по акции выше базовой)
INSERT INTO marketplace_goods (sku, title, base_price, sale_price, discount_percent)
VALUES ('ELC-998877', 'Монитор 27"', 20000.00, 25000.00, 10.00);
-- Ошибка: violates check constraint "chk_sale_price_less_than_base"
```

### Задание 2. Исправление коллизий таблицы `loyalty_cards`
1. **Найденные логические ошибки:**
   - `discount_rate > 5 AND discount_rate < 3` — логически невозможное пересечение интервалов ($x > 5 \land x < 3 \equiv \emptyset$).
   - `min_spend >= 10000 AND max_spend <= 5000` в сочетании с неявным бизнес-правилом $min < max$ приводит к пустому множеству допустимых значений.
   - `card_status IN ('ACTIVE', 'BLOCKED') AND card_status = 'PENDING'` — статус не может быть одновременно равен 'PENDING' и входить во множество {'ACTIVE', 'BLOCKED'}.
2. **Исправленный блок ограничений:**
```sql
ALTER TABLE loyalty_cards
    ADD CONSTRAINT chk_discount_rate_range 
        CHECK (discount_rate BETWEEN 3.00 AND 25.00),
    ADD CONSTRAINT chk_spend_consistency 
        CHECK (min_spend >= 0 AND max_spend > min_spend),
    ADD CONSTRAINT chk_status_valid 
        CHECK (card_status IN ('ACTIVE', 'BLOCKED', 'PENDING'));
```

### Задание 3. Коворкинг с EXCLUDE и DEFERRABLE
```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE coworking_zones (
    zone_id INT PRIMARY KEY,
    zone_name VARCHAR(100) NOT NULL,
    vip_desk_id INT NOT NULL
);

CREATE TABLE coworking_desks (
    desk_id INT PRIMARY KEY,
    zone_id INT NOT NULL REFERENCES coworking_zones(zone_id) ON DELETE CASCADE,
    desk_code VARCHAR(20) NOT NULL
);

ALTER TABLE coworking_zones
    ADD CONSTRAINT fk_zone_vip_desk
    FOREIGN KEY (vip_desk_id) REFERENCES coworking_desks(desk_id)
    DEFERRABLE INITIALLY DEFERRED;

CREATE TABLE desk_rentals (
    rental_id BIGSERIAL PRIMARY KEY,
    desk_id INT NOT NULL REFERENCES coworking_desks(desk_id),
    rental_period TSRANGE NOT NULL,
    client_name VARCHAR(100) NOT NULL,
    CONSTRAINT chk_period_valid CHECK (lower(rental_period) < upper(rental_period)),
    CONSTRAINT exc_desk_no_overlap EXCLUDE USING gist (
        desk_id WITH =,
        rental_period WITH &&
    )
);

-- Транзакция атомарной вставки:
BEGIN;
    INSERT INTO coworking_zones (zone_id, zone_name, vip_desk_id) VALUES (1, 'Open Space Green', 101);
    INSERT INTO coworking_desks (desk_id, zone_id, desk_code) VALUES (101, 1, 'VIP-DESK-01');
COMMIT;
```

## 5. Классификатор типичных студенческих ошибок и штрафная шкала

| Код ошибки | Описание дефекта в ответе студента | Штраф |
| :---: | :--- | :---: |
| **ERR-01** | **Отсутствие якорей в regex:** написание регулярного выражения без `^` и `$` (поиск подстроки вместо строгого соответствия). | **-0.5 балла** |
| **ERR-02** | **Пропуск расширения btree_gist:** попытка создать `EXCLUDE USING gist` со скалярным равенством (`room_id WITH =`) без `CREATE EXTENSION btree_gist`. | **-0.5 балла** |
| **ERR-03** | **Подмена EXCLUDE простым UNIQUE:** попытка решить проблему овербукинга через `UNIQUE(room_id, start_time)`, игнорируя наложение интервалов. | **-1.0 балл** |
| **ERR-04** | **Непонимание циклического дедлока:** предложение убрать `NOT NULL` вместо использования `DEFERRABLE INITIALLY DEFERRED`. | **-0.5 балла** |
