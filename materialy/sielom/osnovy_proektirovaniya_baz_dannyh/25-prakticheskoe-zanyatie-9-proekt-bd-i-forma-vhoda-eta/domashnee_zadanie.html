Домашнее задание - Практическое занятие №9: проект БД и форма входа, этап 1

⚠ Выполняйте только если преподаватель назначил это задание. Срок сдачи сообщит преподаватель.
Дисциплина: ОП.08 Основы проектирования баз данных
Тематический раздел: Тема 4. Проектирование структур баз данных (§2.2 с.7–8)
Трудоемкость: 2 академических часа (внеаудиторная самостоятельная работа)
Максимальный балл: 4 балла (по критериальной рубрике)

1. Назначение и цель домашнего задания

Резервное дистанционное домашнее задание предназначено для студентов, пропустивших аудиторное занятие либо направленных на углубленную самостоятельную проработку этапа 1 курсового/практического проекта БД.

Цель задания: спроектировать архитектуру реляционных таблиц подсистемы учетных записей пользователей с разграничением прав доступа и разработать детальный макет диалогового окна формы входа (Login Dialog) для выбранной предметной области.

2. Варианты предметных областей

Студент выбирает вариант, соответствующий его номеру в журнале учебной группы (по модулю 4: 1, 2, 3 или 4):

Вариант Информационная система Требуемые роли пользователей Отраслевая специфика формы входа
Вариант 1 Информационная система «Оптовый склад» Кладовщик, Менеджер, Бухгалтер, Администратор Поле выбора филиала/склада из выпадающего списка; скрытие символов пароля маркерами; блокировка кнопки входа при пустых полях.
Вариант 2 Медицинская система поликлиники Врач, Регистратор, Главврач Авторизация по табельному номеру сотрудника; макет поля ввода кода двухфакторной аутентификации (2FA / OTP-код из SMS/приложения).
Вариант 3 Банковский терминал обслуживания Оператор, Кредитный инспектор, Контролер Виртуальная цифровая клавиатура (экранный ввод PIN/пароля со случайным перемешиванием кнопок); защита от подглядывания (Shoulder Surfing).
Вариант 4 Образовательный портал колледжа Студент, Преподаватель, Куратор, Родитель Форма входа по логину/email; интерактивная ссылка «Забыли пароль» с проектированием сценария безопасного сброса через временный токен.

3. Структура отчета и требования к выполнению

Отчет по домашнему заданию оформляется в электронном виде и должен содержать три обязательных раздела:

Раздел 1. Проектирование реляционных таблиц подсистемы безопасности (2 балла)

  • DDL-скрипт создания таблицы ролей roles (id, role_name, role_description, created_at).
  • DDL-скрипт создания таблицы учетных записей users (id, login, salt, password_hash, role_id, is_active, failed_attempts, created_at). Обязательно обосновать размерности полей (длина хэша для выбранного алгоритма хэширования, длина соли).
  • DDL-скрипт создания таблицы аудита audit_logs (id, user_id, attempted_login, event_type, ip_address, event_time) с внешним ключом ON DELETE SET NULL.

Раздел 2. Проектирование макета диалогового окна формы входа (1 балл)

  • Графический эскиз или структурированный текстовый макет окна Login Dialog.
  • Описание состояний интерфейса: начальное состояние (IDLE), процесс проверки (SUBMITTING), вывод ошибки (AUTH_ERROR), успешный вход (SUCCESS).
  • Реализация отраслевой специфики согласно варианту (филиал склада / 2FA-код / виртуальная клавиатура / восстановление пароля).
Образец компоновки формы входа

Раздел 3. Аналитическое обоснование и самопроверка (1 балл)

  • Обосновать, почему выбрано хэширование с солью (SHA-256 + Salt или bcrypt), а не обычное хэширование MD5/SHA-1 без соли.
  • Объяснить, почему диалоговое окно должно выводить нейтральное сообщение «Неверный логин или пароль» вместо подсказки «Пользователь не найден».
  • Описать, каким образом флаг is_active = FALSE защищает целостность связей в базе данных при увольнении сотрудника.

4. Критерии оценивания домашнего задания (0–4 балла)

  • 2 балла: Полная и синтаксически корректная спецификация таблиц users, roles, audit_logs; первичные и внешние ключи согласованы; присутствуют поля salt, password_hash, is_active.
  • 1 балл: Продуманный макет формы входа с учетом отраслевой специфики варианта; описаны состояния интерфейса и защита от повторной отправки.
  • 1 балл: Развернутое аналитическое обоснование криптографических решений, аргументация защиты от перечисления пользователей (User Enumeration) и ответы на вопросы самопроверки.
