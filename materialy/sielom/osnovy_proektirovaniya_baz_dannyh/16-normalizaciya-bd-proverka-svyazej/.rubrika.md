## 3. Полные закрытые эталоны решений по 4 практическим вариантам

### Вариант 1. Отношение R(A, B, C) с ФЗ {A → B}

#### 1. Проверка Схемы №1 (R₁(A, B) и R₂(A, C)) по теореме Риссанена
1. Пересечение атрибутов подсхем: $X = R_1 \cap R_2 = \{A, B\} \cap \{A, C\} = \{A\}$.
2. Вычисляем замыкание атрибута $A$ относительно множества ФЗ $F = \{A \to B\}$:
   * Инициализация: $A^{(0)} = \{A\}$.
   * Применяем $A \to B$: $A^{(1)} = \{A, B\}$.
   * Других зависимостей нет, поэтому $A^+ = \{A, B\}$.
3. Проверяем вхождение подсхем в замыкание:
   * $R_1 = \{A, B\} \subseteq A^+$. Следовательно, функциональная зависимость $A \to R_1$ принадлежит $F^+$, и атрибут $A$ является суперключом (и первичным ключом) для отношения $R_1$.
4. **Вывод:** По теореме Риссанена декомпозиция $D_1 = \{R_1(A, B), R_2(A, C)\}$ является **соединением без потерь данных (Lossless-Join)**. Операция $R_1 \bowtie R_2$ гарантированно восстанавливает $R$ в точности.

#### 2. Проверка Схемы №2 (R₁(A, B) и R₃(B, C)) по теореме Риссанена
1. Пересечение атрибутов подсхем: $Y = R_1 \cap R_3 = \{A, B\} \cap \{B, C\} = \{B\}$.
2. Вычисляем замыкание атрибута $B$ относительно множества ФЗ $F = \{A \to B\}$:
   * В левой части зависимости стоит $A$. Из атрибута $B$ мы не можем вывести $A$.
   * Следовательно, $B^+ = \{B\}$.
3. Проверяем вхождение подсхем в замыкание:
   * $R_1 = \{A, B\} \not\subseteq B^+$ (атрибут $A$ не содержится в замыкании).
   * $R_3 = \{B, C\} \not\subseteq B^+$ (атрибут $C$ не содержится в замыкании).
   * Ни одно из условий теоремы Риссанена не выполнено: атрибут $B$ не является суперключом ни для $R_1$, ни для $R_3$.
4. **Вывод:** Декомпозиция $D_2 = \{R_1(A, B), R_3(B, C)\}$ является **декомпозицией с потерями (Lossy)**. Естественное соединение $R_1 \bowtie R_3$ порождает ложные кортежи.

#### 3. Числовой контрпример с ложными кортежами (Spurious Tuples)
Зададим исходное отношение $r(R)$ из двух кортежей, удовлетворяющих $A \to B$:
* Кортеж 1: $(a_1, b_1, c_1)$
* Кортеж 2: $(a_2, b_1, c_2)$

Построим проекции:
* Проекция $\pi_{R_1}(r)$:
  * $(a_1, b_1)$
  * $(a_2, b_1)$
* Проекция $\pi_{R_3}(r)$:
  * $(b_1, c_1)$
  * $(b_1, c_2)$

Выполняем естественное соединение $\pi_{R_1}(r) \bowtie \pi_{R_3}(r)$ по общему атрибуту $B$ (значение $b_1$ совпадает во всех строках):
1. $(a_1, b_1) \bowtie (b_1, c_1) \to (a_1, b_1, c_1)$ — **истинный кортеж** (был в исходном отношении).
2. $(a_1, b_1) \bowtie (b_1, c_2) \to (a_1, b_1, c_2)$ — **ЛОЖНЫЙ КОРТЕЖ (Spurious Tuple)**!
3. $(a_2, b_1) \bowtie (b_1, c_1) \to (a_2, b_1, c_1)$ — **ЛОЖНЫЙ КОРТЕЖ (Spurious Tuple)**!
4. $(a_2, b_1) \bowtie (b_1, c_2) \to (a_2, b_1, c_2)$ — **истинный кортеж** (был в исходном отношении).

**Результат:** 2 исходных кортежа превратились в 4 кортежа. Система сгенерировала 2 паразитных факта, которых не существовало в реальном мире.

#### 4. Самопроверка и выводы
Соединение без потерь гарантируется только тогда, когда связывание выполняется через атрибут, однозначно идентифицирующий кортежи хотя бы в одной из соединяемых таблиц (то есть через суперключ / первичный ключ). Соединение по неключевому атрибуту неизбежно приводит к размножению строк по правилу декартова произведения внутри групп одинаковых значений.

### Вариант 2. База заказов маркетплейса (сохранение зависимости суммы)

#### 1. Анализ декомпозиции и сохранения зависимости Сумма = Количество * Цена_за_ед
При наивном разделении таблицы на $R_1(\text{Номер\_заказа}, \text{Артикул}, \text{Количество})$ и $R_2(\text{Артикул}, \text{Цена\_в\_каталоге})$ с полным удалением поля `Сумма`:
* Зависимость $\{\text{Количество}, \text{Цена}\} \to \text{Сумма}$ оказывается полностью разорванной.
* Атрибут `Количество` находится в $R_1$, а атрибут `Цена` — в $R_2$. Ни в одной из локальных таблиц проверить ограничение целостности без выполнения внешнего `JOIN` невозможно.
* Теряется свойство локального сохранения функциональных зависимостей (Dependency Preservation).

#### 2. Анализ историчности цен (Point-in-Time Pricing) и бухгалтерские риски
Замена атрибута `Цена_за_ед` в строке заказа на динамическую выборку цены из каталога `Products` по внешнему ключу `Артикул` представляет собой **критическую архитектурную ошибку**:
1. **Искажение истории транзакций:** Цены в каталоге регулярно меняются (акции, скидки, инфляция, переоценка поставщика). Если в таблице заказов нет зафиксированной цены на момент оформления сделки, то при изменении цены в каталоге автоматически пересчитаются суммы всех прошлых закрытых заказов за предыдущие месяцы и годы.
2. **Юридические и финансовые последствия:** Невозможно восстановить юридически значимый кассовый чек, нарушается бухгалтерский учет, налоговая отчетность признается недостоверной, клиентам выставляются некорректные финансовые претензии.

#### 3. Синтез корректной схемы реляционных таблиц
Каноническая архитектура требует фиксации фактической цены продажи в момент создания заказа:
1. `Заказы` (`ID_заказа` [PK], `ID_клиента`, `Дата_заказа`, `Статус`)
2. `Строки_заказа` (`ID_заказа` [FK], `Артикул` [FK], `Количество`, `Цена_фактическая`, `Сумма_позиции`) — PK: `{ID_заказа, Артикул}`.
   * Ограничение целостности: `CHECK (Сумма_позиции = Количество * Цена_фактическая)`.
   * Поле `Сумма_позиции` может быть вычисляемым столбцом (`GENERATED ALWAYS AS (Количество * Цена_фактическая) STORED`), что гарантирует сохранение зависимости и отсутствие избыточных аномалий обновления.
3. `Товары` (`Артикул` [PK], `Название_товара`, `Текущая_базовая_цена`)

#### 4. Самопроверка и выводы
Хранение цены транзакции в строке заказа — это обязательный инженерный паттерн фиксации снимка состояния (Snapshot / Point-in-time value). Вычисляемые поля, зависящие от атрибутов разных сущностей, должны либо материализоваться с жесткой фиксацией исторических аргументов, либо генерироваться СУБД строго на основе локальных атрибутов строки.

### Вариант 3. Отношение «Преподаватели, Дисциплины, Учебники» (MVD и 4НФ)

#### 1. Анализ первичного ключа и формального статуса НФБК
* Поскольку один преподаватель ведет много дисциплин, и один преподаватель рекомендует много учебников, а между дисциплинами и учебниками нет функциональной зависимости, ни один атрибут или пара атрибутов не определяют третий функционально:
  * $\text{Преподаватель} \not\to \text{Дисциплина}$
  * $\text{Преподаватель} \not\to \text{Учебник}$
  * $\{\text{Преподаватель}, \text{Дисциплина}\} \not\to \text{Учебник}$
* Единственным потенциальным ключом отношения является все множество атрибутов: $K = \{\text{Преподаватель}, \text{Дисциплина}, \text{Учебник}\}$.
* Поскольку в отношении отсутствуют нетривиальные функциональные зависимости, все функциональные зависимости тривиальны (вида $K \to A$, где $A \in K$). Следовательно, отношение **формально находится в нормальной форме Бойса-Кодда (НФБК)**. Однако оно страдает от тяжелой избыточности!

#### 2. Выявление MVD и расчет комбинаторного взрыва строк
В отношении действуют две независимые многозначные зависимости:
* $\text{Преподаватель} \twoheadrightarrow \text{Дисциплина}$
* $\text{Преподаватель} \twoheadrightarrow \text{Учебник}$

**Расчет строк:** Для 1 преподавателя, ведущего 3 дисциплины и рекомендующего 4 учебника, требуется хранить декартово произведение множеств:
$$\text{Количество строк} = 1 \times 3 \times 4 = 12 \text{ строк!}$$
**Аномалия вставки (Insert Anomaly):** Если преподаватель решит рекомендовать 5-й учебник, система обязана вставить ровно 3 новые строки (по одной на каждую читаемую дисциплину). Если будет вставлена только 1 строка, нарушится семантика независимости пособий, и система посчитает, что данный учебник относится только к одному курсу.
**Аномалия удаления (Delete Anomaly):** Если преподаватель перестает вести одну дисциплину, необходимо найти и удалить сразу 4 строки по всем учебникам.

#### 3. Декомпозиция по теореме Фейгина и приведение к 4НФ
По теореме Фейгина, так как выполняется $\text{Преподаватель} \twoheadrightarrow \text{Дисциплина} \mid \text{Учебник}$, декомпозиция схемы на две проекции является соединением без потерь:
1. $R_1(\underline{\text{Преподаватель}}, \underline{\text{Дисциплина}})$ — PK: $\{\text{Преподаватель}, \text{Дисциплина}\}$.
2. $R_2(\underline{\text{Преподаватель}}, \underline{\text{Учебник}})$ — PK: $\{\text{Преподаватель}, \text{Учебник}\}$.

**Результат нормализации:**
* Объем хранения сократился с 12 строк до $3 + 4 = 7$ строк!
* Добавление нового учебника требует вставки ровно 1 строки в таблицу $R_2$.
* Аномалии вставки и удаления полностью устранены.
* Обе таблицы находятся в **4НФ**, так как в каждой из них нетривиальные MVD отсутствуют (или вырождены в тривиальные).

#### 4. Самопроверка и выводы
Отношение находится в 4НФ, если оно находится в НФБК и для любой нетривиальной многозначной зависимости $X \twoheadrightarrow Y$ ее детерминант $X$ является суперключом отношения. 4НФ устраняет избыточность независимых множеств фактов, с которой не справляется аппарат функциональных зависимостей 3НФ/НФБК.

### Вариант 4. Высоконагруженная витрина данных (контролируемая денормализация)

#### 1. Анализ проблемы производительности нормализованной схемы при аналитических выборках
В транзакционной схеме (3НФ) таблицы нормализованы: `Строки_чека` содержат только `ID_товара`, а само название `Название_товара` хранится в справочнике `Товары`.
При выполнении аналитического отчета по 50 миллионам строк в сутки (или по 500 миллионам за декаду):
* Запрос агрегации требует физического соединения:
  ```sql
  SELECT t.Название_товара, SUM(s.Количество), SUM(s.Количество * s.Цена_продажи)
  FROM Строки_чека s
  JOIN Товары t ON s.ID_товара = t.ID_товара
  GROUP BY t.Название_товара;
  ```
* СУБД вынуждена выполнять соединение методами Hash Join или Nested Loop по огромным массивам строк, что приводит к гигантскому случайному дисковому вводу-выводу (Random I/O), забивает буферный пул памяти (Buffer Pool) и вызывает деградацию производительности всего кластера.

#### 2. Обоснование решения о контролируемой денормализации витрины (OLAP)
* **Решение:** Продублировать неизменяемое текстовое поле `Название_товара` (и при необходимости `Категория`) непосредственно в строку аналитической таблицы `Строки_чека` (или витрины фактов `Fact_Sales`).
* **Эффект:** Запрос агрегации выполняется по единственной таблице без операции `JOIN`:
  ```sql
  SELECT Название_товара, SUM(Количество), SUM(Количество * Цена_продажи)
  FROM Fact_Sales
  GROUP BY Название_товара;
  ```
* Время выполнения (Query Latency) сокращается на порядки (с нескольких минут до сотен миллисекунд), снимается паразитная нагрузка с процессора.

#### 3. Архитектурные риски денормализации и компенсирующие механизмы
* **Риски:**
  1. *Рассинхронизация данных (Data Inconsistency):* Если менеджер в каталоге исправит опечатку в названии товара, старые строки витрины останутся со старым названием, что разорвет агрегацию на две разные группы.
  2. *Разрастание объема памяти (Storage Overhead):* Хранение строк вместо 4-байтных целочисленных идентификаторов увеличивает объем таблицы фактов на десятки гигабайт.
* **Компенсирующие механизмы:**
  1. *Триггеры СУБД:* При изменении названия в справочнике `Товары` триггер каскадно обновляет строки в витрине (подходит для умеренных объемов).
  2. *Потоковая синхронизация CDC (Change Data Capture):* Использование инструментов вроде Debezium/Kafka для асинхронного распространения обновлений справочников в хранилище данных без блокировки транзакций.
  3. *Регламентные ночные ETL/ELT-пакеты:* Полная фоновая сверка и перестроение материализованных витрин в часы наименьшей нагрузки.

#### 4. Самопроверка и выводы
Золотое правило архитектора БД: *«Нормализуй при логическом проектировании до 3НФ/4НФ для обеспечения абсолютной целостности транзакций (OLTP); денормализуй только физический слой и только под профилированную аналитическую нагрузку чтения (OLAP), обязательно закладывая компенсирующие механизмы синхронизации данных»*.

## 4. Полный закрытый эталон решения домашнего задания (domashnee_zadanie.html)

### Задание 1. Формулировка и инженерный смысл критерия Риссанена
* **Математическая формулировка:** Декомпозиция схемы $R$ на подсхемы $\{R_1, R_2\}$ ($R_1 \cup R_2 = R$) является соединением без потерь относительно множества ФЗ $F$ тогда и только тогда, когда выполняется хотя бы одно из условий:
  $$(R_1 \cap R_2 \to R_1) \in F^+ \quad \text{ИЛИ} \quad (R_1 \cap R_2 \to R_2) \in F^+$$
* **Инженерный смысл:** Общий набор атрибутов двух декомпозированных отношений обязан являться суперключом (однозначно идентифицировать все атрибуты) хотя бы для одного из полученных отношений.

### Задание 2. Проверка бинарной декомпозиции R(A, B, C, D) с F = {A → B, B → C, C → D}
* **Вариант декомпозиции I: $R_1(A, B, C)$ и $R_2(C, D)$**
  1. Пересечение: $X = R_1 \cap R_2 = \{C\}$.
  2. Замыкание: $C^+ = \{C, D\}$ (по зависимости $C \to D$).
  3. Проверка: $R_2 = \{C, D\} \subseteq C^+$. Следовательно, $C \to R_2$ выполняется, и атрибут $C$ является первичным ключом для $R_2$.
  4. **Вывод:** Декомпозиция является **соединением без потерь (Lossless-Join)**.
* **Вариант декомпозиции II: $R_1(A, B)$ и $R_3(B, C, D)$**
  1. Пересечение: $Y = R_1 \cap R_3 = \{B\}$.
  2. Замыкание: $B^+ = \{B, C, D\}$ (по зависимостям $B \to C$ и $C \to D$).
  3. Проверка: $R_3 = \{B, C, D\} \subseteq B^+$. Следовательно, $B \to R_3$ выполняется, и атрибут $B$ является первичным ключом для $R_3$.
  4. **Вывод:** Декомпозиция также является **соединением без потерь (Lossless-Join)**.

### Задание 3. Числовой контрпример ложных кортежей для R(A, B, C) с F = {A → B} при декомпозиции на R₁(A, B) и R₂(B, C)
* **Исходные данные:**
  * $t_1 = (a_1, b_1, c_1)$
  * $t_2 = (a_2, b_1, c_2)$
* **Проекция $R_1(A, B)$:** $(a_1, b_1)$, $(a_2, b_1)$.
* **Проекция $R_2(B, C)$:** $(b_1, c_1)$, $(b_1, c_2)$.
* **Результат соединения $R_1 \bowtie R_2$:**
  * $(a_1, b_1, c_1)$ — истинный.
  * $(a_1, b_1, c_2)$ — **ложный кортеж (Spurious Tuple)**.
  * $(a_2, b_1, c_1)$ — **ложный кортеж (Spurious Tuple)**.
  * $(a_2, b_1, c_2)$ — истинный.

### Задание 4. Практический инженерный кейс (Служба доставки)
* **Схема:** $R(\text{Номер\_заказа}, \text{Курьер\_ID}, \text{Тип\_транспорта}, \text{Зона\_доставки})$.
* **ФЗ:** $\text{Номер\_заказа} \to \{\text{Курьер\_ID}, \text{Зона\_доставки}\}$, $\text{Курьер\_ID} \to \text{Тип\_транспорта}$.
* **Первичный ключ:** $\text{Номер\_заказа}$.
* **Декомпозиция:**
  1. $R_1(\underline{\text{Номер\_заказа}}, \text{Курьер\_ID}, \text{Зона\_доставки})$
  2. $R_2(\underline{\text{Курьер\_ID}}, \text{Тип\_транспорта})$
* **Доказательство по Риссанену:**
  * Пересечение: $R_1 \cap R_2 = \{\text{Курьер\_ID}\}$.
  * Замыкание: $\text{Курьер\_ID}^+ = \{\text{Курьер\_ID}, \text{Тип\_транспорта}\} = R_2$.
  * Так как $R_1 \cap R_2 \to R_2$, декомпозиция является соединением без потерь!

### Задание 5. Самопроверка
1. Кортежей становится больше из-за перекрестного соединения строк по неуникальному общему атрибуту (декартово произведение внутри совпавших групп значений).
2. Соединение без потерь гарантирует точное восстановление исходных данных при объединении, а сохранение ФЗ гарантирует возможность локальной проверки бизнес-правил без межтабличных соединений.
3. Денормализация применяется в аналитических системах (OLAP / DWH) для ускорения агрегирующих запросов и исключения дорогостоящих операций JOIN по миллионам строк.
