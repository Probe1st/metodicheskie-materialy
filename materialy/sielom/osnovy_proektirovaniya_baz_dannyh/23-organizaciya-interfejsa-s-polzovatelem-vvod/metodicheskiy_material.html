2. Архитектурные принципы сопряжения UI и реляционной базы данных

2.1. Многоуровневая (n-уровневая) архитектура и изоляция слоев

Фундаментальный принцип современной программной инженерии при работе с базами данных — строгое разделение ответственности (Separation of Concerns, SoC). Прямой доступ интерфейса пользователя к базе данных категорически запрещен в промышленных информационных системах, так как создает критические уязвимости безопасности (SQL Injection, перехват учетных данных БД), исключает масштабирование и делает систему неподдерживаемой.

+-----------------------------------------------------------------------+
| УРОВЕНЬ ПРЕДСТАВЛЕНИЯ (Presentation Layer / View) | Элементы управления: Input, Select, DatePicker, Таблицы Detail |
+-----------------------------------+-----------------------------------+
 | (События UI: Submit, Change, Input)
 v
+-----------------------------------------------------------------------+
| УРОВЕНЬ БИЗНЕС-ЛОГИКИ И КООРДИНАЦИИ (Controller / Service / Backend) | - Парсинг DTO, валидация бизнес-правил, аутентификация пользователя | - Управление транзакциями (Transaction Boundary: BEGIN / COMMIT) |
+-----------------------------------+-----------------------------------+
 | (Вызов методов репозитория / DAO)
 v
+-----------------------------------------------------------------------+
| УРОВЕНЬ ДОСТУПА К ДАННЫМ (Data Access Layer / DAO / ORM Repository) | - Формирование параметризованных запросов INSERT / UPDATE / SELECT | - Преобразование объектов (Object-Relational Mapping / Data Mapper) |
+-----------------------------------+-----------------------------------+
 | (SQL через драйвер БД: JDBC, Npgsql, asyncpg)
 v
+-----------------------------------------------------------------------+
| СЛОЙ ХРАНЕНИЯ ДАННЫХ (Database Engine / PostgreSQL, MySQL, Oracle) | - Первичные (PK) и внешние (FK) ключи, CHECK, UNIQUE, NOT NULL | - Индексы, триггеры целостности, ACID-гарантии хранения |
+-----------------------------------------------------------------------+

2.2. Паттерны организации пользовательского интерфейса (MVC, MVP, MVVM)

  • MVC (Model-View-Controller): Классический паттерн. View отображает форму ввода и генерирует события. Controller перехватывает ввод, формирует команды обновления Model (доменных сущностей и репозиториев) и определяет следующее отображение. В веб-приложениях MVC часто реализуется через серверные шаблонизаторы или связку SPA-клиента и REST-контроллера на бэкенде.
  • MVP (Model-View-Presenter): Presenter полностью берет на себя логику координации, извлекая значения из пассивного View через интерфейс и передавая их в модель. Широко применяется в настольных толстых клиентах (WinForms, WPF).
  • MVVM (Model-View-ViewModel): Стандарт современных клиентских фреймворков (Vue, Angular, React с хуками, WPF). ViewModel хранит реактивное состояние формы, а механизм декларативного Data Binding автоматически синхронизирует состояние контролов и свойств модели.

2.3. Механизм связывания данных (Data Binding)

Data Binding (привязка данных) — программный мост между графическими элементами пользовательского интерфейса (UI Controls) и атрибутами программных моделей / реляционных таблиц. Различают два основных типа связывания:

  • Одностороннее связывание (One-Way Binding, View ← Model или Model ← View): Данные передаются только в одном направлении. Например, при открытии формы редактирования атрибуты строки таблицы инициализируют поля UI; либо при клике кнопки «Сохранить» снимок полей формы переносится в объект запроса (DTO).
  • Двустороннее связывание (Two-Way Binding, View ↔ ViewModel): Любое изменение пользователем текста в <input> немедленно модифицирует свойство в оперативной памяти, а программное изменение модели мгновенно перерисовывает контрол интерфейса.
Педагогический акцент: Студентам необходимо четко разъяснить: форма ввода никогда не связывается с таблицей БД напрямую. Связывание на стороне клиента всегда происходит с DTO (Data Transfer Object) или ViewModel, а затем бэкенд транслирует DTO в реляционную строку через слой DAO/ORM с помощью параметризованных команд SQL.

3. Инженерная типология элементов ввода и правила их маппинга на атрибуты БД

Каждый столбец реляционной таблицы обладает строгим типом данных, диапазоном допустимых значений и ограничениями целостности. Выбор графического контрола в UI должен строго соответствовать реляционной семантике атрибута:

Элемент управления UI Тип данных в СУБД (PostgreSQL / ANSI) Назначение и поддерживаемые ограничения Принцип сопряжения и маппинга
Текстовое поле с маской ввода (Masked Input) VARCHAR(n), CHAR(n), предикаты CHECK (col ~ '^[0-9...]+$') Структурированные строковые идентификаторы: телефоны, СНИЛС, ИНН, почтовые индексы, номера авто, паспорта. Маска отсекает некорректные символы в реальном времени. В БД передается очищенная строка без символов маски (raw-значение), либо нормализованная строка строго фиксированной длины.
Выпадающий список (Combobox / Select / Autocomplete) INT, BIGINT, UUID со связью FOREIGN KEY REFERENCES parent(id) Отображение связей «многие к одному» (M:1). Выбор значения из родительского справочника (клиенты, товары, города, статусы). Разделение Text и Value: пользователю отображается читаемое имя display_name, а в DTO и далее во внешний ключ foreign_key_id записывается первичный ключ выбранной записи. При больших справочниках (>100 записей) обязателен динамический Autocomplete с сервером.
Группа переключателей (RadioGroup) VARCHAR(n), ENUM, INT (код статуса), CHECK (status IN (...)) Взаимоисключающий выбор из небольшого фиксированного набора альтернатив (от 2 до 5 вариантов): приоритет (Low/Medium/High), пол, режим доставки. Все радиокнопки объединяются общим атрибутом name. Атрибут value выбранной кнопки напрямую мапится в строковую константу перечисления или код категории. Исключает ввод пустого значения, если один пункт выбран по умолчанию.
Флажок (Checkbox / Switch) BOOLEAN (BOOLEAN NOT NULL DEFAULT FALSE) Бинарные атрибуты и флаги состояния: «Активен», «Доставлен», «Согласен на обработку ПДн», «НДС включен». Состояние checked конвертируется в TRUE или FALSE. Для nullable-булевых колонок в СУБД требуется трехпозиционный переключатель (Tri-state checkbox), но в проектировании UI их рекомендуется избегать.
Выбор даты и времени (DatePicker / DateTimePicker) DATE, TIMESTAMP, TIMESTAMPTZ, интервалы TSRANGE Календарные даты, время создания, дата отгрузки, дата госпитализации. Календарный виджет предотвращает ввод несуществующих дат (например, 31 февраля). Маппинг выполняется в стандартном формате ISO 8601 (YYYY-MM-DD или YYYY-MM-DD"T"HH:mm:ssZ) для исключения региональных коллизий СУБД.
Табличная часть деталей (Master-Detail Grid) Две связанные таблицы master (id PK) и detail (id PK, master_id FK) Спецификации заказов, позиции накладной, этапы работ, прикрепленные документы. Отношение 1:M. Шапка формы привязана к записи Master. Табличная сетка отображает массив строк Detail. При сохранении весь пакет (Master + массив Detail) передается в бэкенд единым DTO и записывается в одной транзакции СУБД.

4. Компоновка форм ввода и правила эргономики UI (UX-инженерия)

Качество проектного решения оценивается не только правильностью типов данных, но и эргономикой формы (сокращение числа ошибок оператора, снижение утомляемости, скорость ввода):

Золотые правила компоновки экранных форм ввода:
  1. Естественный поток взгляда (F- и Z-паттерны): Логическое группирование полей сверху вниз и слева направо. Разделение формы на семантические карточки/блоки: «Основная информация», «Адресные реквизиты», «Спецификация».
  2. Клавиатурная навигация (Tab Order): Корректный порядок табуляции (tabindex) — оператор должен иметь возможность заполнить всю форму и отправить ее (Enter), не касаясь мыши.
  3. Индикация обязательности полей: Все атрибуты со свойством NOT NULL должны быть явно помечены визуальным маркером (символ звездочки *) и поясняющим текстом.
  4. Автофокус на первом поле: При загрузке формы курсор автоматически позиционируется в первое поле ввода (autofocus).
  5. Предотвращение двойной отправки (Double Submit Prevention): После клика кнопки «Сохранить» контрол немедленно блокируется (disabled) с индикацией процесса (spinner), исключая дублирование записей в СУБД при повторном клике.
  6. Контекстные подсказки и валидация «на лету» (Inline Validation): Ошибки подсвечиваются рядом с проблемным полем сразу при потере фокуса (событие blur), а не общим нечитаемым списком после перезагрузки экрана.

5. Типовые ошибки студентов и методы их педагогического устранения

Типовая ошибка студента Суть дефекта и последствия Педагогический прием устранения
Сохранение текстового наименования вместо ID внешнего ключа Студент связывает поле ввода клиента или категории с текстовым названием (client_name), записывая его напрямую в дочернюю таблицу. Это разрушает нормализацию (де-факто возврат к 0NF/1NF), приводит к дублированию строк и потере целостности при переименовании сущности. Разбор анатомии тега <select>: демонстрация атрибута value="142" (PK) в связке с видимым текстом ООО "Альфа". Пояснение механизма реляционного JOIN по числовому суррогатному ключу.
Прямой SQL-запрос из обработчика кнопки формы (Direct SQL) Вставка кода вида SELECT... FROM... или INSERT INTO прямо в обработчик события кнопки (onClick). Создает катастрофическую уязвимость SQL Injection, делает невозможным разграничение прав доступа и нарушает n-уровневую модель. Концептуальный разбор слоев. Показать архитектурный барьер: клиент → HTTP/JSON (DTO) → Backend Controller → Repository (SQL с параметрами) → СУБД.
Исключительная ставка на клиентскую валидацию Студент считает, что атрибутов HTML5 required, maxlength или JS-валидаторов достаточно для защиты БД, и не проектирует ограничения в самой СУБД (CHECK, NOT NULL). Показ сценария обхода: отправка запроса напрямую через cURL / Postman или отключение JavaScript в браузере. Вывод правила: «Клиентская валидация — для удобства пользователя (UX); серверные ограничения СУБД — для гарантии целостности (ACID)».
Разрушение атомарности в Master-Detail формах Студент сохраняет шапку заказа одним запросом, а каждую строку спецификации — отдельными несвязанными запросами без транзакции. При сбое сети или ошибке во второй строке в БД остается заказ-«пустышка» или полузаполненная спецификация. Объяснение транзакционного контекста: вся форма Master-Detail собирается в единый агрегат и фиксируется на бэкенде внутри блока BEGIN... COMMIT. При ошибке любой позиции спецификации происходит полный ROLLBACK.

6. Рекомендации по оцениванию и закрытая критериальная шкала

Оценивание результатов работы студентов на уроке производится по 4-балльной шкале, зафиксированной в критериальной рубрике .rubrika.md:

  • Критерий 1 (2 балла): Схема экранной формы ввода, корректный выбор UI-компонентов и компоновка (1 балл за неполный состав элементов или нарушение порядка ввода, 0 баллов за отсутствие схемы или бессистемный набор полей).
  • Критерий 2 (1 балл): Маппинг элементов управления формы на атрибуты реляционной БД (корректность разделения Value/Text для FK, соответствие типов данных, индикация NOT NULL).
  • Критерий 3 (1 балл): Эргономика пользовательского интерфейса, валидация и ответы на контрольные вопросы самопроверки.

Итоговая отметка выставляется по шкале СИЭУиП: 4 балла — «отлично» (5), 3 балла — «хорошо» (4), 2 балла — «удовлетворительно» (3), 0–1 балл — «неудовлетворительно» (2).
