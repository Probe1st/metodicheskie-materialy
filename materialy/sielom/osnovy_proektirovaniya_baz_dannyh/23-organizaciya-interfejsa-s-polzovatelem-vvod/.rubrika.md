# Закрытая критериальная рубрика преподавателя: Организация интерфейса с пользователем: ввод

Данный документ представляет собой закрытый методический инструмент преподавателя дисциплины «ОП.08 Основы проектирования баз данных» (СИЭУиП) и содержит критериальную шкалу оценивания, полные эталонные решения для всех 4 практических вариантов рабочего листа `zanyatie.html`, эталон резервного домашнего задания `domashnee_zadanie.html` и классификатор типовых студенческих ошибок со шкалой штрафных вычетов.

## 1. Паспорт оценивания занятия

- **Дисциплина:** ОП.08 Основы проектирования баз данных.
- **Тематический раздел:** Тема 4. Проектирование структур баз данных (§2.2 с.7–8 программы).
- **Тема занятия:** Организация интерфейса с пользователем: ввод (Занятие 23).
- **Вид занятия:** Урок с объяснением теории (2 академических часа: 80 минут основной регламент / 60 минут сокращенный).
- **Форма контроля:** Проверка индивидуального проектного продукта в интерактивном рабочем листе `zanyatie.html` (4 дифференцированных варианта) либо в резервном дистанционном задании `domashnee_zadanie.html`.
- **Критериальная шкала:** 4-балльная шкала (схема экранной формы и элементы 2 б., маппинг элементов на атрибуты БД 1 б., эргономика и самопроверка 1 б.):
  * **Часть 1. Схема экранной формы и элементы управления:** **2 балла** (1 балл за неполную схему или пропуск обязательных полей, 0 баллов при грубых ошибках компоновки).
  * **Часть 2. Маппинг элементов управления на атрибуты реляционной БД:** **1 балл** (0 баллов при сохранении текста вместо внешнего ключа FK или неверных типах данных).
  * **Часть 3. Эргономика UI, валидация и самопроверка:** **1 балл** (0 баллов при отсутствии ответов на вопросы самопроверки или непонимании двухуровневой валидации).
- **Срок сдачи:** До начала следующего занятия по расписанию.

### Вариант 1. Регистрация нового заказа в CRM-системе оптовых продаж (Master-Detail)

#### 1. Эталон компоновки формы (Задание 1.1)
- **Шапка документа (Карточка «Параметры заказа»):**
  * Поле 1: Номер заказа — `Masked Input` (шаблон `ORD-2026-99999`), генерируется автоматически или вводится с маской, `readonly` для оператора при автогенерации.
  * Поле 2: Дата заказа — `DatePicker` (по умолчанию текущая дата, формат ISO `YYYY-MM-DD`).
  * Поле 3: Контрагент (Клиент) — `Combobox / Autocomplete` со строкой поиска. Отображает `Наименование компании + ИНН`.
  * Поле 4: Склад отгрузки — `Select` (выпадающий список активных складов).
  * Поле 5: Статус — скрыт или доступен как информационный бейдж («Черновик»).
- **Спецификация (Табличная часть Detail Grid):**
  * Динамическая сетка с кнопками `[+ Добавить позицию]` и `[Удалить]`.
  * Колонки таблицы: `№ п/п` (авто), `Товар` (Autocomplete по каталогу), `Количество` (Number Input, шаг 1, min 0.001), `Цена` (Number Input, подтягивается из прайса, доступна корректировка по правам), `Скидка %` (Number Input 0–100), `Сумма` (Readonly, автовычисление: `Qty * Price * (1 - Discount/100)`).
- **Подвал формы:**
  * Информационная плашка: «Итого к оплате: X руб. Позиций: N».
  * Кнопка `[Сохранить и провести]` (Primary) с блокировкой `disabled` после клика.
  * Кнопка `[Отмена / Закрыть]` (Secondary).

#### 2. Матрица маппинга полей на атрибуты БД (Задание 1.2)
| Элемент UI | Атрибут БД | Тип данных в БД | Правило маппинга и разделение Display/Value | Валидация |
| :--- | :--- | :--- | :--- | :--- |

| Выбор клиента (Select) | `wholesale_orders.client_id` | `INT` | **Display:** `client_name (ИНН)`, **Value:** `client_id` (PK) | `NOT NULL, REFERENCES clients(id)` |
| Выбор склада (Select) | `wholesale_orders.warehouse_id` | `INT` | **Display:** `warehouse_name`, **Value:** `warehouse_id` (PK) | `NOT NULL, REFERENCES warehouses(id)` |
| Дата заказа (DatePicker) | `wholesale_orders.order_date` | `DATE` | Формат ISO 8601 (`YYYY-MM-DD`) | `NOT NULL` |

#### 3. Транзакционный JSON DTO и алгоритм сохранения (Задание 1.3)
```json
{
  "orderNumber": "ORD-2026-00481",
  "clientId": 104,
  "warehouseId": 2,
  "orderDate": "2026-10-01",
  "status": "draft",
  "items": [
    { "productId": 301, "quantity": 10, "unitPrice": 4500.00, "discountPercent": 5.00 },
    { "productId": 814, "quantity": 2, "unitPrice": 18200.00, "discountPercent": 0.00 }
  ]
}
```
```sql
BEGIN;

INSERT INTO wholesale_orders (order_number, client_id, warehouse_id, order_date, total_amount, status)
VALUES ('ORD-2026-00481', 104, 2, '2026-10-01', 79150.00, 'draft')
RETURNING order_id;

-- Предполагаем, что сгенерирован order_id = 1502
INSERT INTO wholesale_order_items (order_id, product_id, quantity, unit_price, discount_percent, line_total)
VALUES 
  (1502, 301, 10, 4500.00, 5.00, 42750.00),
  (1502, 814, 2, 18200.00, 0.00, 36400.00);

COMMIT;
```

#### 4. Ответы на вопросы самопроверки (Задание 1.4)
1. Сохранение каждой строки отдельным запросом недопустимо, так как нарушает атомарность (ACID). При сбое сети между строками 1 и 2 в базе останется частично сохраненный заказ с неверной итоговой суммой. Master-Detail требует единой неделимой транзакции.
2. В `<select>` или объекте Autocomplete используется разделение свойств: пользователю рендерится текстовая метка `Display Member` (например, "ООО Альфа"), а во внутреннее состояние формы и в DTO помещается числовой первичный ключ `Value Member` (`id = 104`).

### Вариант 2. Экранная форма оформления путевого листа АТП

#### 1. Эталон компоновки формы (Задание 2.1)
- Блок 1. «Параметры путевого листа»: Номер путевого листа (`Masked Input` вида `ПЛ-9999-9999`), Маршрут (`Combobox`).
- Блок 2. «Ресурсы автопарка»: Выбор автомобиля (`Combobox` с выводом госномера, марки и гаражного номера, значение — `vehicle_id`), Выбор водителя (`Combobox` с табельным номером и ФИО, значение — `driver_id`).
- Блок 3. «Хронометраж рейса»: `DateTimePicker` выезда и `DateTimePicker` возврата. Возврат опционален при выезде.
- Блок 4. «Одометр и допуски»: Поле «Одометр выезд, км» (NumberInput, обязательное), Поле «Одометр возврат, км» (NumberInput, блокируется до возврата). Флажки (Checkbox): `[x] Предрейсовый медосмотр пройден`, `[x] Технический контроль ТС пройден`.

#### 2. Матрица маппинга полей на атрибуты БД (Задание 2.2)

#### 3. Алгоритм валидации одометра и времени рейса (Задание 2.3)
- На клиенте (JS): на событии `blur` поля `odometer_end` выполняется проверка `if (endVal < startVal)`. При нарушении поле подсвечивается красной рамкой с текстом: «Показания одометра при возврате не могут быть меньше показаний при выезде».
- В ядре СУБД: предикат таблицы `CHECK (odometer_end >= odometer_start)` и `CHECK (return_time IS NULL OR return_time > departure_time)`. Даже если клиентский скрипт будет отключен, СУБД отвергнет некорректную транзакцию с ошибкой `check_violation`.

#### 4. Ответы на вопросы самопроверки (Задание 2.4)
1. DateTimePicker обязан передавать дату и время строго в стандарте ISO 8601 (`YYYY-MM-DDTHH:mm:ssZ`). Это исключает ошибки СУБД при различных локалях (разночтения между российским `DD.MM.YYYY` и американским `MM/DD/YYYY`).
2. В автопарке могут быть автомобили одинаковой марки или дублирующиеся гаражные номера филиалов. Комбинация `Госномер + Марка + Гаражный номер` обеспечивает безошибочную визуальную идентификацию машины диспетчером.

#### 3. Каскадное связывание списков (Задание 3.3)
При изменении значения в выпадающем списке «Отделение» (событие `change`) срабатывает обработчик:
1. Очищается текущее выбранное значение в списке «Лечащий врач».
2. Элемент «Лечащий врач» временно блокируется (`disabled = true`) с индикатором загрузки.
3. Отправляется асинхронный запрос к API: `GET /api/doctors?department_id=${deptId}`.
4. Полученный список врачей заполняет выпадающий список новыми элементами `<option value="doctor_id">ФИО</option>`, после чего контрол разблокируется.

#### 4. Ответы на вопросы самопроверки (Задание 3.4)
1. Сохранение текстовой формулировки вместо кода нарушает 3NF и создает дублирование данных. При изменении формулировки в справочнике старые записи останутся нескоординированными, а поиск и статистика по заболеваниям станут невозможными.
2. Маска ввода для СНИЛС блокирует ввод букв и лишних символов, гарантирует ввод ровно 11 цифр и позволяет на клиенте проверить контрольную сумму СНИЛС по официальному алгоритму до отправки запроса в СУБД.

#### 3. Ограничение длины текста и загрузка файлов (Задание 4.3)
- Счетчик символов: на событии `input` textarea вычисляется `2000 - textarea.value.length`. При приближении к нулю цвет счетчика меняется на предупреждающий оранжевый/красный.
- Загрузка файлов: файл передается через `multipart/form-data` на сервер, сохраняется в объектном хранилище (MinIO/S3), а в таблицу `ticket_attachments` записывается метаинформация: имя файла, размер, MIME-тип и путь `storage_path`. Это предотвращает раздувание таблиц СУБД бинарными BLOB-данными.

#### 4. Ответы на вопросы самопроверки (Задание 4.4)
1. Приоритет обязан иметь значение по умолчанию (`DEFAULT 'medium'`), чтобы заявка не оказалась в неопределенном статусе, если пользователь пропустил выбор или растерялся при оценке серьезности сбоя.
2. Если кнопка не блокируется, нетерпеливый пользователь кликает по ней несколько раз подряд, порождая в базе данных 2–3 идентичные заявки-дубликата, искажая нагрузку на службу поддержки.

### 4. Ответы на контрольные вопросы (Задание 4)
1. В интерфейсе у второго `DatePicker` (дата окончания) динамически устанавливается атрибут `min`, равный выбранному значению в первом `DatePicker` плюс 1 день. Это делает выбор некорректной даты физически невозможным в виджете календаря.
2. Текстовое поле позволит оператору ввести несуществующий номер офиса (например, «305-бис»), что вызовет ошибку `foreign_key_violation`, либо вписать офис, который уже занят другим арендатором. Выпадающий список предлагает только реально существующие и свободные помещения с фильтрацией на сервере.
3. Кнопка немедленно блокируется (`disabled = true`), ее текст заменяется на «Сохранение...» с показом спиннера, а форма перестает принимать повторные клики до завершения ответа сервера.
