Тестирование в жизненном цикле разработки

Что важно понять

Проверки распределяют по жизненному циклу, а не оставляют на последний день. Неясный текст требования выгодно найти при чтении требования; неверную ветвь расчёта — в модульном тесте; несовместимость API — при интеграционной проверке; непонятный сценарий покупки — при приёмке.

Статическое тестирование включает чтение требований, ревью кода, проверку схем и анализатор. Оно хорошо находит противоречия и пропуски до запуска. Динамическое тестирование исполняет программу и сравнивает фактическое поведение с ожиданием. Эти подходы дополняют друг друга.

Уровень отвечает на вопрос «какую границу мы проверяем?», а вид — «какое свойство проверяем?». Например, компонентный тест функции скидки проверяет функциональную пригодность, а системный тест может проверять безопасность доступа к заказу. Не смешивайте эти два измерения в отчёте.

Раннее тестирование не отменяет позднее. Модульный тест не покажет ошибку маршрутизации HTTP, а успешный ручной сценарий не гарантирует, что все ветви расчёта покрыты. Стратегия — это осознанный набор проверок, а не один любимый инструмент.

Рабочий пример

# Компонент: расчёт скидки
assert total_price(2, 500, 10) == 900

# Интеграция: HTTP-слой передаёт пользователя в сервис
response = client.get("/orders/17", headers={"X-User": "5"})
assert response.status_code == 200

После работы с материалом вы выбираете уровень, вид и момент проверки так, чтобы риск обнаруживался как можно раньше.

Ключевые понятия

Статическое тестирование

Проверка артефактов без выполнения программы.

Динамическое тестирование

Проверка поведения при запуске программы.

Уровень тестирования

Граница, на которой проверяется компонент, интеграция, система или приёмка.

Регрессия

Повторная проверка, выявляющая нежелательное влияние изменений.

Учебный кейс

После изменения формата скидки часть заказов не подтверждается, а часть получает неверную сумму. Разместите проверки по уровням и объясните, почему нельзя ограничиться ручной проверкой интерфейса.

Исходные данные

# Компонент: расчёт скидки
assert total_price(2, 500, 10) == 900

# Интеграция: HTTP-слой передаёт пользователя в сервис
response = client.get("/orders/17", headers={"X-User": "5"})
assert response.status_code == 200

Порядок действий

  1. Определите артефакты: требование, функция расчёта, API, пользовательский сценарий.
  2. Для каждого укажите подходящую раннюю проверку.
  3. Добавьте один риск, который останется до системного уровня.
  4. Составьте краткую последовательность проверок после изменения скидок.

Самопроверка

  • Я могу объяснить, какое правило проверяю.
  • Я использую конкретные данные и ожидаемый результат.
  • Мой вывод опирается на наблюдение, а не на предположение.

Практическая мини-задача

Выполните порядок действий, затем сравните свой результат с критериями самопроверки.
